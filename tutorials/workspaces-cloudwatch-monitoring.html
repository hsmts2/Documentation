CloudWatchのEC2・Windows OS監視とSNS通知

仕様

構成・動作

AWS Architecture Iconsを使用して、本環境の監視・通知経路を図示しています。AWS Architecture Icons

監視対象 名前空間・メトリクス 用途
EC2 AWS/EC2：StatusCheckFailed、CPUUtilization ステータスチェック失敗・CPU高負荷の検知
Windows OS CWAgent：LogicalDisk % Free Space、Memory % Committed Bytes In Use ドライブ空き容量・メモリコミット率の監視
通知 SNS StandardトピックとEmailサブスクリプション ALARMへの状態変更をメールで通知
可視化 CloudWatchダッシュボード メトリクス推移とアラーム状態の確認

管理範囲

CloudWatch agentの設定はSystems ManagerのRun CommandとParameter Storeで管理します。WorkSpacesの監視設定は「Amazon WorkSpaces監視設定手順」で実施し、通知先とダッシュボードを共用します。Windowsイベントログの収集は本書の設定に含みません。

制約事項

  • OKは設定した評価条件を満たした状態です。業務機能の確認は、対象サービス・OS・認証の確認と合わせて実施します。
  • 欠落データをnotBreachingとして扱うアラームは、メトリクス停止時にも正常扱いとなる可能性があります。データの最新時刻も点検します。
  • Memory % Committed Bytes In Useはコミット上限に対する使用率です。物理メモリ使用率とは計算対象が異なります。
  • しきい値は検証環境の初期値です。通常時の負荷と業務要件に合わせて確定します。

前提条件

既存リソース・ネットワーク

  • 対象のWindows EC2が起動し、Systems Managerのマネージドノードとしてオンラインであること。
  • EC2からSystems Manager、Parameter Store、CloudWatchへTCP/443で到達できること。NAT、プロキシ、または対応VPCエンドポイントを使用します。
  • 通知先メールアドレスが確定し、購読確認メールを受信できること。

権限・接続環境

作業者にはCloudWatchアラーム・ダッシュボードの管理、SNSトピック・購読・テスト発行、および対象リソースの参照権限が必要です。SCPやアクセス許可境界による制限も確認します。

EC2インスタンスロールにはAmazonSSMManagedInstanceCoreとCloudWatchAgentServerPolicyを使用します。作業者の管理権限とEC2の実行権限は分けて設定します。

構築作業

1. SNSトピックを作成する

  1. AWSマネジメントコンソールへサインインし、東京リージョンでAmazon SNSを開きます。
  2. 「トピック」で既存の通知先を確認します。同じ用途のトピックがある場合は、名前・ARN・通知先を照合して使用します。
  3. 新規作成する場合は「トピックの作成」を選択します。
  4. タイプを「スタンダード」、名前をsample-sns-cloudwatch-alertsにします。
  1. 表示名はメール通知のみの場合は空欄にできます。暗号化・アクセスポリシーは承認済み設計に合わせ、「トピックの作成」を選択します。
  1. 詳細画面でトピック名・タイプ・ARNを確認します。

ℹ️ 情報：掲載画像の購読状況 トピック作成時の画像ではサブスクリプションが0件です。次の登録・購読確認を実施して通知先を有効にします。

2. Emailサブスクリプションを登録する

  1. 作成したトピックの「サブスクリプション」タブで「サブスクリプションの作成」を選択します。
  2. 次の値を設定します。
項目 設定値・確認内容
トピックARN sample-sns-cloudwatch-alertsのARN
プロトコル Email
エンドポイント 承認済みの運用通知先メールアドレス
サブスクリプションフィルターポリシー 全アラーム通知を受信する場合は指定なし
  1. メールアドレスを再確認し、「サブスクリプションの作成」を選択します。
  2. 一覧で対象の通知先と、購読確認待ち（Pending confirmation）の状態を確認します。

3. 確認メールから購読を承認する

  1. 登録した通知先で、Amazon SNSから届いた購読確認メールを開きます。
  2. メール本文のトピックARNが今回の通知先トピックと一致することを確認します。
  3. 「Confirm subscription」を選択します。
  4. ブラウザーに購読確認完了の画面が表示されることを確認します。
  5. SNSコンソールを更新し、対象のサブスクリプションが「確認済み」（Confirmed）となり、サブスクリプションARNが表示されることを確認します。

⚠️ 注意：購読確認が完了するまでメール通知は配信されない 確認待ちの場合は、宛先・迷惑メール・メール受信制限を確認し、SNSコンソールから確認リクエストを再送信します。配布リストを使用する場合は、管理担当者が確認メールを受信できることも確認します。

ℹ️ 情報：購読確認の画像は未取得 保管済み画像はトピック作成までです。登録画面、確認済みの一覧、テストメール受信画面は本作業で取得します。メールアドレスや購読確認用URLの取り扱いは、お客様の記録ルールに従います。

4. SNSのメール配信をテストする

  1. 通知先へテスト実施を周知します。
  2. SNSの対象トピックで「メッセージの発行」を選択します。
  3. 件名へ「CloudWatch監視通知テスト」、本文へ対象環境とテスト実施日時を入力します。
  4. 「メッセージの発行」を選択します。
  5. 通知先で件名・本文・受信日時を確認します。

SNS単体のテスト後、アラーム経由の通知を「通知試験と運用確認」で確認します。Amazon SNSのメール通知

5. EC2ステータスチェックアラームを作成する

作成前のアラームを確認する

CloudWatchでアラーム－すべてのアラームを開き、同じインスタンス・メトリクスのアラームがないことを確認してから、アラームの作成を選択します。

StatusCheckFailedを選択する

  1. メトリクスの選択を選択します。
  2. AWS/EC2－インスタンス別メトリクスを開きます。
  3. インスタンスIDi-05914a8b6088a3a42、メトリクス名StatusCheckFailedの行を選択します。

ℹ️ 情報：停止中のメトリクス StatusCheckFailedは、インスタンスまたは基盤側のステータスチェックに失敗した場合に1となります。停止済みインスタンスではメトリクスが途切れ、設定によりINSUFFICIENT_DATAとなる場合があります。停止の検知が必要な場合は、EC2の状態変更も監視対象にします。

7. Windows OSメトリクスを収集する

EC2標準メトリクスだけでは、Windowsのメモリコミット率とドライブ別空き容量は取得できません。CloudWatch agentをインストール・設定してCWAgent名前空間へ送信します。

導入前の画像ではCWAgentメトリクスが未出力です。設定後の出力結果は図18で確認します。

IAM権限を確認する

EC2に関連付けたインスタンスプロファイルへ、少なくとも次のAWS管理ポリシーが付与されていることを確認します。

  • Systems Managerで管理する場合：AmazonSSMManagedInstanceCore
  • CloudWatch agentでメトリクス・ログを送信する場合：CloudWatchAgentServerPolicy

本検証では、Sample_EC2RoleにAmazonSSMManagedInstanceCoreは付与済みでしたが、CloudWatchAgentServerPolicyが未付与でした。IAMコンソールでCloudWatchAgentServerPolicyを追加し、許可ポリシー一覧に次の3ポリシーが表示されることを確認しました。

  • AmazonSSMManagedInstanceCore
  • CloudWatchAgentServerPolicy
  • Sample-Policy

IAMロールの許可ポリシー一覧で、CloudWatchAgentServerPolicyが付与されていることを確認します。

⚠️ 注意：CloudWatch agent用IAM権限
AmazonSSMManagedInstanceCoreだけでは、CloudWatch Agentによるメトリクス送信に必要な権限を満たしません。Agentを導入する前に、対象EC2のインスタンスロールへCloudWatchAgentServerPolicyが付与されていることを確認します。

CloudWatch agentを導入する

  1. 既存設定を上書きしないよう、最初にSystems ManagerのAmazonCloudWatch-ManageAgentをAction=statusで実行し、agentの導入・稼働状態を確認します。
  2. 既にagentを利用している場合は、C:\ProgramData\Amazon\AmazonCloudWatchAgent配下の設定と、既存のログ収集設定を確認・退避します。新しい設定は既存設定とマージしてから適用します。
  3. 未導入の場合はAWS Systems ManagerのRun Commandを開き、AWS管理ドキュメントAWS-ConfigureAWSPackageを選択します。
  4. Action=Install、Name=AmazonCloudWatchAgent、Version=latestを設定し、対象EC2へ実行します。
  5. コマンドの全体的なステータスと詳細なステータスがともにSuccess（日本語表示では「成功」）となっていることを確認します。

本検証では、導入前のAction=statusが失敗しました。状態確認コマンドの失敗時は、出力内容・サービスの有無を確認します。その後、AWS-ConfigureAWSPackageを次の値で実行し、インストールが成功しました。

項目 設定値
Action Install

Version latest
対象 Sample-mng-001（i-05914a8b6088a3a42）

Run Commandの実行結果で、全体的なステータスと詳細なステータスがともに「成功」となっていることを確認します。

収集設定を作成する

設定ウィザードまたはJSON設定で、次のWindows Performance Counterを1分間隔で収集します。

オブジェクト カウンター リソース
LogicalDisk % Free Space 監視対象ドライブ。本例はC:
Memory % Committed Bytes In Use なし

}

Parameter Storeへ収集設定を保存する

  1. Systems ManagerのParameter Storeを開き、パラメータの作成を選択します。
  2. 名前をAmazonCloudWatch-sample-windows-basic-v1、階層をStandard、タイプをStringにします。
  3. 値に前項のJSONを貼り付けて保存します。

本検証では、パラメータAmazonCloudWatch-sample-windows-basic-v1をStandard、Stringで新規作成し、作成成功メッセージと一覧表示を確認しました。

保存したパラメータを開き、名前、利用枠、種類および設定値が指定内容と一致していることを確認します。

ℹ️ 情報：Parameter Store名の接頭辞 CloudWatchAgentServerPolicyが取得できる標準的な接頭辞に合わせ、本例ではAmazonCloudWatch-から始まる名前を使用します。既存の同名パラメータがある場合は上書きせず、内容を確認してバージョン名を変更してください。

設定を適用し、メトリクスを確認する

  1. Systems ManagerのRun CommandでAmazonCloudWatch-ManageAgentを選択します。
  2. Action=configure、Mode=ec2、Optional Configuration Source=ssm、Optional Configuration Location=AmazonCloudWatch-sample-windows-basic-v1、Optional Restart=yesを指定し、対象EC2へ実行します。
  3. Run CommandがSuccessとなり、AmazonCloudWatch-ManageAgentのAction=statusでAgentがrunningかつconfigstatusがconfiguredとなることを確認します。
  4. 本設定は1分間隔のため、起動後1～5分を目安にCloudWatchのすべてのメトリクスでCWAgent名前空間を開きます。
  5. 対象インスタンスのLogicalDisk % Free Space（instance=C:）とMemory % Committed Bytes In Useが1分間隔で出力されることを確認します。グラフ化したメトリクスの期間も1分に変更します。
  6. Windows上のパフォーマンスモニターの値と大きく乖離していないことを確認します。

設定適用コマンドが成功し、コマンドパラメータが指定内容と一致していることを確認します。

状態確認コマンドの出力で、statusがrunning、configstatusがconfiguredとなっていることを確認します。

CloudWatchで対象メトリクスをグラフ化し、ディスク空き容量とメモリ使用率のデータが1分間隔で表示されることを確認します。

9. ダッシュボードへEC2・Windows OSメトリクスを追加する

  1. CloudWatchの「ダッシュボード」でsample-cw-monitoring-dashboardを開きます。未作成の場合は「ダッシュボードの作成」から作成します。
  2. 「ウィジェットの追加」で折れ線グラフを選択し、対象EC2のCPUUtilizationとStatusCheckFailedを追加します。
  3. CWAgentから対象EC2のディスク空き容量（instance=C:）とメモリコミット率を追加します。
  4. CPUはAverage、ステータスチェックはMaximum、Windows OSはAverageとし、対象ID・単位・期間が分かるタイトルを設定します。
  5. 「アラームステータス」のウィジェットへ今回作成したEC2・Windows OSアラームを追加します。
  6. 保存し、グラフの最新時刻と表示値を確認します。

ℹ️ 情報：検証画像の確認範囲 CloudWatch agentの稼働とWindows OSメトリクスの出力は掲載画像で確認できます。Windows OSのアラーム作成、ダッシュボードへの追加、SNSメール受信の画像は未取得です。

通知試験と運用確認

1. テスト用アラームで通知経路を確認する

  1. 通知担当者と試験時間・通知先・テスト名を共有します。
  2. 継続してデータが取得できる検証用EC2のメトリクスを選び、専用のテスト用アラームを作成します。
  3. 現在値でALARMとなるしきい値を設定し、SNS通知先を指定します。EC2停止・再起動などのアクションは設定しません。
  4. 必要な評価期間を待ち、「履歴」でALARMへの状態変更とSNS通知アクションの結果を確認します。
  5. 通知先でアラーム名・対象・状態変更時刻が一致するメールを確認します。
  6. テスト用アラームを削除し、運用アラームのしきい値・アクションを変更していないことを確認します。

⚠️ 注意：状態を強制変更する試験の確認範囲 cloudwatch set-alarm-stateを使用する場合は、通知専用のテストアラームを対象とします。この方法では通知アクションを確認でき、実際のメトリクスによるしきい値判定は別途確認します。

2. 通知されない場合を切り分ける

確認箇所 確認内容
アラーム メトリクスの最新時刻、統計、期間、しきい値、状態変更履歴、アクション有効化
SNS 指定したトピックARN、確認済みのEmail購読、フィルターポリシー
メール 宛先、迷惑メール、配布リストの受信制限
権限 SNSトピックのCloudWatchからのPublish許可。暗号化使用時はKMSキーポリシーも確認

❌ エラー：通知アクションが失敗した場合 アラーム履歴のエラー内容を確認し、SNSトピック・暗号化キーの許可設定を見直します。設定修正後は、テスト用アラームで通知を再確認します。

3. 定期点検と変更時の対応

  • 月次：アラームのアクション、長期のデータ欠落、SNS購読状態と受信担当者を確認します。
  • 四半期：通常値とピーク値、しきい値、不要なアラーム・ウィジェットを見直します。
  • 構成変更時：新しいリソースを監視対象へ追加し、通知試験を行います。
  • 設定を戻す場合：作業前に退避したagent設定を復元し、既存のログ収集とメトリクス送信を確認します。共有IAMロールのポリシーは利用先への影響を確認してから変更します。
