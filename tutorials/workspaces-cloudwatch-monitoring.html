CloudWatch・SNS 監視／通知

Amazon EC2、Windows OSおよびAmazon WorkSpacesのメトリクスをCloudWatchへ集約する
SNS通知、アラーム、ダッシュボードおよび監視動作の確認手順を整理する

01. Amazon SNS通知と監視構成

1. 監視構成

Amazon EC2とAmazon WorkSpacesの標準メトリクス、およびCloudWatch agentが収集するWindows OSメトリクスをCloudWatchへ集約します。CloudWatchアラームがしきい値違反を検出した場合はAmazon SNSへ通知し、メトリクスとアラーム状態はダッシュボードで確認する

対象 監視・表示するメトリクス 用途
Amazon EC2 StatusCheckFailed、CPUUtilization ステータスチェック失敗とCPU高負荷の検知
Windows OS LogicalDisk % Free Space、Memory % Committed Bytes In Use ディスク空き容量とメモリ使用率の監視。CloudWatch agentが必要
Amazon WorkSpaces Unhealthy、ConnectionFailure、UserConnected 異常状態・接続失敗の検知と接続状況の可視化
Amazon WorkSpaces（追加推奨） CPUUsage、MemoryUsage、RootVolumeDiskUsage、UserVolumeDiskUsage リソース不足とボリューム容量逼迫の検知
Amazon WorkSpaces（接続品質） SessionLaunchTime、InSessionLatency、UDPPacketLossRate、TCPRetransmissionRate 通常値をダッシュボードで確認した後にアラーム化を検討
Amazon SNS sample-sns-cloudwatch-alerts アラーム状態変更の通知先
CloudWatchダッシュボード 上記メトリクスと作成済みアラーム 状態と傾向の一元確認

CloudWatchアラームのOKは、設定した評価期間内でしきい値違反が成立していないことを示します。OS、アプリケーション、認証などを含むサービス全体の正常性を保証するものではない

2. 目的

CloudWatchアラームがALARM状態へ変わった際に、運用担当者へ通知するためのSNSトピックとサブスクリプションを設定する

3. 前提・入力値

項目 入力値
リージョン アジアパシフィック（東京）ap-northeast-1
トピックタイプ スタンダード
トピック名 sample-sns-cloudwatch-alerts
表示名 任意。SMS利用時のみ意味を持つため、メール通知のみの場合は空欄可
サブスクリプションプロトコル Email（運用方針に応じてHTTPS等も可）
エンドポイント お客様指定の運用通知先

4. SNSトピックを作成する

手順1：SNSを開く

  1. AWSマネジメントコンソールでリージョンが「アジアパシフィック（東京）」であることを確認
  2. Amazon SNSを開き、左メニューからトピックを選択
  3. 作成前のトピック一覧を確認
項目 内容
目的 既存トピックとの重複を避ける
期待結果 同名のトピックが存在しない
証跡 トピック一覧画面
注意 同名または同一用途のトピックがある場合は新規作成せず、所有者と利用範囲を確認する

手順2：トピック作成画面へ進む

トピックの作成を選択する

手順3：トピック名とタイプを設定する

  1. タイプでスタンダードを選択
  2. 名前にsample-sns-cloudwatch-alertsを入力
  3. 暗号化、アクセスポリシー、配信ステータスのログ記録は、組織のセキュリティ基準で指定がなければ初期値のままと
  4. トピックの作成を選択
項目 内容
期待結果 トピックが作成され、トピックARNが表示される
証跡 トピック詳細の名前、タイプ、ARN
注意 FIFOトピックは本手順では使用しない

手順4：作成結果を確認する

トピック詳細画面で、名前がsample-sns-cloudwatch-alerts、タイプがスタンダードであることを確認する

5. サブスクリプションを作成する

検証環境では未設定
実際の通知先が未確定のため、トピックのみ作成済みです。通知先はお客様の運用窓口を確認してから設定してください

  1. 作成したトピックの詳細でサブスクリプションの作成を選択
  2. プロトコルでEmailを選択
  3. エンドポイントに運用通知先メールアドレスを入力
  4. サブスクリプションの作成を選択
  5. 宛先に届いたAWS Notificationメールを開き、Confirm subscriptionを選択
  6. SNSコンソールでステータスがConfirmedになったことを確認
項目 内容
目的 アラーム通知の配信先を有効化する
入力値 お客様指定の通知先メールアドレス
期待結果 サブスクリプションのステータスがConfirmed
証跡 SNSのサブスクリプション一覧と、件名・宛先・受信日時が分かるテスト通知
注意 Pending confirmationのままでは通知されない。迷惑メールフォルダーも確認する
ロールバック 誤ったサブスクリプションのみを選択して削除する
未検証 検証環境では通知先未確定のため、購読確認およびメール受信は未実施

6. セキュリティ・運用上の注意

  • 個人メールアドレスではなく、監視担当者が共同利用する配布リストを推奨する
  • 本番、検証、開発で通知先を分ける場合は、環境別のトピック名を定義する
  • CloudWatchアラーム作成時に、ALARMへの遷移通知を本トピックへ関連付けます。必要に応じてOK復旧通知も追加する
  • トピックを削除すると、参照中のアラームから通知できなくなります。削除前にCloudWatchアラームのアクションを確認する

02. EC2・Windows OS監視

1. 目的

EC2の標準メトリクスでインスタンスの死活とCPU負荷を監視し、CloudWatch agentでWindows OSの論理ディスク空き容量とメモリ使用率を監視する

2. 前提・入力値

項目 値
検証用EC2 i-05914a8b6088a3a42
EC2名 Sample-mng-001
EC2インスタンスロール Sample_EC2Role
SNSトピック sample-sns-cloudwatch-alerts
リージョン アジアパシフィック（東京）ap-northeast-1
インスタンス用IAMポリシー AmazonSSMManagedInstanceCore、CloudWatchAgentServerPolicy（Windows OSメトリクス収集時）
ネットワーク 対象EC2からTCP/443でSystems Manager、Parameter Store、CloudWatchの各サービスエンドポイントへ到達できること。インターネットへ直接公開する必要はなく、NAT／プロキシまたは対応VPCエンドポイントを使用可能

権限の考え方
EC2上でCloudWatch agentからメトリクス・ログを送信する実行ロールにはCloudWatchAgentServerPolicyを使用します。CloudWatchAgentAdminPolicyは、設定ウィザード等からSystems Manager Parameter StoreへCloudWatch agent設定を書き込む管理用途で必要になる権限を含むため、通常の送信用EC2実行ロールには付与しません。設定作成者と送信元EC2の役割を分け、最小権限を優先する

3. EC2ステータスチェックアラームを作成する

手順1：作成前のアラームを確認する

CloudWatchでアラーム－すべてのアラームを開き、同じインスタンス・メトリクスのアラームがないことを確認してから、アラームの作成を選択する

手順2：StatusCheckFailedを選択する

  1. メトリクスの選択を選択
  2. AWS/EC2－インスタンス別メトリクスを開く
  3. インスタンスIDi-05914a8b6088a3a42、メトリクス名StatusCheckFailedの行を選択

手順3：条件を設定する

設定項目 設定値
統計 最大値（Maximum）
期間 5分
しきい値の種類 静的
条件 1以上
アラームを実行するデータポイント 2/2
欠落データの処理 欠落（missing）
ℹ️ 確認事項

StatusCheckFailedは、インスタンスまたは基盤側のステータスチェックに失敗した場合に1となります。停止済みインスタンスではメトリクスが途切れ、設定によりINSUFFICIENT_DATAとなる場合があります。「停止＝ステータスチェック失敗」ではない

手順4：SNS通知を設定する

  1. アラーム状態トリガーでアラーム状態を選択
  2. 既存のSNSトピックを選択を選択
  3. sample-sns-cloudwatch-alertsを選択

手順5：名前と説明を設定する

項目 値
アラーム名 sample-cw-critical-ec2-statuscheckfailed-i-05914a8b6088a3a42

注意 作成直後は評価データがそろうまでINSUFFICIENT_DATAになる場合がある
ロールバック 対象アラームのみを削除する。EC2やSNSトピックは削除しない

5. Windows OSメトリクスを出力する

EC2標準メトリクスだけでは、Windowsのメモリ使用率とドライブ別空き容量は取得できません。CloudWatch agentをインストール・設定してCWAgent名前空間へ送信する

手順1：IAM権限を確認する

EC2に関連付けたインスタンスプロファイルへ、少なくとも次のAWS管理ポリシーが付与されていることを確認する

  • Systems Managerで管理する場合：AmazonSSMManagedInstanceCore
  • CloudWatch agentでメトリクス・ログを送信する場合：CloudWatchAgentServerPolicy

本検証では、Sample_EC2RoleにAmazonSSMManagedInstanceCoreは付与済みでしたが、CloudWatchAgentServerPolicyが未付与でした。IAMコンソールでCloudWatchAgentServerPolicyを追加し、許可ポリシー一覧に次の3ポリシーが表示されることを確認した

  • AmazonSSMManagedInstanceCore
  • CloudWatchAgentServerPolicy
  • Sample-Policy

IAMロールの許可ポリシー一覧で、CloudWatchAgentServerPolicyが付与されていることを確認する

注意：CloudWatch Agent用IAM権限
AmazonSSMManagedInstanceCoreだけでは、CloudWatch Agentによるメトリクス送信に必要な権限を満たしません。Agentを導入する前に、対象EC2のインスタンスロールへCloudWatchAgentServerPolicyが付与されていることを確認する

手順2：CloudWatch agentを導入する

  1. 既存設定を上書きしないよう、最初にSystems ManagerのAmazonCloudWatch-ManageAgentをAction=statusで実行し、agentの導入・稼働状態を確認
  2. 既にagentを利用している場合は、C:\ProgramData\Amazon\AmazonCloudWatchAgent配下の設定と、既存のログ収集設定を確認・退避します。新しい設定は既存設定とマージしてから適用
  3. 未導入の場合はAWS Systems ManagerのRun Commandを開き、AWS管理ドキュメントAWS-ConfigureAWSPackageを選択
  4. Action=Install、Name=AmazonCloudWatchAgent、Version=latestを設定し、対象EC2へ実行
  5. コマンドの全体的なステータスと詳細なステータスがともにSuccess（日本語表示では「成功」）であることを確認

本検証では、導入前のAction=statusはWindows側で失敗し、Agentが稼働していないことを確認しました。その後、AWS-ConfigureAWSPackageを次の値で実行し、インストールが成功した

項目 設定値
Action Install
Installation Type Uninstall and reinstall
Name AmazonCloudWatchAgent
Version latest
対象 Sample-mng-001（i-05914a8b6088a3a42）
S3出力 無効

Run Commandの実行結果で、全体的なステータスと詳細なステータスがともに「成功」であることを確認する

手順3：収集設定を作成する

設定ウィザードまたはJSON設定で、次のWindows Performance Counterを1分間隔で収集する

オブジェクト カウンター リソース
LogicalDisk % Free Space 監視対象ドライブ。本例はC:
Memory % Committed Bytes In Use なし

設定例は次のとおりです。環境で必要なドライブだけを対象にし、一時領域やリカバリ領域を除外してください

json
{
  "metrics": {
    "namespace": "CWAgent",
    "append_dimensions": {
      "InstanceId": "${aws:InstanceId}"
    },
    "metrics_collected": {
      "LogicalDisk": {
        "measurement": [
          {
            "name": "% Free Space",
            "rename": "LogicalDisk % Free Space",
            "unit": "Percent"
          }
        ],
        "metrics_collection_interval": 60,
        "resources": ["C:"]
      },
      "Memory": {
        "measurement": [
          {
            "name": "% Committed Bytes In Use",
            "rename": "Memory % Committed Bytes In Use",
            "unit": "Percent"
          }
        ],
        "metrics_collection_interval": 60
      }
    }
  }
}

手順4：Parameter Storeへ収集設定を保存する

  1. Systems ManagerのParameter Storeを開き、パラメータの作成を選択
  2. 名前をAmazonCloudWatch-sample-windows-basic-v1、階層をStandard、タイプをStringに
  3. 値に前項のJSONを貼り付けて保存

本検証では、パラメータAmazonCloudWatch-sample-windows-basic-v1をStandard、Stringで新規作成し、作成成功メッセージと一覧表示を確認した

保存したパラメータを開き、名前、利用枠、種類および設定値が指定内容と一致していることを確認する

ℹ️ 確認事項

CloudWatchAgentServerPolicyが取得できる標準的な接頭辞に合わせ、本例ではAmazonCloudWatch-から始まる名前を使用します。既存の同名パラメータがある場合は上書きせず、内容を確認してバージョン名を変更してください

手順5：設定を適用し、メトリクスを確認する

  1. Systems ManagerのRun CommandでAmazonCloudWatch-ManageAgentを選択
  2. Action=configure、Mode=ec2、Optional Configuration Source=ssm、Optional Configuration Location=AmazonCloudWatch-sample-windows-basic-v1、Optional Restart=yesを指定し、対象EC2へ実行
  3. Run CommandがSuccessとなり、AmazonCloudWatch-ManageAgentのAction=statusでAgentがrunningかつconfigstatusがconfiguredとなることを確認
  4. 本設定は1分間隔のため、起動後1～5分を目安にCloudWatchのすべてのメトリクスでCWAgent名前空間を開く
  5. 対象インスタンスのLogicalDisk % Free Space（instance=C:）とMemory % Committed Bytes In Useが1分間隔で出力されることを確認する。グラフ化したメトリクスの期間も1分に変更
  6. Windows上のパフォーマンスモニターの値と大きく乖離していないことを確認

設定適用コマンドが成功し、コマンドパラメータが指定内容と一致していることを確認する

状態確認コマンドの出力で、statusがrunning、configstatusがconfiguredであることを確認する

CloudWatchで対象メトリクスをグラフ化し、ディスク空き容量とメモリ使用率のデータが1分間隔で表示されることを確認する

03. Amazon WorkSpaces監視

1. 目的

Amazon WorkSpacesの異常状態と接続失敗をアラームで検知し、利用状況をダッシュボードで確認する

2. 前提・入力値

項目 値
検証用WorkSpace ID ws-jkxz7js0s
SNSトピック sample-sns-cloudwatch-alerts
リージョン アジアパシフィック（東京）ap-northeast-1

3. Unhealthyアラームを作成する

手順

  1. CloudWatchでアラーム－すべてのアラーム－アラームの作成を選択
  2. メトリクスの選択からAWS/WorkSpacesを開く
  3. WorkspaceId=ws-jkxz7js0s、メトリクスUnhealthyを選択
  4. 次の条件を設定
設定項目 設定値
統計 最大値（Maximum）
期間 5分
条件 1以上
アラームを実行するデータポイント 3/3
欠落データの処理 正常（notBreaching）
SNSトピック sample-sns-cloudwatch-alerts
アラーム名 sample-cw-critical-workspaces-unhealthy-ws-jkxz7js0s

Unhealthy=1が3期間連続で発生した場合に通知します。瞬間的な状態遷移による誤報を抑えつつ、継続する異常を検知する初期設計

4. ConnectionFailureアラームを作成する

手順

  1. AWS/WorkSpacesから対象WorkSpaceのConnectionFailureを選択
  2. 次の条件を設定
設定項目 設定値
統計 合計（Sum）
期間 15分
条件 3以上
アラームを実行するデータポイント 1/1
欠落データの処理 正常（notBreaching）
SNSトピック sample-sns-cloudwatch-alerts
アラーム名 sample-cw-warning-workspaces-connectionfailure-ws-jkxz7js0s
  1. 説明欄には、監視範囲を明確にするため「クライアント認証後、WorkSpacesセッションの接続開始時に発生した失敗を監視する。事前認証段階のAD認証失敗は含まれない」旨を記載
  2. 設定内容を確認してアラームを作成

誤解しやすい点
ConnectionFailureは、WorkSpacesクライアントの認証が成功した後、WorkSpaceセッションへの接続が開始されてからの失敗を示します。パスワード誤り、アカウントロック、認証前のActive Directoryエラーをすべて検知するメトリクスではありません。認証関連はDirectory Serviceログ、Windowsイベントログ、認証基盤側の監視と組み合わせる

5. UserConnectedをダッシュボードへ追加する

UserConnectedは利用状況の可視化に使用し、本手順では固定しきい値アラームを作成しない

  1. CloudWatchでダッシュボードを開き、対象ダッシュボードを選択
  2. 折れ線または数値ウィジェットを追加
  3. AWS/WorkSpaces－UserConnectedを選択
  4. WorkSpace単位では接続時の値が1、未接続時が0となるため、単体の接続有無はMaximumで表示します。複数台の同時接続数を表示する場合は、各WorkSpaceの0/1系列を同じ期間・時点でメトリクス数式により合算します。期間内のSumだけを人数として扱うと、同じWorkSpaceの複数データポイントを重複計上するため使用しない
  5. 業務時間帯を含む期間でグラフを確認
ℹ️ 確認事項

UserConnected=0は、必ずしも異常とは限らない。利用者が接続していない時間帯やAutoStop状態では正常な状態。固定アラームではなく、利用実態、ライセンス・キャパシティ検討、問い合わせ時の確認に用いる

6. 追加を推奨する監視メトリクス

現在の画像で作成を確認できるアラームはUnhealthyとConnectionFailureの2つです。次のメトリクスは、WorkSpaceのリソース不足や利用者の操作感を早期に検知するための追加候補です。現時点では作成画像がないため、設定済みの監視としては扱わない

優先して追加するアラーム

メトリクス 検知する内容 初期設定例 補足
CPUUsage CPU使用率の継続的な高騰 Average、5分、80%以上、3/3 バンドルのコンピューティングタイプ見直しに使用する
MemoryUsage メモリ使用率の継続的な高騰 Average、5分、80%以上、3/3 ページング増加やアプリケーション遅延と併せて確認する
RootVolumeDiskUsage ルートボリュームの容量逼迫 Average、5分、80%以上、3/3 90%以上を重大アラームとする二段階監視も検討する
UserVolumeDiskUsage ユーザーボリュームの容量逼迫 Average、5分、80%以上、3/3 利用者データの増加傾向と併せて確認する

上記の80%はAWSがすべての環境へ指定する固定値ではなく、導入時の初期値です。業務アプリケーションの通常値とピーク値を確認し、お客様の運用基準に合わせて調整する

ダッシュボードで傾向を確認してからアラーム化するメトリクス

メトリクス 用途 設定時の考え方
SessionLaunchTime セッション開始に要した時間 AverageとMaximumを表示し、通常値と利用者が許容できる時間を確認してからしきい値を決める
InSessionLatency クライアントとWorkSpace間の往復遅延 AverageとMaximumを表示し、拠点・回線別の通常値を取得してからアラーム化する
UDPPacketLossRate ストリーミング通信のUDPパケット損失率 DCVではゲートウェイからクライアント方向の損失を示す。遅延や画面品質低下時の切り分けに使用する
TCPRetransmissionRate TCP再送率 DCVで使用可能。InSessionLatencyやBandwidthと同じ時間帯で確認する
SessionDisconnect セッション切断回数 正常な切断を含む可能性があるため、単発通知ではなく増加傾向の確認に使用する
ConnectionAttempt、ConnectionSuccess、ConnectionFailure 接続試行と成否 同じ期間・ディメンションで並べ、失敗数だけでなく成功率の低下を確認する
Available、Stopped、Maintenance WorkSpaces全体の状態把握 DirectoryIdディメンションで台数を集約し、運用ダッシュボードへ表示する

Bandwidth、BandwidthInbound、ConnectionDuration、FramesPerSecondもDCVで使用できます。これらは通常値の個体差が大きいため、固定しきい値を先に決めず、接続品質の問い合わせ時に同時刻の推移を確認できるようダッシュボードへ追加します。GPUバンドルを使用する場合だけGPUUsageも追加する

信頼されたデバイス機能を有効にする場合だけ、TrustedDeviceValidationFailureとTrustedDeviceCertificateDaysBeforeExpirationも監視対象へ追加する

ディメンションを選択する

  • 個別障害を検知するアラームではWorkspaceIdを使用する
  • 全体傾向を把握するダッシュボードではDirectoryIdを使用する
  • RunningMode、Protocol、ComputeType、BundleIdを使用すると、AutoStop／AlwaysOn、DCV、バンドル種別ごとの比較ができる
  • 接続関連メトリクスは、WorkSpacesクライアントでの認証成功後にセッション接続を開始した時点から記録されます。認証前のADエラーは別途監視する

7. 成功可否と切り分け

  1. アラーム一覧で作成した2アラームの状態がOKで、アクションが有効であることを確認
  2. UnhealthyがALARMの場合、WorkSpacesコンソールで対象IDの状態、ヘルスチェック、再起動・再構築履歴を確認
  3. ConnectionFailureがALARMの場合、同時刻のクライアントエラー、ネットワーク経路、Directory Service、セキュリティグループ、証明書・プロキシ設定を確認
  4. ConnectionFailureがOKでも、認証前の失敗は別途確認

1. 目的

作成したアラームを一覧で確認し、監視値をCloudWatchダッシュボードへ集約します。また、SNS通知、アラーム判定、対象サービスの確認を分けて実施する

2. 作成済みアラームを確認する

CloudWatchでアラーム－すべてのアラームを開き、検索欄へsample-cw-を入力する

検証環境では次の4アラームを作成し、いずれもOK、アクション有効であることを確認済み

アラーム名 対象 検証結果
sample-cw-critical-ec2-statuscheckfailed-i-05914a8b6088a3a42 EC2死活 OK
sample-cw-warning-ec2-cpu-high-i-05914a8b6088a3a42 EC2 CPU OK
sample-cw-critical-workspaces-unhealthy-ws-jkxz7js0s WorkSpaces状態 OK

  1. アラーム名が命名規則に一致
  2. 対象リソースID、メトリクス、統計、期間、しきい値が設計値と一致

4. SNS通知をテストする

4.1 SNS単体の配信確認

  1. SNSサブスクリプションがConfirmedであることを確認
  2. 変更作業時間帯に、トピックsample-sns-cloudwatch-alertsから「CloudWatch監視通知テスト」と分かるテストメッセージを発行
  3. 宛先で件名、本文、受信時刻を確認

この確認は「SNSトピックから通知先まで」の配信経路を確認するもので、メトリクスやアラームの判定は確認しない

4.2 アラームを含む確認

本番リソースに負荷や障害を意図的に発生させないでください。検証環境で次のいずれかを実施する

  • 一時的なテスト用アラームを作り、現在値に対して安全にALARMとなるしきい値を設定する
  • AWS CLIのcloudwatch set-alarm-stateを利用できる運用環境では、承認済みのテスト手順に従って一時的に状態を変更する

確認後はテスト用アラームを削除し、本番アラームのしきい値を変更していないことを確認する

5. 成功可否の判定方法

5.1 CloudWatch上の確認

状態 意味 対応
OK 評価期間内でしきい値違反が成立していない 対象メトリクスの最終時刻も確認する
ALARM しきい値違反が成立した 履歴、メトリクス、対象サービスを確認する
INSUFFICIENT_DATA 判定に必要なデータが不足 停止、削除、agent停止、リージョン、メンテナンスを確認する
  1. アラーム詳細のグラフで、状態変更前後の値を確認
  2. 履歴で、状態変更時刻、理由、通知アクションの成否を確認
  3. SNS通知の受信時刻とアラーム履歴を照合
  4. 対象サービスのコンソール、OSログ、ジョブ履歴で原因と影響を確認

5.2 「成功」「OK」「正常」を混同しない

  • アラーム作成画面の成功：設定APIが受理されたこと
  • アラーム状態OK：設定したメトリクスが、その期間でしきい値に違反していないこと
  • SNS配信成功：SNSから購読先への配信が成功したこと
  • サービス正常：業務上必要な機能、OS、アプリケーションおよび認証に問題がないこと

したがって、OK表示だけで作業完了とせず、「対象メトリクスの最新時刻」「アラーム履歴」「SNS受信」「対象サービス側の状態」を証跡として残す
