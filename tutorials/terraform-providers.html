TerraformのProviderとマルチクラウド

Providerとモジュールの違いProviderの選定と初期化AWSの複数リージョン・アカウントAzureでの最小ネットワーク構築Google Cloudでの最小ネットワーク構築HCP Terraformの動的AWS認証

Providerの選定、AWSの複数リージョン、Azure・Google Cloudの最小構成と、HCP Terraformの動的認証を整理

Providerとモジュールの違い

要素役割例
Terraform CLI構成・State・依存関係を評価して実行init／plan／apply
ProviderサービスのAPIとリソース型を提供hashicorp/aws、hashicorp/azurerm
モジュール複数の構成を再利用可能な部品にまとめるVPC構成、SQS構成
tenvTerraformなどの実行バイナリのバージョンを管理tenv tf use

Terraformで共通になるのは操作の流れ。AWSのresourceをそのままAzureへ転用することはできず、認証・権限・ネットワーク・リソース型は各サービスに合わせて定義

Providerの選定と初期化

Registryで対象サービスを検索し、配布元・選択バージョンのDocumentation・対応リソース・Import形式・更新履歴を確認。Official／Partner／Communityは管理主体の区分であり、自分の用途での動作保証を表すものではない

用途Providerの例確認する内容
AWShashicorp/aws、hashicorp/awscc対応リソース型、サービス仕様、必要IAM権限
Azure／Google Cloudhashicorp/azurerm、hashicorp/google対象Subscription／Project、APIの有効化、認証
ローカルコンテナkreuzwerker/docker実行環境からDocker Engineへ接続できるか
HCP Terraformの設定hashicorp/tfeWorkspace・チーム・変数等を管理するAPI権限
HashiCorp Cloud Platformhashicorp/hcpHCPリソースの管理。TFE Providerとは対象が異なる
秘密情報の管理hashicorp/vault取得した値がStateへ保存されるか
仮想化基盤vSphere、Nutanix向けProvider管理APIへの接続経路、対象製品の互換性
CDN・監視・構成管理Fastly、Datadog、Splunk、Ansible向けProvider対象リソース、APIトークン、Providerの配布元

① 現在の構成に必要なProviderを確認

PowerShell
terraform providers

② 通常の初期化で、制約に適合するロック済みバージョンを使用

PowerShell
terraform init

③ 依存関係を更新すると決めた場合のみ実行し、ロックファイルの差分とPlanを確認

PowerShell
terraform init -upgrade
terraform validate
terraform plan

バージョンは「常に最新」ではなく、対象構成で確認した系列・版を指定。Providerのversion条件と.terraform.lock.hclを合わせて管理

AWSの複数リージョン・アカウント

以下はAWS Providerの接続設定とリソースへの割り当て例。既存のproviderブロックへ重複追記せず、別の検証用ルートで使用

HCL：リージョン別のProvider
provider "aws" {
  region = "ap-northeast-1"
}

provider "aws" {
  alias  = "osaka"
  region = "ap-northeast-3"
}

resource "aws_sqs_queue" "tokyo" {
  name = "tf-region-lab-tokyo"
}

resource "aws_sqs_queue" "osaka" {
  provider = aws.osaka
  name     = "tf-region-lab-osaka"
}

provider指定のないresourceは既定設定、provider = aws.osakaはalias設定を使用。リージョンを変えてもStateは自動分割されない

HCL：子モジュールへ接続設定を渡す例
module "osaka_queue" {
  source = "./modules/queue"
  providers = {
    aws = aws.osaka
  }
  name = "tf-module-osaka"
}

子の既定awsへ親のaws.osakaを割り当てる例。子が複数のaliasを直接参照する設計では、子側にもconfiguration_aliasesの宣言が必要

別アカウントはローカル実行のprofileまたはassume_roleで分離。対象ロールの信頼ポリシーと呼び出し元権限を確認し、アカウントごとにCaller Identityを確認。リソースが残っているProvider設定を先に削除しない

Azureでの最小ネットワーク構築

Azure CLI導入済み、検証用Subscriptionへの権限と必要なResource Provider登録を前提。AWSとは別の空フォルダーに配置。VM・DBは作成せず、リソースグループとVNetだけを対象

① 新しい作業フォルダーを作成して移動。既に存在する場合は別名を使用

PowerShell
New-Item -ItemType Directory -Path "$env:USERPROFILE\IaC\Terraform\azure-network-lab"
Set-Location "$env:USERPROFILE\IaC\Terraform\azure-network-lab"

② Azureへログインし、を実際の検証用IDへ置換して選択

PowerShell
az login
az account set --subscription "<SUBSCRIPTION_ID>"
az account show --query "{name:name,id:id,tenantId:tenantId}"

③ main.tfを保存。ProviderはAzure CLIのログインを利用するローカル実行用

main.tf
terraform {
  required_version = ">= 1.10, < 2.0"
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 4.0"
    }
  }
}

variable "subscription_id" {
  type = string
}

provider "azurerm" {
  features {}
  subscription_id = var.subscription_id
}

resource "azurerm_resource_group" "lab" {
  name     = "rg-tf-network-lab"
  location = "Japan East"
}

resource "azurerm_virtual_network" "lab" {
  name                = "vnet-tf-network-lab"
  location            = azurerm_resource_group.lab.location
  resource_group_name = azurerm_resource_group.lab.name
  address_space       = ["10.64.0.0/16"]
}

output "network_id" {
  value = azurerm_virtual_network.lab.id
}

④ 選択中のSubscription IDを入力変数へ設定して初期化

PowerShell
$env:TF_VAR_subscription_id = az account show --query id --output tsv
terraform init
terraform validate

⑤ 計画を保存し、対象が検証用のリソースグループとVNetの2件であることを確認

PowerShell
terraform plan -out=azure.tfplan

⑥ 確認済みの計画を適用。再確認なしで実行

PowerShell
terraform apply azure.tfplan

⑦ 作成されたネットワークIDと、差分がないことを確認

PowerShell
terraform output network_id
terraform plan

不要になったら同じフォルダーから削除計画と適用を実施。リソースグループへ手作業で追加したリソースがないことも確認

Google Cloudでの最小ネットワーク構築

Google Cloud CLI導入済み、課金設定済みの検証用Projectとネットワーク操作権限を前提。Compute Engine APIを有効化して使用。VM・Cloud SQLは作成せず、カスタムVPCとサブネットだけを対象

① Azure・AWSとは別の空フォルダーを作成して移動

PowerShell
New-Item -ItemType Directory -Path "$env:USERPROFILE\IaC\Terraform\google-network-lab"
Set-Location "$env:USERPROFILE\IaC\Terraform\google-network-lab"

② を検証用Projectへ置換し、CLIログインと設定を確認

PowerShell
gcloud auth login
gcloud config set project "<PROJECT_ID>"
gcloud config get-value project
gcloud auth list

③ Terraformが使用するApplication Default Credentials（ADC）でログイン。CLIログインとは別の認証保存先

PowerShell
gcloud auth application-default login

④ 検証用ProjectでCompute Engine APIを有効化。API有効化権限がない場合は管理者へ依頼

PowerShell
gcloud services enable compute.googleapis.com --project="<PROJECT_ID>"

⑤ main.tfを保存

main.tf
terraform {
  required_version = ">= 1.10, < 2.0"
  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 6.0"
    }
  }
}

variable "project_id" {
  type = string
}

provider "google" {
  project = var.project_id
  region  = "asia-northeast1"
}

resource "google_compute_network" "lab" {
  name                    = "tf-network-lab"
  auto_create_subnetworks = false
}

resource "google_compute_subnetwork" "lab" {
  name          = "tf-subnet-lab"
  ip_cidr_range = "10.72.1.0/24"
  region        = "asia-northeast1"
  network       = google_compute_network.lab.id
}

output "network_id" {
  value = google_compute_network.lab.id
}

⑥ Project IDを入力変数へ設定して初期化

PowerShell
$env:TF_VAR_project_id = "<PROJECT_ID>"
terraform init
terraform validate

⑦ 計画を保存し、検証用ネットワークとサブネットの2件だけが追加されることを確認

PowerShell
terraform plan -out=google.tfplan

⑧ 確認済みの計画を適用。再確認なしで実行

PowerShell
terraform apply google.tfplan

⑨ 出力と差分を確認

PowerShell
terraform output network_id
terraform plan

不要になったら同じフォルダーから削除計画をレビューして適用。Projectの削除や共有APIの無効化は、このネットワークの削除と一緒に実施しない

HCP Terraformの動的AWS認証

ローカルPCのSSO設定はHCP TerraformのRemote実行環境へ自動転送されない。Remote実行では、OIDCでRunごとにAWSの一時認証情報を取得する構成を使用可能

① AWS IAMでIDプロバイダーの追加画面を開き、タイプをOpenID Connect、URLをhttps://app.terraform.io、対象者をaws.workload.identityとして登録。既にある場合は既存設定を確認

② 専用IAMロールを作成し、信頼条件をOrganization・Project・Workspaceに限定。次は信頼ポリシーの例。山括弧の値を置換し、業務用Workspace全体へのワイルドカードは使用しない

IAMロールの信頼ポリシー
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::<ACCOUNT_ID>:oidc-provider/app.terraform.io"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "app.terraform.io:aud": "aws.workload.identity"
      },
      "StringLike": {
        "app.terraform.io:sub": "organization:<ORGANIZATION>:project:<PROJECT>:workspace:<WORKSPACE>:run_phase:*"
      }
    }
  }]
}

③ 信頼ポリシーとは別に、管理するサービスとState参照に必要な許可ポリシーを付与。全管理者権限を前提にしない

④ 対象WorkspaceのVariablesで環境変数として次を登録。Terraform変数としては登録しない

KeyValue
TFC_AWS_PROVIDER_AUTHtrue
TFC_AWS_RUN_ROLE_ARNarn:aws:iam::<ACCOUNT_ID>:role/<ROLE_NAME>
AWS_REGIONap-northeast-1

⑤ 検証用Workspaceから先に移行。競合する固定AWSキー・AWS_PROFILE・コード内の認証指定を除き、AWSのdata sourceや管理リソースを含むPlanで接続を確認。固定キーの削除は保管先・他の利用者を確認し、移行成功後に不要なキーを失効

⑥ Runの成否とAWS側で使用したロールを確認。必要に応じてPlan用とApply用にロールを分け、各フェーズの権限を制限

⚠️ 注意

Plan成功だけでApplyの書き込み権限まで確認できたとは限らない。VCS連携やRemote実行の基本手順はHCP Terraformを参照
