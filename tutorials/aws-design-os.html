採用リポジトリで利用可能な版を確認する

AL2023はリポジトリをリリース単位で固定するため、同じOS名でも導入できる版が異なる
次の参照コマンドはパッケージをインストール・更新しない／リポジトリ照会ではローカルのメタデータキャッシュが更新されることがある

shell
cat /etc/os-release
uname -m
rpm -q system-release

releaseverの上書きファイルと、有効なリポジトリを確認する

shell
if [ -f /etc/dnf/vars/releasever ]; then cat /etc/dnf/vars/releasever; fi
dnf repolist --enabled

現在参照している標準リポジトリamazonlinuxの提供版を照会する／外部リポジトリを一時的に除外する

shell
dnf --disablerepo='*' --enablerepo=amazonlinux list --showduplicates httpd nginx php8.4-fpm mariadb114-server postgresql17-server valkey

掲載表と同じ固定リリースを照会する場合は、コマンド単位でreleaseverを指定する／OS全体のリポジトリ固定先は変更しない

shell
dnf --releasever=2023.12.20260817 --disablerepo='*' --enablerepo=amazonlinux list --showduplicates httpd nginx php8.4-fpm mariadb114-server postgresql17-server valkey

インストール済みの版と、提供される版は別に記録する／未インストールのパッケージを含むrpm照会は非ゼロで終了する

shell
rpm -q httpd nginx php8.4-fpm mariadb114-server postgresql17-server valkey

設計対象標準の考え方追加・変更する条件
定期処理systemd timerを利用する／cronieは標準でインストールされない既存のcrontab互換が必要ならcronieを追加する

cronieやrsyslogを追加する場合も、systemdやjournaldを単純に置き換える必要はない
cronとtimerによる二重実行、journalとsyslogからの重複転送を防ぐように、各処理とログの経路を1つずつ管理する

定期処理の基本設計

表は横にスクロールして確認できる

項目設計の論点
実行時刻時刻・タイムゾーン・時刻同期・許容遅延を決める
停止中の予定再起動後に実行し直すか、取りこぼしとして通知するかを決める
実行権限実行ユーザー、作業ディレクトリ、環境変数、必要な秘密情報を決める
失敗と長時間処理終了コード、タイムアウト、再試行回数、通知、再実行の安全性を決める
重複実行1台内の排他だけでなく、複数台から同じ業務を実行しない仕組みを決める

systemd timerのPersistent=trueはOnCalendarの停止中の実行機会を補う設定であり、取りこぼした全回数を順番に再生する仕組みではない
同じserviceが実行中ならtimerはそのserviceを重ねて起動しないが、複数サーバー間の排他は別に設計する

採用AMIの状態を確認する

カスタムAMIでは追加パッケージや設定が異なるため、OS名だけで標準状態と判断しない
次のコマンドは状態確認用であり、パッケージやサービス設定は変更しない

shell
cat /etc/os-release

systemdのバージョンと登録済みtimerを確認する

shell
systemctl --version
systemctl list-timers --all

cronieとrsyslogのインストール有無を確認する／未インストールの場合はrpmが非ゼロで終了する

shell
rpm -q cronie rsyslog

OS全体のjournal確認に必要な権限を得る

shell
sudo -i

journalの起動履歴と使用容量を確認する

root shell
journalctl --list-boots
journalctl --disk-usage

現在の起動以降の警告以上のjournalを確認する

root shell
journalctl -b -p warning --no-pager

journalの保存と収集を設計する

journaldのStorage=autoは/var/log/journalの存在などによって永続保存の動作が変わるため、再起動後も残ると決めつけない
対象AMIの設定・保存先・容量上限を調べ、実際の再起動試験で保存を確認する

CloudWatch agentのファイル収集に/var/log/journalのバイナリファイルを直接指定する設計は採用しない
テキスト収集が必要なら、rsyslogなどで必要なイベントをファイルへ出し、CloudWatch agentへ渡す経路を検証する

既存運用を移行するときの受入条件

既存の設定と収集経路を退避し、定期処理の正常・失敗・長時間実行・再起動後の動作を検証してから旧方式を止める
ログは同じ試験イベントが想定回数だけ到着すること、ローテーションと転送停止からの復旧、保持期限での削除まで確認する

systemd上流の説明には対象AMIより新しい機能も含まれるため、実装時には採用したAL2023上のmanとsystemdバージョンを照合する
本ページでは実機での設定変更・再起動・復旧試験は実施していない
