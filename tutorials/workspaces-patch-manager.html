Systems Manager Patch Manager

⑩[Systems Manager] Systems Manager環境構築手順書

仕様

構成・動作

EC2インスタンスプロファイルへAmazonSSMManagedInstanceCoreと用途別の権限を付与します。S3出力権限は出力先に合わせて別途確認します。

管理範囲

本書の設定表と画像は検証環境の例です。実作業では承認済みパラメータシートの値を使用します。

制約事項

Systems Manager用の受信ポートは不要です。対象ノードからSystems Manager、必要なS3バケットおよび更新元へ接続できる通信経路を用意します。

機能 役割
SSM Agent Windows EC2上でSystems Managerから受け取った命令を実行する
EC2用IAMロール SSM AgentがSystems Managerや出力先S3へアクセスする権限を提供する
Patch Baseline 適用対象とする更新プログラムの分類、重要度、承認条件などを定義する
Patch Group EC2と、そのEC2へ適用するパッチベースラインを関連付ける
Maintenance Windows パッチ処理を実行できる日時と時間帯を定義する
Maintenance Windowターゲット Maintenance Windowsの処理対象となるEC2をタグ条件などで指定する
Run Commandタスク AWS-RunPatchBaselineを実行してScanまたはInstallを行う
S3 Run Commandの標準出力および標準エラーを保存する
Compliance Scan／Install後のパッチ適用状況を確認する
Fleet Manager マネージドノードのOnline状態、OS、SSM Agentバージョンなどを確認する

構築作業

1. EC2用IAMロールを作成する

目的

EC2上のSSM AgentをSystems Managerへ登録し、Run CommandおよびPatch Managerを使用できるようにします。

AWSでは、組織の運用方式に適合する場合はDefault Host Management Configurationの利用を推奨しています。本手順では、本番環境の既存設計を再現する場合にも使用できるよう、EC2インスタンスプロファイルを個別に割り当てる構成を扱います。個別ロールを作成する場合は、信頼されたエンティティのユースケースに「EC2」を選び、基本ポリシーとしてAmazonSSMManagedInstanceCoreを付与します。旧ユースケースEC2 Role for AWS Systems Managerは新規構築で選択しません。

Configure instance permissions required for Systems Manager

操作
  1. IAMコンソールで「ロール」－「ロールを作成」を選択します。
  2. 「信頼されたエンティティタイプ」で「AWSのサービス」を選択します。
  3. ユースケースで「EC2」を選択します。
  4. AWS管理ポリシーAmazonSSMManagedInstanceCoreを選択します。
  5. S3出力、CloudWatch Logs、KMSなどを使用する場合だけ、必要な操作と対象リソースに限定した用途別ポリシーを追加します。
  6. ロール名を入力し、信頼ポリシーのサービスプリンシパルがec2.amazonaws.comとなっていることを確認します。
  7. 設定内容を確認してロールを作成します。

本番環境の既存ロールに付与された4ポリシーは、後述の比較表へ調査結果として記録します。これは新規ロールの作成手順ではなく、4ポリシーを新規ロールへ一括付与して再現するものでもありません。

設定の確認
  • EC2を信頼するIAMロールが作成されている
  • EC2起動画面のIAMインスタンスプロフィールで作成したロールを選択できる
  • 今回の検証ではSample_EC2RoleへAmazonSSMManagedInstanceCoreが付与されている
本番環境で確認された4ポリシー

次の4ポリシーは既存ロールの調査結果を示すものです。新しいワークロード用EC2インスタンスロールへ付与する推奨セットではありません。特にAmazonSSMFullAccessはSSM Agentの基本通信には不要なため、インスタンスロールへ自動的に追加しません。

正式名称 用途・扱い
AmazonEC2RoleforSSM 旧来のSSM用サービスロールポリシー。AWS資料では廃止予定とされ、AmazonSSMManagedInstanceCoreへの移行が案内されている
AmazonSSMFullAccess Systems Manager全体への広い操作権限。お客様既存構成として記録する
AmazonSSMManagedInstanceCore EC2をSystems Managerのマネージドノードとして動作させる基本権限
CloudWatchAgentAdminPolicy CloudWatch Agentの管理、メトリクス／ログ送信、関連Parameter Store操作に使用

本書では差分確認のため上記4ポリシーを記録します。既存ロールを変更する場合は、利用中の機能と実際のAPIアクセスを確認し、AmazonSSMManagedInstanceCoreと用途別の限定権限へ段階的に移行します。

弊社標準と最小権限の違い

弊社標準として指定された正式名称は、AWS管理ポリシーAmazonSSMFullAccessです。一方、AWS公式のEC2インスタンスプロファイル手順はAmazonSSMManagedInstanceCoreを基本としています。AmazonSSMFullAccessはssm:*などの広い操作権限を持ち、SSM Agentの基本通信だけを目的とするEC2ロールには必須ではありません。最小権限構成ではAmazonSSMManagedInstanceCoreを基本とし、S3、KMS、Directory Service、CloudWatch Logsなどの権限を利用機能と対象リソースに限定して追加します。

本番環境のS3出力権限

AmazonSSMFullAccessにはS3への書き込み権限は含まれません。一方、本番環境で付与されている旧ポリシーAmazonEC2RoleforSSMには、全リソースを対象とするs3:PutObject、s3:GetObject、s3:GetBucketLocation等が含まれます。既存のpatchmanager/出力も確認できるため、本番環境の再現では既存ロールの付与状況と実際の書き込み成功を確認し、不足する権限だけを追加します。

検証環境で同様に最小権限化する場合は、AmazonSSMManagedInstanceCoreを基本とし、arn:aws:s3:::sample-mw-bucket/patchmanager/*への必要な書き込み権限等へ限定したカスタムポリシーを用意します。切り替えテストが完了するまでAmazonEC2RoleforSSMを先に外しません。

S3出力だけに限定するポリシー例

次は同一アカウントの既存バケットへRun Command出力を書き込む用途に限定した例です。実際の暗号化方式、アクセス境界、SCPおよびバケットポリシーを確認してから適用します。

json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "WritePatchManagerCommandOutput",
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::sample-mw-bucket/patchmanager/*"
    },
    {
      "Sid": "ReadPatchLogBucketSettings",
      "Effect": "Allow",
      "Action": [
        "s3:GetBucketLocation",
        "s3:GetEncryptionConfiguration"
      ],
      "Resource": "arn:aws:s3:::sample-mw-bucket"
    }
  ]
}

SSE-KMSを使用する場合は対象KMSキーの必要権限を追加します。別アカウントのバケットへ出力する場合は、バケット側許可と必要に応じてs3:PutObjectAclも検討します。

2. 既存のログ保存用S3バケットを使用する

必要性

対象環境では、既存バケットsample-mw-bucketのpatchmanager/プレフィックスへRun Commandの実行ログを保存します。したがって、新しいS3バケットは作成せず、既存バケットとプレフィックスを出力先として指定します。

実行成功判定では、対象のMaintenance Window実行時刻、コマンドID、ノードIDおよびS3へ保存された出力オブジェクトを突き合わせます。

⚠️ 注意：S3書き込み権限の確認
CloudTrail用の既存バケットポリシーが設定されていても、それだけではPatch Manager／Run Commandの書き込み権限を満たしません。S3出力を有効にする場合は、対象ノードへ割り当てたEC2インスタンスプロファイルが、指定プレフィックスへ出力を書き込めることを確認します。

操作
  1. S3コンソールで既存バケットsample-mw-bucketを開きます。
  2. patchmanager/プレフィックスが存在し、過去の実行ログが保存されていることを確認します。
  3. 「パブリックアクセスをすべてブロック」、サーバー側暗号化、ライフサイクルルールおよび保存期間を確認します。
  4. 対象EC2のインスタンスプロファイルに、指定プレフィックスへのS3出力権限が付与されていることを確認します。必要なS3権限の許可元を確認し、不足する場合は指定プレフィックスに限定して追加します。
  5. Run Commandタスクの出力オプションで「S3への書き込みの有効化」を選択します。
  6. S3バケット名へsample-mw-bucket、キープレフィックスへpatchmanagerを入力します。
  7. テスト実行後、対象実行に対応する出力オブジェクトが作成されたことを確認します。

検証環境の入力値は、⑪に記載したRun Commandタスクのパラメータ画面で確認できます。画像内のバケット名は検証用のsample-mw-bucketです。対象環境では上記の既存バケットへ読み替えます。

設定の確認
  • パブリックアクセスがブロックされたログ用バケットが存在する
  • EC2インスタンスロールが指定プレフィックスへ出力を書き込める
  • 実行後、コマンドIDおよびノードIDに対応する標準出力／標準エラーが保存される
今回の確認結果

2026年9月8日01:00 JSTのInstall実行について、sample-mw-bucket/patchmanager/へ出力が保存されたことを確認しました。S3出力内のコマンドID9c048d9e-720c-47bc-ab41-b7d5fdc43045、ノードIDi-05914a8b6088a3a42、OperationType=Installおよび実行時刻をRun Command画面と突き合わせます。初回確認時にオブジェクトが見えない場合も、Run Command本体の成否とは分け、更新後の一覧、指定バケット／プレフィックス、コマンドID配下を再確認します。

Run CommandタスクのS3出力は、操作ユーザーではなく、対象マネージドノードへ割り当てたインスタンスプロファイルの権限で書き込まれます。Assign tasks to a maintenance window using the console

最新版をコマンドで確認する方法

最新のAmazon提供AMIを参照する場合は、Systems Managerのパブリックパラメータを利用できます。次のコマンドは東京リージョンにおける最新のWindows Server 2022日本語Full Base AMI IDを返します。日付を固定した既存環境の再現には使用せず、返されたAMI名と検証済み所有者を別途確認します。

PowerShell
aws ssm get-parameter --name "/aws/service/ami-windows-latest/Windows_Server-2022-Japanese-Full-Base" --region ap-northeast-1 --query "Parameter.Value" --output text

Find the latest AMIs using Systems Manager parameters

AMI IDはリージョンごとに異なり、同じ製品でもリリースごとに更新されます。したがって、手順書には検索文字列だけでなく、検証で使用したAMI名とAMI IDの両方を記録します。

操作
  1. EC2コンソールで「インスタンスを起動」を選択します。
  2. 名前、AMI、インスタンスタイプ、キーペア、VPC、サブネットおよびセキュリティグループを指定します。
  3. 「高度な詳細」で作成したIAMインスタンスプロフィールを選択します。
  4. SSM、SSM Messages、EC2 Messages、必要なAWS管理S3バケットおよびWindows Update Catalog／WSUSへ到達できる通信経路を確認します。
  5. インスタンスを起動し、状態が「実行中」、全ステータスチェックが合格になるまで待ちます。
注意事項
  • AMI IDはリージョン固有です。AMIが表示されない場合は別AMIへ無断で置き換えません。
  • RDPを使う場合はTCP/3389の接続元を承認済み管理元へ限定します。
  • Patch Groupタグは、使用するパッチベースラインとPatch Group値を確定してから付与します。

4. SSM Agentとマネージドノードを確認する

Amazon提供のWindows Server AMIには通常SSM Agentがプレインストールされているため、先にサービス状態とバージョンを確認し、未導入の場合だけインストールします。

Windows上で確認する

管理者権限のPowerShellで次を実行します。

PowerShell
Get-Service AmazonSSMAgent
Get-CimInstance Win32_Service -Filter "Name='AmazonSSMAgent'" |
    Select-Object Name, State, StartMode, PathName
& 'C:\Program Files\Amazon\SSM\amazon-ssm-agent.exe' -version

次の結果を確認します。

  • サービス状態がRunningです
  • 開始モードがAutoです
  • SSM Agentのバージョンが表示される

未導入でSystems Managerから接続できない場合は、次のいずれかの経路でWindowsへ管理者接続してインストールします。

  • 承認済み接続元からのRDP
  • EC2 Serial Console（Windows側の事前設定と権限がある場合）
  • Systems Manager以外の踏み台／運用接続経路
  • AMI作成工程またはUser Dataによる事前導入

SSM Agentがない状態ではFleet Manager、Session Manager、Run Commandからインストールできません。

SSM Agentが未導入の場合

Amazon提供のWindows Server 2022 AMIには、通常SSM Agentがプレインストールされています。Get-Service AmazonSSMAgentでサービスが見つからない場合だけ、次の手順を実施します。SSM Agentが未導入または停止している状態では、Session Manager、Fleet ManagerおよびRun Commandをインストール経路として使用できないため、RDP、踏み台、EC2 Serial Console、User Dataなど、Systems Manager以外の承認済み管理経路を使用します。

  1. Windows Serverへ管理者権限で接続します。
  2. Windows PowerShell 3.0以降が利用できることを確認します。
  3. 管理者権限のPowerShellで、東京リージョンの64-bit版インストーラーをダウンロードしてサイレントインストールします。
PowerShell
[System.Net.ServicePointManager]::SecurityProtocol = 'TLS12'
$installerPath = Join-Path $env:TEMP 'AmazonSSMAgentSetup.exe'
Invoke-WebRequest `
    -Uri 'https://amazon-ssm-ap-northeast-1.s3.ap-northeast-1.amazonaws.com/latest/windows_amd64/AmazonSSMAgentSetup.exe' `
    -OutFile $installerPath
Start-Process -FilePath $installerPath -ArgumentList '/S' -Wait
Restart-Service AmazonSSMAgent
Remove-Item -LiteralPath $installerPath -Force
  1. サービス状態、開始方式およびバージョンを確認します。
PowerShell
Get-Service AmazonSSMAgent
Get-CimInstance Win32_Service -Filter "Name='AmazonSSMAgent'" |
    Select-Object Name, State, StartMode, PathName
& 'C:\Program Files\Amazon\SSM\amazon-ssm-agent.exe' -version
  1. EC2へSystems Manager用IAMロールが割り当てられ、HTTPS（TCP/443）で必要なSystems Managerエンドポイントへ到達できることを確認します。
  2. 数分後にFleet Managerで対象ノードがOnlineとなることを確認します。

Runningにならない場合は、C:\ProgramData\Amazon\SSM\Logs\amazon-ssm-agent.log、IAMインスタンスプロフィール、DNS、プロキシおよびTCP/443の通信経路を確認します。

⑪[Systems Manager] Patch Manager設定手順書

仕様

構成・動作

Patch Groupは適用ベースラインの選択に使用します。Maintenance Windowのターゲット登録とベースラインへの関連付けをそれぞれ行います。

管理範囲

本書の設定表と画像は検証環境の例です。実作業では承認済みパラメータシートの値を使用します。

制約事項

スケジュール登録後は指定日時にタスクが起動します。運用開始前はウィンドウを無効化し、対象とパラメータの確認後に有効化します。

構築作業

1. Windows用パッチベースラインを決定する

  1. Systems Manager－「パッチマネージャー」－「パッチベースライン」を開きます。
  2. Windows Server用のAWS定義済みパッチベースラインについて、製品、分類、重要度、承認ルールが要件を満たすか確認します。
  3. AWS定義済みベースラインで要件を満たす場合は、そのベースラインを使用します。
  4. 承認日数、分類、重要度、拒否パッチなどを変更する必要がある場合だけ、Windows Server用カスタムパッチベースラインを作成します。
  5. 使用するベースラインID、ベースライン名、承認ルールおよび変更承認を記録します。

今回はAWS定義済みパッチベースラインの一覧まで確認しましたが、使用するWindowsベースラインとsample-windowの関連付けを直接示す照会結果は取得していません。この確認が終わるまで、関連付けを完了扱いにしません。

Windows用カスタムパッチベースラインを作成する場合

今回確認したAWS-DefaultPatchBaselineで要件を満たす場合、カスタムパッチベースラインの作成は不要です。承認待機日数、対象分類、重要度、Microsoft製アプリケーション、個別の承認／拒否KBなどを変更する場合だけ、次の手順で作成します。

  1. Systems Managerコンソールで「パッチマネージャー」－「パッチベースライン」を開きます。

  2. 「パッチベースラインを作成する」を選択します。

  3. 名前と説明を入力し、オペレーティングシステムにWindowsを選択します。

  4. 「利用可能なセキュリティ更新プログラムのコンプライアンスステータス」を選択します。承認待機中のセキュリティ更新も非準拠として可視化する場合はNon-Compliantを選択します。

  5. 「オペレーティングシステムの承認ルール」で、製品、分類、重要度および自動承認条件を設定します。

    • デフォルトベースライン相当の例：製品All、分類CriticalUpdatesおよびSecurityUpdates、重要度CriticalおよびImportant、リリースまたは更新から7日後に自動承認
    • Windows Server 2022だけへ限定する場合：製品で対応するWindowsServer2022を選択
    • 即時承認を避ける場合：自動承認日数を0にせず、変更管理で定めた検証期間を設定

  6. Microsoft製アプリケーションも対象にする要件がある場合だけ、「アプリケーションの承認ルール」を追加します。

  7. 個別に承認または拒否するKBがある場合だけ、「パッチの例外」へKB番号を入力し、拒否パッチのアクションを選択します。拒否リストは自動承認ルールおよび承認リストより優先されます。

  8. 必要に応じて管理用タグを付与し、「パッチベースラインを作成する」を選択します。

  9. 作成されたベースラインID、名前、Windows用承認ルールおよび例外設定を記録します。

  10. 作成しただけでは対象EC2に適用されないため、次節に従い、Patch Group値sample-windowを作成したベースラインへ関連付けます。

  11. Scanテストで出力されたBaselineIdが作成したベースラインIDと一致することを確認してからInstallへ進みます。

「Windowsのデフォルトとして設定」は、Patch Groupを指定しないWindowsノードを含めて影響範囲が広がるため、組織全体の設計・変更承認がある場合だけ使用します。

2. Patch Groupをパッチベースラインへ関連付ける

今回のPatch Group値はsample-windowです。

Patch Groupタグには次の2つの役割があります。

  1. Maintenance Windowが実行対象EC2を選ぶためのタグ条件
  2. Patch Managerが、そのEC2へどのパッチベースラインを適用するか選ぶための関連付けキー

Maintenance Windowのターゲット登録だけでは、2つ目の「どのベースラインを使うか」は設定されません。そのため、Patch Group=sample-windowを使う構成では、sample-windowを使用するWindowsパッチベースラインへ登録します。

  1. 使用するWindowsパッチベースラインの詳細を開きます。
  2. Patch Groupの変更／登録操作を選択します。
  3. Patch Group値へsample-windowを入力して登録します。
  4. ベースラインIDとPatch Group値の組み合わせを確認します。

Patch GroupのタグキーにはPatch GroupまたはPatchGroupを使用できますが、同一環境ではどちらか一方へ統一します。EC2のインスタンスメタデータからタグを参照できるようにしている場合は、空白を含まないPatchGroupを使用します。本検証では画面証跡に合わせてPatch Groupを使用します。

コンソールでPatch Groupを登録できないアカウント／リージョンでは、AWS CLIを使用します。まず、現在の関連付けを照会します。

PowerShell
$patchGroup = 'sample-window'
aws ssm get-patch-baseline-for-patch-group `
  --region ap-northeast-1 `
  --patch-group $patchGroup `
  --operating-system WINDOWS `
  --no-cli-pager

関連付けがない場合、または承認済みベースラインと異なる場合だけ、今回の検証値を使用して登録します。対象環境では、$patchGroupと$baselineIdを本番確認後の値へ置き換えます。

PowerShell
$patchGroup = 'sample-window'
$baselineId = 'pb-04ba050f612fba3a6'
aws ssm register-patch-baseline-for-patch-group `
  --region ap-northeast-1 `
  --baseline-id $baselineId `
  --patch-group $patchGroup `
  --no-cli-pager

登録後、get-patch-baseline-for-patch-groupを再実行し、返されたBaselineIdとPatchGroupが承認値と一致することを確認します。

⚠️ 注意：関連付け確認前はScan／Installを実行しない
Patch Group=sample-windowを使用する場合、適用するベースラインとの関連付けを照会結果で確認できるまでScan／Installへ進みません。

Patch Groupによるベースライン切り替えが不要で、単にMaintenance Windowの対象を選びたいだけであれば、予約されたPatch Groupキーではなく、MaintenanceWindow=sample-windowなどの通常タグをターゲット条件に使用できます。この構成ではPatch Groupとベースラインの関連付け手順を省略します。

1. 実行前チェック

次のすべてを満たすまでMaintenance Windowを実行しません。

  • EC2が実行中で、全ステータスチェックが合格です
  • Fleet ManagerのPing statusがOnlineです
  • AmazonSSMAgentがRunningです

  • 初回テストのRebootOptionがNoRebootです

2. Scanテストと成功判定

  1. 対象Maintenance WindowのタスクでOperation=Scan、RebootOption=NoReboot、登録済みターゲットとS3出力先を確認します。
  2. メンテナンスウィンドウの次回実行日時を確認し、承認済み時間帯に有効化します。検証用の日時へ変更する場合は元のスケジュールを記録します。実行開始後、「履歴」で実行IDと開始時刻を記録します。
  3. Maintenance Window、タスク、Run Commandおよびノード別結果を確認します。
  4. S3へ標準出力／標準エラーが保存されたことを確認します。
  5. Patch ManagerのComplianceを開き、最新スキャン結果を確認します。

次をすべて満たした場合、Scan実行成功と判定します。

  • Run Command全体と対象ノードがSuccess
  • WindowsのPatchWindowsステップがSuccess、応答コード0
  • Failed、Timed out、Delivery timed outが0
  • S3出力が実行IDおよび対象ノードと一致

Scan後にMISSINGまたはNonCompliantが表示されても、未適用パッチを正常に検出した結果であればScanコマンドの失敗ではありません。

Installと再起動設定を確認する

Installを実行する場合は、Maintenance WindowのRun Commandタスクを編集し、Operation=Installを選択します。RebootIfNeededは、Patch Managerが1件以上のパッチをインストールした場合、またはINSTALLED_PENDING_REBOOTを検出した場合にOSを再起動します。個々のパッチが再起動を必要とするかを判定してから再起動する設定ではありません。タスクを更新後、承認済みのInstall実行日時を設定して有効化し、実行開始後に履歴から実行IDを記録します。検証終了後は、承認済みの定期スケジュールとタスク設定へ戻します。今回再起動しなかったのは、新規適用パッチがなく、InstalledPendingRebootCount=0だったためです。

NoRebootを選択すると、Patch Managerはパッチ適用後にOSを再起動しません。ただし、インストーラーによるサービス再起動まで抑止するものではありません。

4. Systems Managerの成功とWindows Update表示の違い

Systems ManagerのSuccessと、Windows Update画面に「利用可能な更新プログラムはありません」と表示されることは同じ意味ではありません。また、Patch ManagerでCompliantでも、Windows Updateに別の更新が表示される場合があります。

  • Patch ManagerのSuccess：AWS-RunPatchBaselineコマンドが正常終了したことを示します
  • Patch ManagerのCompliant／MissingCount=0：使用したパッチベースラインで承認された更新に不足がないことを示します
  • Windows Updateの表示：Windows UpdateまたはWSUSが現在提示する更新を表示します。パッチベースラインの分類、重要度および承認待機日数と一致するとは限りません

今回使用したAWS-DefaultPatchBaselineは、Windows Serverについて、分類がCriticalUpdatesまたはSecurityUpdatesで、MSRC重要度がCriticalまたはImportantの更新を、公開または更新から7日後に承認します。Windows Updateで検出されたKB2267602はMicrosoft Defender Antivirusのセキュリティインテリジェンス更新です。頻繁に更新される定義更新です。今回のデフォルトベースラインで承認されたOSパッチとは別に管理されるため、Patch ManagerがCompliantでもWindows Updateに表示される場合があります。

5. 失敗時の対応と切り戻し

  1. 対象ウィンドウを無効化して次回実行を停止し、コマンドID、対象ノード、エラー出力を記録します。無効化だけでは進行中の処理は停止しません。
  2. SSM接続、更新元への通信、WindowsイベントログとRun Command出力を確認します。
  3. 再実行または復元が必要な場合は、影響範囲を確認し、事前に準備した復元手順に従います。更新プログラムの削除可否はKBごとに確認します。
  4. 復旧後、Online、サービス、業務疎通を確認し、スケジュールを再開します。
