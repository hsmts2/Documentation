Maintenance Window、Patch Group、Scan・Install、S3ログおよび適用後確認まで実機証跡で整理する

Patch Manager・メンテナンスウィンドウ構成概要

1. 本資料の目的

本資料は、AWS Systems Managerを初めて操作する方が、Windows Serverのパッチ適用に使用する各機能の役割と作成順序を体系的に理解することを目的とする

本書では、次の構成を対象とする

  • Windows Server 2022のEC2インスタンス
  • Systems Manager Patch Manager
  • AWS定義済みパッチベースラインおよび必要に応じたカスタムパッチベースライン
  • Patch Groupタグによる対象管理
  • Maintenance Windowsによる定期実行
  • AWS-RunPatchBaselineによるScanおよびInstall

2. まず知っておく全体像

Patch Managerでは、「どのパッチを適用するか」と「いつ、どのEC2へ実行するか」を別々の設定で管理する

決めること 使用する機能
どのパッチを承認・拒否するか パッチベースライン
どのEC2がそのルールを使うか Patch Group
いつ実行するか メンテナンスウィンドウ
どのEC2を実行対象とするか メンテナンスウィンドウのターゲット
何を実行するか メンテナンスウィンドウのタスク
パッチを調査するか、適用するか AWS-RunPatchBaselineのOperation

今回の構成は次の関係になる

text
パッチベースライン
  └─ Patch Group「p-pm-window」を関連付け
          ↑
EC2タグ：Patch Group = p-pm-window
          ↓
メンテナンスウィンドウのターゲット
  └─ タグ条件に一致するEC2を選択
          ↓
メンテナンスウィンドウのタスク
  └─ AWS-RunPatchBaseline（ScanまたはInstall）

図の読み方

  2. Maintenance Windowsで実行日時と実行可能な時間帯を決める

中央のManaged node（Windows EC2）では、SSM Agentがコマンドを実行し、IAMロールがAWSサービスとの通信権限を提供する。処理後はComplianceで適用状況を確認し、Fleet Managerでノードの接続状態と基本情報を確認する

4. 用語の説明

4.1 AWS Systems Manager

EC2やオンプレミスサーバーを一元管理するAWSサービス群。本手順では、Fleet Manager、Run Command、Patch Manager、Maintenance Windowsを使用する

4.2 SSM Agent

Windows Server内で動作し、Systems Managerからの命令を受け取るソフトウェア。SSM Agentが未導入、停止中またはSystems Managerへ通信できない場合、Run CommandやPatch Managerは使用できない

4.3 マネージドノード

SSM Agent、IAM権限および通信経路が準備され、Systems Managerから管理できる状態のサーバー。本手順ではWindows Server 2022のEC2インスタンスが該当する

4.4 Patch Manager

マネージドノードのパッチ不足状況を調査し、承認されたパッチを適用するSystems Managerの機能。AWSが個々のパッチを利用者環境でテストするわけではないため、適用前に対象、スケジュール、承認条件および再起動影響を確認する

4.5 パッチベースライン

「どのパッチを適用対象とするか」を定める判定基準。Windows Serverでは、製品、分類、MSRC重要度、自動承認までの日数、個別の承認・拒否パッチ等を設定する。ベースライン自体はスケジュールではない

4.6 カスタムパッチベースライン

利用組織が自ら承認条件を設定したベースライン。テスト期間、除外対象、コンプライアンス判定を明示できる。AWS公式ドキュメントは、コンプライアンスの基準をより明確に制御するため、カスタムベースラインの作成を推奨している

4.7 Patch Group

同じパッチベースラインを使うノードをまとめる論理的なグループ。独立したAWSリソースではなく、EC2等へタグを付与して定義する

text
キー：Patch Group
値：p-pm-window

タグキーは大文字・小文字を区別し、Patch GroupまたはPatchGroupを使用する。EC2インスタンスメタデータのタグを有効化している場合は、空白のないPatchGroupを使用する

4.8 メンテナンスウィンドウ

パッチ適用やソフトウェア更新など、サーバーへ影響を与える作業を実行できる時間帯とスケジュールを定義する機能。複数ノードの対象選択、同時実行数、エラー上限および実行履歴をAWS上で管理できる

4.9 ターゲット

メンテナンスウィンドウで「どのノードに実行するか」を定める設定。インスタンスID、タグ、AWS Resource Groups等で指定できる。タグ指定では、実行時点で条件に一致するノードが対象となる

4.10 タスク

メンテナンスウィンドウで「何を実行するか」を定める設定。今回はRun CommandタスクとしてAWS-RunPatchBaselineを登録する

4.11 AWS-RunPatchBaseline

パッチのScanまたはInstallを実行するAWS管理のSSMコマンドドキュメント。これ自体はパッチベースラインではない。適用するベースラインは、Patch Groupの関連付けまたはOSのデフォルト設定から決定される

Operation 動作 パッチ適用 再起動
Scan 不足パッチとコンプライアンスを調査 しない しない
Install 承認済みの不足パッチをインストール する RebootOptionに従う

4.12 コンプライアンス

パッチベースラインで承認されたパッチが、対象ノードへ適用されているかを表す判定結果。Scan後のMISSINGやNonCompliantは、不足パッチを正常に検出した結果であり、コマンドの失敗を意味しない

4.13 SuccessとWindows Updateの表示

Run CommandのSuccessは、AWS-RunPatchBaselineがエラーなく終了したことを示す。Windows Updateに表示されるすべての更新が適用済みであることを保証するものではない

Patch ManagerのCompliantやMissingCount=0は、使用したパッチベースラインで承認された更新に不足がないことを示す。Windows Updateは、ベースラインの分類、重要度または承認待機日数に含まれない更新も表示するため、両方の画面で結果が異なる場合がある

今回の検証では、AWS-DefaultPatchBaselineによるInstallがSuccess、MissingCount=0で終了した後、Windows Updateの手動確認でMicrosoft Defender Antivirusのセキュリティインテリジェンス更新KB2267602が表示された。これは頻繁に更新されるDefender定義更新であり、今回のベースラインで承認されたOSパッチとは区別して扱う

5. メンテナンスウィンドウの構成要素

構成要素 意味 今回の例
Name 識別するための名前 p-pm-mw-windowsupdate
Schedule 実行日時または頻度 検証時刻で試験後、承認済み本番日時へ変更
Schedule timezone スケジュールのタイムゾーン Asia/Tokyo
Duration メンテナンスウィンドウを開く時間 【構築時確認】
Cutoff 終了の何時間前から新規タスクを開始しないか 【構築時確認】
Target 実行対象 Patch Group=p-pm-window
Task 実行内容 AWS-RunPatchBaseline
Operation ScanまたはInstall 初回テストはScan
RebootOption Install後の再起動方針 本番適用前に承認を得て確定
Concurrency 同時実行台数または割合 検証時は1台
Error threshold 他ノードへの実行を停止するエラー数または割合 検証時は1エラーで停止

6. 今回の作成順序

AWS公式のコンソール手順は、「メンテナンスウィンドウ作成 → ターゲット登録 → Run Commandタスク登録」の順番である。本手順ではPatch Groupとベースラインの関係を明確にするため、次の順番とする

順番 作業 作成・設定するもの 確認ポイント
1 前提条件を確認 EC2、SSM Agent、IAM、通信経路 Fleet ManagerでOnline
2 使用するパッチベースラインを決定 AWS-DefaultPatchBaselineまたは承認済みカスタムベースライン OS、分類、重要度、承認日数
3 Patch Groupをベースラインへ関連付け sample-window 値の完全一致
4 メンテナンスウィンドウを作成 p-pm-mw-windowsupdate スケジュール、タイムゾーン、Duration、Cutoff
5 ターゲットを登録 Patch Group=p-pm-window タグ条件を記録
6 EC2へタグを付与 Patch Group=p-pm-window 対象が検証EC2の1台のみ
7 Run Commandタスクを登録 AWS-RunPatchBaseline 登録済みターゲットを選択
8 Scanテストを実行 Operation=Scan Success、応答コード0、コンプライアンス生成
9 結果をレビュー 実行履歴、パッチコンプライアンス MISSINGは検出結果でありScan失敗ではない
10 承認後にInstallを設定・実行 Operation=Install 再起動、サービス復旧、再Scan

注意
Run Commandタスクは、通常、登録済みのメンテナンスウィンドウターゲットを選択して作成する。そのため、ターゲット登録をタスク登録より先に実施する

8. 初学者が間違えやすい点

  • パッチベースラインはスケジュールではない。「何を適用するか」を決めるルールである
  • AWS-RunPatchBaselineはベースライン名ではなく、ScanまたはInstallを実行するコマンドドキュメントである
  • Patch Groupとターゲットは役割が異なる。今回は同じタグを両方に使う
  • ScanがSuccessで、不足パッチが検出された場合、ノードはNonCompliantになることがある。これはScan失敗ではない
  • Installはパッチ適用や再起動が発生し得るため、対象と実行時刻を承認してから実行する
  • InstallがSuccessでも、承認済み不足パッチが0件なら新しいKBのインストールと再起動は発生しない
  • Patch ManagerがCompliantでも、ベースライン対象外のDefender定義更新などがWindows Updateに表示される場合がある

4.1 目的

弊社標準として指定された正式名称は、AWS管理ポリシーAmazonSSMFullAccessである。一方、AWS公式のEC2インスタンスプロファイル手順はAmazonSSMManagedInstanceCoreを基本としている。AmazonSSMFullAccessはssm:*などの広い操作権限を持ち、SSM Agentの基本通信だけを目的とするEC2ロールには必須ではない。最小権限構成ではAmazonSSMManagedInstanceCoreを基本とし、S3、KMS、Directory Service、CloudWatch Logsなどの権限を利用機能と対象リソースに限定して追加する

情報：お客様環境のS3出力権限
AmazonSSMFullAccessにはS3への書き込み権限は含まれない。一方、お客様環境で付与されている旧ポリシーAmazonEC2RoleforSSMには、全リソースを対象とするs3:PutObject、s3:GetObject、s3:GetBucketLocation等が含まれる。既存のpatchmanager/出力も確認できるため、お客様環境の再現手順ではS3権限を追加作成せず、既存ロールの付与状況と実際の書き込み成功を確認する

最小権限化する場合は、AmazonSSMManagedInstanceCoreを基本とし、arn:aws:s3:::skyarch-pid-2849-logs/patchmanager/*への必要な書き込み権限等へ限定したカスタムポリシーを用意する。切り替えテストが完了するまでAmazonEC2RoleforSSMを先に外さない

情報：S3出力だけに限定するポリシー例
