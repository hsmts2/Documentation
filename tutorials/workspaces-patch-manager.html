Systems Manager Patch Manager

Windows ServerをSystems Managerのマネージドノードとして登録する
Maintenance Window、Patch Group、Scan・Install、S3ログおよび適用後確認まで実機証跡で整理する

SSM環境設定・Patch Manager運用手順（Windows Server 2022）

目次

概要

アジアパシフィック（東京）リージョンで、Windows Server 2022のEC2インスタンスSample-mng-001をSystems Managerのマネージドノードとして管理します。AWS-DefaultPatchBaseline、Patch Groupsample-window、メンテナンスウィンドウSample-MW-WindowsUpdateおよびAWS-RunPatchBaselineを使用し、Windowsパッチの検出・適用・実行結果確認までを行う

注意：Scan単独テストと実パッチ適用は未完了
2026年9月7日から8日に取得した画面で、設定登録とInstallコマンドの正常終了は確認済みです。ただし、初回実行は意図したScanではなくInstall/NoRebootであり、後続のInstall/RebootIfNeeded実行でも新規適用対象は0件でした。これらをScan単独テストまたは実パッチ適用の完了証跡として扱わない

本手順書で実施すること

  • EC2用IAMロールを作成し、Systems Managerに必要な権限を付与する
  • Windows Server 2022のEC2を起動し、SSM Agentとマネージドノードの状態を確認する
  • Windows用パッチベースラインとPatch Groupの関係を確認する
  • メンテナンスウィンドウ、ターゲットおよびRun Commandタスクを登録する
  • AWS-RunPatchBaselineのScanとInstallを実行し、Run Command、Compliance、S3およびWindowsの表示を照合する

完了条件

  • ✔ 対象EC2がFleet ManagerでOnlineとなり、SSM AgentがRunningである
  • ✔ 使用するパッチベースラインとPatch Groupの関連付けを確認できる
  • ✔ メンテナンスウィンドウの対象が承認済みノードに限定されている
  • ✔ Scan/NoRebootが正常終了し、パッチコンプライアンスを確認できる
  • ✔ 変更承認後のInstallが正常終了し、適用KB、再起動および業務影響を確認できる
  • ✔ Run Commandの出力が指定したS3プレフィックスに保存されている

現時点では、Scan/NoRebootの単独確認と、実際に不足パッチがある状態でのInstall・再起動・復旧確認が残っているため、本手順書の全完了条件は未達成

EC2用IAMロールを作成する

目的

EC2上のSSM AgentをSystems Managerへ登録し、Run CommandおよびPatch Managerを使用できるようにする

AWSでは、組織の運用方式に適合する場合はDefault Host Management Configurationの利用を推奨しています。本手順では、本番環境の既存設計を再現する場合にも使用できるよう、EC2インスタンスプロファイルを個別に割り当てる構成を扱います。個別ロールを作成する場合は、信頼されたエンティティのユースケースに「EC2」を選び、基本ポリシーとしてAmazonSSMManagedInstanceCoreを付与します。旧ユースケースEC2 Role for AWS Systems Managerは新規構築で選択しない

出典：Configure instance permissions required for Systems Manager

操作

  1. IAMコンソールで「ロール」－「ロールを作成」を選択
  2. 「信頼されたエンティティタイプ」で「AWSのサービス」を選択
  3. ユースケースで「EC2」を選択
  4. AWS管理ポリシーAmazonSSMManagedInstanceCoreを選択
  5. S3出力、CloudWatch Logs、KMSなどを使用する場合だけ、必要な操作と対象リソースに限定した用途別ポリシーを追加
  6. ロール名を入力し、信頼ポリシーのサービスプリンシパルがec2.amazonaws.comであることを確認
  7. 設定内容を確認してロールを作成

本番環境の既存ロールに付与された4ポリシーは、後述の比較表へ調査結果として記録します。これは新規ロールの作成手順ではなく、4ポリシーを新規ロールへ一括付与して再現するものでもない

画像では、① AmazonSSMManagedInstanceCoreを選択し、② 本手順では許可の境界を設定しないため「許可の境界なしでロールを作成」、③「次へ」の順に操作する

画像では、① ロール名、② 信頼ポリシーのec2.amazonaws.com、③ 許可ポリシーのAmazonSSMManagedInstanceCore、④ 管理用タグを確認し、⑤「ロールを作成」を選択する

実施後の確認

  • ✔ EC2を信頼するIAMロールが作成されている
  • ✔ EC2起動画面のIAMインスタンスプロフィールで作成したロールを選択できる
  • ✔ 今回の検証ではSample_EC2RoleへAmazonSSMManagedInstanceCoreが付与されている

本番環境で確認された4ポリシー

次の4ポリシーは既存ロールの調査結果を示すものであり、新しいワークロード用EC2インスタンスロールへ付与する推奨セットではありません。特にAmazonSSMFullAccessはSSM Agentの基本通信には不要なため、インスタンスロールへ自動的に追加しない

正式名称 用途・扱い
AmazonEC2RoleforSSM 旧来のSSM用サービスロールポリシー。AWS公式では廃止予定とされ、AmazonSSMManagedInstanceCoreへの移行が案内されている
AmazonSSMFullAccess Systems Manager全体への広い操作権限。お客様既存構成として記録する
AmazonSSMManagedInstanceCore EC2をSystems Managerのマネージドノードとして動作させる基本権限
CloudWatchAgentAdminPolicy CloudWatch Agentの管理、メトリクス／ログ送信、関連Parameter Store操作に使用

本書では差分確認のため上記4ポリシーを記録します。既存ロールを変更する場合は、利用中の機能と実際のAPIアクセスを確認し、AmazonSSMManagedInstanceCoreと用途別の限定権限へ段階的に移行する

弊社標準と最小権限の違い

弊社標準として指定された正式名称は、AWS管理ポリシーAmazonSSMFullAccessです。一方、AWS公式のEC2インスタンスプロファイル手順はAmazonSSMManagedInstanceCoreを基本としています。AmazonSSMFullAccessはssm:*などの広い操作権限を持ち、SSM Agentの基本通信だけを目的とするEC2ロールには必須ではありません。最小権限構成ではAmazonSSMManagedInstanceCoreを基本とし、S3、KMS、Directory Service、CloudWatch Logsなどの権限を利用機能と対象リソースに限定して追加する

本番環境のS3出力権限

AmazonSSMFullAccessにはS3への書き込み権限は含まれません。一方、本番環境で付与されている旧ポリシーAmazonEC2RoleforSSMには、全リソースを対象とするs3:PutObject、s3:GetObject、s3:GetBucketLocation等が含まれます。既存のpatchmanager/出力も確認できるため、本番環境の再現ではS3権限を追加作成せず、既存ロールの付与状況と実際の書き込み成功を確認する

最小権限化する場合は、AmazonSSMManagedInstanceCoreを基本とし、arn:aws:s3:::skyarch-pid-2849-logs/patchmanager/*への必要な書き込み権限等へ限定したカスタムポリシーを用意します。切り替えテストが完了するまでAmazonEC2RoleforSSMを先に外しない

S3出力だけに限定するポリシー例

次は同一アカウントの既存バケットへRun Command出力を書き込む用途に限定した例です。実際の暗号化方式、アクセス境界、SCPおよびバケットポリシーを確認してから適用する

json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "WritePatchManagerCommandOutput",
      "Effect": "Allow",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::skyarch-pid-2849-logs/patchmanager/*"
    },
    {
      "Sid": "ReadPatchLogBucketSettings",
      "Effect": "Allow",
      "Action": [
        "s3:GetBucketLocation",
        "s3:GetEncryptionConfiguration"
      ],
      "Resource": "arn:aws:s3:::skyarch-pid-2849-logs"
    }
  ]
}

SSE-KMSを使用する場合は対象KMSキーの必要権限を追加します。別アカウントのバケットへ出力する場合は、バケット側許可と必要に応じてs3:PutObjectAclも検討する

既存のログ保存用S3バケットを使用する

必要性

本番環境では、既存バケットskyarch-pid-2849-logsのpatchmanager/プレフィックスへRun Commandの実行ログを保存します。したがって、新しいS3バケットは作成せず、既存バケットとプレフィックスを出力先として指定する

実行成功判定では、対象のMaintenance Window実行時刻、コマンドID、ノードIDおよびS3へ保存された出力オブジェクトを突き合わせる

注意：S3書き込み権限の確認
CloudTrail用の既存バケットポリシーが設定されていても、それだけではPatch Manager／Run Commandの書き込み権限を満たしません。S3出力を有効にする場合は、対象ノードへ割り当てたEC2インスタンスプロファイルが、指定プレフィックスへ出力を書き込めることを確認する

操作

  1. S3コンソールで既存バケットskyarch-pid-2849-logsを開く
  2. patchmanager/プレフィックスが存在し、過去の実行ログが保存されていることを確認
  3. 「パブリックアクセスをすべてブロック」、サーバー側暗号化、ライフサイクルルールおよび保存期間を確認
  4. 対象EC2のインスタンスプロファイルにAmazonEC2RoleforSSMが付与されていることを確認する。本番環境をそのまま再現する場合、追加のS3ポリシーは作成しない
  5. Run Commandタスクの出力オプションで「S3への書き込みの有効化」を選択
  6. S3バケット名へskyarch-pid-2849-logs、キープレフィックスへpatchmanagerを入力
  7. テスト実行後、対象実行に対応する出力オブジェクトが作成されたことを確認

検証環境の入力値は、後述するRun Commandタスクのパラメータ画面で確認できます。画像内のバケット名は検証用のsample-mw-bucketであり、本番環境では上記の既存バケットへ読み替える

実施後の確認

  • ✔ パブリックアクセスがブロックされたログ用バケットが存在する
  • ✔ EC2インスタンスロールが指定プレフィックスへ出力を書き込める
  • ✔ 実行後、コマンドIDおよびノードIDに対応する標準出力／標準エラーが保存される

今回の確認結果

2026年9月8日01:00 JSTのInstall実行について、sample-mw-bucket/patchmanager/へ出力が保存されたことを確認しました。S3出力内のコマンドID9c048d9e-720c-47bc-ab41-b7d5fdc43045、ノードIDi-05914a8b6088a3a42、OperationType=Installおよび実行時刻をRun Command画面と突き合わせます。初回確認時にオブジェクトが見えない場合も、Run Command本体の成否とは分け、更新後の一覧、指定バケット／プレフィックス、コマンドID配下を再確認する

Run CommandタスクのS3出力は、操作ユーザーではなく、対象マネージドノードへ割り当てたインスタンスプロファイルの権限で書き込まれます。出典：Assign tasks to a maintenance window using the console

SNS通知を設定する（任意）

SNSはMaintenance Windowsの必須要素ではありません。今回の設定画面では「SNS通知の有効化」が未選択であるため、本手順の必須作業には含めない

  5. Run CommandタスクでSNS通知、通知対象イベントおよびCommand／Invocation単位を設定

SSM Agentとマネージドノードを確認する

Amazon提供のWindows Server AMIには通常SSM Agentがプレインストールされているため、先にサービス状態とバージョンを確認し、未導入の場合だけインストールする

Windows上で確認する

管理者権限のPowerShellで次を実行する

powershell
Get-Service AmazonSSMAgent
Get-CimInstance Win32_Service -Filter "Name='AmazonSSMAgent'" |
    Select-Object Name, State, StartMode, PathName
& 'C:\Program Files\Amazon\SSM\amazon-ssm-agent.exe' -version

次の結果を確認する

  • ✔ サービス状態がRunningである
  • ✔ 開始モードがAutoである
  • ✔ SSM Agentのバージョンが表示される

未導入でSystems Managerから接続できない場合は、次のいずれかの経路でWindowsへ管理者接続してインストールする

  • 承認済み接続元からのRDP
  • EC2 Serial Console（Windows側の事前設定と権限がある場合）
  • Systems Manager以外の踏み台／運用接続経路
  • AMI作成工程またはUser Dataによる事前導入

SSM Agentがない状態ではFleet Manager、Session Manager、Run Commandからインストールできない

SSM Agentが未導入の場合

Amazon提供のWindows Server 2022 AMIには、通常SSM Agentがプレインストールされています。Get-Service AmazonSSMAgentでサービスが見つからない場合だけ、次の手順を実施します。SSM Agentが未導入または停止している状態では、Session Manager、Fleet ManagerおよびRun Commandをインストール経路として使用できないため、RDP、踏み台、EC2 Serial Console、User Dataなど、Systems Manager以外の承認済み管理経路を使用する

  1. Windows Serverへ管理者権限で接続
  2. Windows PowerShell 3.0以降が利用できることを確認
  3. 管理者権限のPowerShellで、東京リージョンの64-bit版インストーラーをダウンロードしてサイレントインストール
powershell
[System.Net.ServicePointManager]::SecurityProtocol = 'TLS12'
$installerPath = Join-Path $env:TEMP 'AmazonSSMAgentSetup.exe'
Invoke-WebRequest `

Windows用カスタムパッチベースラインを作成する場合

  1. Systems Managerコンソールで「パッチマネージャー」－「パッチベースライン」を開く

  2. 「パッチベースラインを作成する」を選択

  3. 名前と説明を入力し、オペレーティングシステムにWindowsを選択

  4. 「利用可能なセキュリティ更新プログラムのコンプライアンスステータス」を選択します。承認待機中のセキュリティ更新も非準拠として可視化する場合はNon-Compliantを選択

    • Windows Server 2022だけへ限定する場合：製品で対応するWindowsServer2022を選択
    • 即時承認を避ける場合：自動承認日数を0にせず、変更管理で定めた検証期間を設定

  6. Microsoft製アプリケーションも対象にする要件がある場合だけ、「アプリケーションの承認ルール」を追加

  7. 個別に承認または拒否するKBがある場合だけ、「パッチの例外」へKB番号を入力し、拒否パッチのアクションを選択します。拒否リストは自動承認ルールおよび承認リストより優先される

Patch Groupをパッチベースラインへ関連付ける

今回のPatch Group値はsample-window

Patch Groupタグには次の2つの役割がある

  1. Maintenance Windowが実行対象EC2を選ぶためのタグ条件
  2. Patch Managerが、そのEC2へどのパッチベースラインを適用するか選ぶための関連付けキー

Maintenance Windowのターゲット登録だけでは、2つ目の「どのベースラインを使うか」は設定されません。そのため、Patch Group=sample-windowを使う構成では、sample-windowを使用するWindowsパッチベースラインへ登録する

  1. 使用するWindowsパッチベースラインの詳細を開く
  2. Patch Groupの変更／登録操作を選択
  3. Patch Group値へsample-windowを入力して登録
  4. ベースラインIDとPatch Group値の組み合わせを確認

Patch GroupのタグキーにはPatch GroupまたはPatchGroupを使用できますが、同一環境ではどちらか一方へ統一します。EC2のインスタンスメタデータからタグを参照できるようにしている場合は、空白を含まないPatchGroupを使用します。本検証では画面証跡に合わせてPatch Groupを使用する

コンソールでPatch Groupを登録できないアカウント／リージョンでは、AWS CLIを使用します。まず、現在の関連付けを照会する

powershell
$patchGroup = 'sample-window'
aws ssm get-patch-baseline-for-patch-group `
  --region ap-northeast-1 `
  --patch-group $patchGroup `
  --operating-system WINDOWS `
  --no-cli-pager

関連付けがない場合、または承認済みベースラインと異なる場合だけ、今回の検証値を使用して登録します。本番環境では、$patchGroupと$baselineIdを本番確認後の値へ置き換える

powershell
$patchGroup = 'sample-window'
$baselineId = 'pb-04ba050f612fba3a6'
aws ssm register-patch-baseline-for-patch-group `
  --region ap-northeast-1 `
  --baseline-id $baselineId `
  --patch-group $patchGroup `
  --no-cli-pager

登録後、get-patch-baseline-for-patch-groupを再実行し、返されたBaselineIdとPatchGroupが承認値と一致することを確認する

注意：関連付け確認前はScan／Installを実行しない
Patch Group=sample-windowを使用する場合、適用するベースラインとの関連付けを照会結果で確認できるまでScan／Installへ進まない

Patch Groupによるベースライン切り替えが不要で、単にMaintenance Windowの対象を選びたいだけであれば、予約されたPatch Groupキーではなく、MaintenanceWindow=sample-windowなどの通常タグをターゲット条件に使用できます。この構成ではPatch Groupとベースラインの関連付け手順を省略する

Systems Managerの成功とWindows Update表示の違い

Systems ManagerのSuccessと、Windows Update画面に「利用可能な更新プログラムはありません」と表示されることは同じ意味ではありません。また、Patch ManagerでCompliantでも、Windows Updateに別の更新が表示される場合がある

  • Patch ManagerのSuccess：AWS-RunPatchBaselineコマンドが正常終了したことを示する
  • Patch ManagerのCompliant／MissingCount=0：使用したパッチベースラインで承認された更新に不足がないことを示する
  • Windows Updateの表示：Windows UpdateまたはWSUSが現在提示する更新を表示します。パッチベースラインの分類、重要度および承認待機日数と一致するとは限らない

今回使用したAWS-DefaultPatchBaselineは、Windows Serverについて、分類がCriticalUpdatesまたはSecurityUpdatesで、MSRC重要度がCriticalまたはImportantの更新を、公開または更新から7日後に承認します。Windows Updateで検出されたKB2267602はMicrosoft Defender Antivirusのセキュリティインテリジェンス更新であり、頻繁に更新される定義更新です。今回のデフォルトベースラインで承認されたOSパッチとは別に管理されるため、Patch ManagerがCompliantでもWindows Updateに表示される場合がある
