TerraformのState管理と運用

構成ファイル・State・実リソースStateの確認手動変更があった場合既存リソースを管理対象へ取り込むリソース名・配置の変更ファイル分割とState分割S3 Backendへの移行ロック・診断・バージョン更新

Stateの確認、手動変更との整合、Import、アドレス変更、環境分割とBackend移行を整理

構成ファイル・State・実リソース

対象保持する情報編集・更新方法
構成ファイル（.tf）目標とするリソースと属性利用者がコードを編集
StateTerraformのアドレスと実リソースIDの対応・属性情報Terraformのコマンドで管理
実リソースクラウド上の現在の状態通常はTerraform経由で変更

Stateは構成ファイルの代わりではない。Terraformは管理対象の現在値を読み取り、構成との差分をPlanへ表示。コンソールで変更した属性が.tfへ自動で書き戻されるわけではない

手順内のaws_sqs_queue.practiceは基本操作とHCLの検証用キュー。実際のアドレスはstate listで確認

Stateの確認

① 対象フォルダーへ移動し、接続先とWorkspaceを確認

PowerShell
Set-Location "$env:USERPROFILE\IaC\Terraform\queue-lab"
$env:AWS_PROFILE = "iac-admin"
aws sts get-caller-identity --profile iac-admin
terraform workspace show

② State内のリソースアドレスを一覧表示

PowerShell
terraform state list

③ 検証用キューのState内の属性を確認。実リソースの最新値を必ず再取得するコマンドではない点に注意

PowerShell
terraform state show aws_sqs_queue.practice

④ 実リソースとの照合を含む通常Planを表示。予定外の変更がある場合はApplyを保留

PowerShell
terraform plan
⚠️ 注意

Stateには秘密値が含まれる可能性があるため、内容をそのままチャットや公開リポジトリに掲載しない。Stateを手動で編集・削除して帳尻を合わせない

手動変更があった場合

例えばSQSの最大メッセージサイズをコンソールから変更した場合は、Planで対象属性を確認したうえで、変更を残すか戻すかを決定

方針対応注意
コードの値へ戻す通常のPlanで戻し先を確認してApply戻したい属性以外の差分にも注意
手動変更を正式な構成として残す.tf／tfvarsも同じ値に更新し、通常のPlanを再確認refresh-onlyだけではコードは更新されない
実状態をStateへ記録するだけrefresh-onlyの計画を確認して適用コードが古いままなら次の通常Planで元に戻す変更が出る

① 実状態をStateへ記録する差分を確認したい場合だけ、refresh-onlyの計画を作成

PowerShell
terraform plan -refresh-only -out=refresh.tfplan

② 内容を確認後にStateと出力を更新。実リソースをコードどおりに変更する操作ではない

PowerShell
terraform apply refresh.tfplan

③ 通常のPlanでも意図した状態になっていることを確認

PowerShell
terraform plan

ignore_changesは指定属性を以後の更新計画で無視する設定。別の管理主体が所有する属性に限定し、ドリフトを見えなくするための一括指定は避ける

既存リソースを管理対象へ取り込む

Importは既存リソースとTerraformアドレスの対応をStateへ登録する操作。既に別のStateで管理しているリソースを重複登録しない。ここでは未管理のSQSキューを、別の空の作業フォルダーへ取り込む例

① AWS Providerの設定を用意し、main.tfとimport.tfを保存。名前・サイズは実リソースの値を調査して設定。<QUEUE_URL>を実際のキューURLへ置換

main.tf
resource "aws_sqs_queue" "adopted" {
  name             = "existing-practice-queue"
  max_message_size = 4096
}
import.tf
import {
  to = aws_sqs_queue.adopted
  id = "<QUEUE_URL>"
}

② 作業フォルダーを初期化し、Importと属性変更の両方を確認

PowerShell
terraform init
terraform plan -out=import.tfplan
⚠️ 注意

Importの計画に更新・置換・削除が混在している場合は、そのまま適用しない。実リソースに合わせてコードを修正し、取り込みだけの計画になってから進行

③ 確認済みの計画でStateへ登録

PowerShell
terraform apply import.tfplan

④ 登録されたアドレスと、意図しない差分がないことを確認

PowerShell
terraform state list
terraform plan

Import用IDの形式はリソース型ごとに異なる。dataブロックは参照専用であり、Importの代わりに管理対象へ取り込むものではない

リソース名・配置の変更

クラウド上のキュー名は変えず、Terraform内部のアドレスだけを変更する例。main.tfのresourceラベルをpracticeからmessagesへ変更し、outputs.tfなどの参照も更新。そのうえで同じルートモジュールに次を追加

moved.tf
moved {
  from = aws_sqs_queue.practice
  to   = aws_sqs_queue.messages
}

① 移動として認識され、作成・削除が計画されていないことを確認

PowerShell
terraform plan -out=move.tfplan

② 確認したアドレス変更をStateへ反映

PowerShell
terraform apply move.tfplan

③ 新アドレスと差分がないことを確認

PowerShell
terraform state list
terraform plan

モジュール化する場合も、移動先アドレスをmodule.queue.aws_sqs_queue.thisなどへ指定。movedは同じState内の対応変更であり、別Stateへの移管とは別作業

⚠️ 注意

terraform state rmは実リソースを削除せず、管理対象から外す操作。構成を残したままだと次のPlanで新規作成が提案されるため、削除コマンドの代用にはしない

ファイル分割とState分割

分け方効果State
同じフォルダーでnetwork.tfとapp.tfに分割コードの見通しを改善同じState
子モジュールへ分割して同じルートから呼び出す共通化・再利用同じState
別のルートフォルダー＋別のBackend key／HCP Workspace環境・担当・変更周期を分離別State
配置例
terraform-project/
  envs/
    dev/     # dev専用のBackendまたはHCP Workspace
    prod/    # prod専用のBackendまたはHCP Workspace
  modules/
    queue/   # 共通の子モジュール

フォルダーだけを分けても同じBackend keyを指定すると同じStateを共有。CLI Workspaceの切り替えも認証や権限の境界とは別。業務と検証では接続先・権限・State保存先を合わせて分離

他のStateを参照する場合、terraform_remote_stateで利用するのはルートのoutput。ただしBackendの認証はState全体を読める権限につながるため、秘密値の境界としては扱わない。必要な値だけをParameter Store等へ公開する方法も検討

S3 Backendへの移行

ローカルStateから移行する場合の例。HCP Terraformへの移行はHCP Terraformを参照。両方式を同時に指定しない

① State用S3バケットを別管理で準備し、公開アクセス遮断・暗号化・バージョニングを確認。対象Stateへの読み書き、ロック用オブジェクトの作成・読み取り・削除権限を実行ロールへ付与。バケットを移行対象と一緒にdestroyしない構成に分離

② 既存Stateをアクセス制限された保存先へバックアップし、チーム内の同時実行を停止。ローカルのterraform.tfstateをコピーする場合は暗号化・保管権限も確認

③ <STATE_BUCKET>を用意したバケット名へ置換し、backend.tfを追加。keyはこの環境専用の値を使用

backend.tf
terraform {
  backend "s3" {
    bucket       = "<STATE_BUCKET>"
    key          = "queue-lab/dev/terraform.tfstate"
    region       = "ap-northeast-1"
    encrypt      = true
    use_lockfile = true
  }
}

④ 移行先の認証を確認してStateを移行。表示される移行元・移行先を確認してから承認

PowerShell
terraform init -migrate-state

⑤ 移行後の管理対象とPlanを確認し、S3側でも対象キーの存在を確認

PowerShell
terraform state list
terraform plan

use_lockfileには対応するTerraformが必要。この手順はTerraform 1.10以降を前提。古いDynamoDB方式を新規導入する手順とは分離

⚠️ 注意

移行に失敗した場合は別のBackendでApplyを始めず、どちらが正のStateかを確認。-reconfigureだけではState移行にならない

ロック・診断・バージョン更新

状況先に確認する内容
Stateロックを取得できない他の利用者・CIが実行中か、ロック情報の操作・作成時刻を確認。稼働中のロックを強制解除しない
Providerの変更が必要required_providersとロックファイルを確認。init -upgradeは許容範囲内の依存更新を伴う
特定リソースを作り直したい通常Planを先に確認。必要な場合だけ-replaceで置換計画をレビュー
Planの終了コードをCIで使う-detailed-exitcodeは0が差分なし、1がエラー、2が差分あり
詳細ログが必要TF_LOGを必要な間だけ設定し、ログを秘密情報として保護

① Provider依存関係を表示

PowerShell
terraform providers

② 詳細ログを一時的に取得する場合の例。処理後にこのターミナルのログ設定を解除

PowerShell
$env:TF_LOG = "DEBUG"
$env:TF_LOG_PATH = Join-Path $env:TEMP "terraform-debug.log"
try { terraform plan } finally {
  Remove-Item Env:TF_LOG
  Remove-Item Env:TF_LOG_PATH
}

生成したログは公開しない。障害復旧時も-targetやforce-unlockを普段の手順へ組み込まず、対象と影響を特定してから使用
