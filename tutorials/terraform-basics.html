実行場所・接続先の確認

TerraformとAWS CLIを導入済みのWindowsで、VS Codeの統合ターミナル（PowerShell）を使用。認証はIAM Identity Center、導入はIaCを参照。既存のSQSとは別名の検証用キューを作成

① 既存構成とStateを分離するため、新しい作業フォルダーを作成して移動。既に同名フォルダーがある場合は中身を確認し、別名を使用

PowerShell
New-Item -ItemType Directory -Path "$env:USERPROFILE\IaC\Terraform\queue-lab"
Set-Location "$env:USERPROFILE\IaC\Terraform\queue-lab"
Get-Location
Get-ChildItem -Force

② SSOにログインし、このターミナルで使用するプロファイルを指定

PowerShell
aws sso login --profile iac-admin
$env:AWS_PROFILE = "iac-admin"
$env:AWS_REGION = "ap-northeast-1"

③ AWSアカウント・ロールとTerraformのバージョンを確認。接続先が意図した検証環境と異なる場合は中止

PowerShell
aws sts get-caller-identity --profile iac-admin
terraform version
⚠️ 注意

以降のapplyはAWSのリソースを変更。利用量に応じた料金や、削除によるメッセージ消失が発生するため、業務環境とは分離して実施

構成ファイルの作成

VS Codeで同じ作業フォルダーに次の4ファイルを保存。下位フォルダー内の.tfファイルは自動では読み込まれない

ファイル役割
versions.tfTerraform・Providerのバージョン条件と接続リージョン
variables.tf外部から受け取る値と入力条件
main.tf共通値と作成するリソース
outputs.tf作成後に取り出す値
versions.tf
terraform {
  required_version = ">= 1.10, < 2.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = "ap-northeast-1"
}
variables.tf
variable "environment" {
  type        = string
  description = "Name used to separate the practice environment"
  default     = "dev"

  validation {
    condition     = contains(["dev", "stg"], var.environment)
    error_message = "Choose dev or stg."
  }
}

variable "message_size" {
  type        = number
  description = "Maximum message size in bytes"
  default     = 2048

  validation {
    condition     = contains([2048, 4096], var.message_size)
    error_message = "Use 2048 or 4096 for this exercise."
  }
}
main.tf
locals {
  queue_name = "tf-practice-${var.environment}"
  common_tags = {
    Environment = var.environment
    ManagedBy   = "Terraform"
  }
}

resource "aws_sqs_queue" "practice" {
  name                      = local.queue_name
  max_message_size          = var.message_size
  sqs_managed_sse_enabled   = true
  tags                      = merge(local.common_tags, { Name = local.queue_name })
}
outputs.tf
output "queue_url" {
  description = "URL of the practice queue"
  value       = aws_sqs_queue.practice.url
}

var.environmentは外部入力、local.queue_nameは内部で組み立てた値、aws_sqs_queue.practice.urlはリソース属性の参照。同じフォルダーのファイルはまとめて評価され、ファイル名で実行順序は決まらない

初期化・作成・確認

① Providerをダウンロードし、依存関係を初期化

PowerShell
terraform init

② HCLを整形して構文・整合性を検証。validateだけではAWS権限や作成可否の確認は未完了

PowerShell
terraform fmt
terraform validate

③ 作成計画をファイルへ保存。対象がtf-practice-devのみで、追加1件・変更0件・削除0件であることを確認

PowerShell
terraform plan -out=create.tfplan

④ 確認した計画を適用。保存済みPlanを指定するため、yesの再入力はなく即時実行

PowerShell
terraform apply create.tfplan

⑤ キューURLとState上の管理対象を確認

PowerShell
terraform output queue_url
terraform state list

⑥ 再度Planを実行し、差分がないことを確認

PowerShell
terraform plan
⚠️ 注意

Stateと保存済みPlanには秘密値が含まれる場合があるため、Gitへ登録しない。sensitive = trueは表示抑制であり、Stateの暗号化指定ではない

変数の指定・属性変更

① 作業フォルダーに次のterraform.tfvarsを保存。environmentは変更せず、最大メッセージサイズだけを2048から4096へ変更

terraform.tfvars
environment  = "dev"
message_size = 4096

② 変更計画を保存。max_message_sizeの更新だけで、置換・削除がないことを確認

PowerShell
terraform plan -out=update.tfplan

③ 確認した更新を適用し、再実行時の差分がないことを確認

PowerShell
terraform apply update.tfplan
terraform plan
指定方法読み込み方
variableのdefault入力値を渡さない場合の既定値
TF_VAR_message_sizePowerShellでは $env:TF_VAR_message_size = "4096" の形式
terraform.tfvars / terraform.tfvars.jsonルートモジュールで自動読み込み
*.auto.tfvars / *.auto.tfvars.jsonファイル名の辞書順で自動読み込み
-var / -var-fileコマンド実行時に明示的に指定

ローカルCLIでは表の下ほど優先。複数の-var／-var-fileは後の指定を優先。HCP Terraformの変数セット・優先変数は別途優先順位の確認が必要

別名のファイル（例：stg.tfvars）は自動では読み込まれない。次の例はPlanのみで確認し、environmentを変えるとキュー名の変更・置換が生じ得る点に注意

stg.tfvars
environment  = "stg"
message_size = 2048

④ 別の変数ファイルで計画を表示。適用はせず、tfvarsを変えてもStateが別環境に分離されないことを確認

PowerShell
terraform plan -var-file=stg.tfvars

繰り返し・式・テンプレート

以降は記法の例。作成済みのキュー定義への追記ではなく、別の検証用構成で使用

記法使い分け
for_eachMapのキーやSetの要素で個別管理。キーは計画時点で確定させる
count個数や0／1での有効・無効切り替え。要素の並びを変えると数値インデックスの対応に注意
for既存コレクションを別のList／Mapに変換
dynamicProviderが定義する繰り返し可能なネストブロックを生成。resource自体の複製にはfor_each／countを使用
HCL：for_eachと出力の例
variable "queue_names" {
  type    = set(string)
  default = ["orders", "notifications"]
}

resource "aws_sqs_queue" "batch" {
  for_each = var.queue_names
  name     = "tf-lab-${each.key}"
}

output "queue_urls" {
  value = { for name, queue in aws_sqs_queue.batch : name => queue.url }
}

この例は2キューを管理。State上のアドレスはaws_sqs_queue.batch["orders"]のようにキー付きになる。countの全用途が非推奨という意味ではない

HCL：テンプレートの読み込み例
locals {
  rendered_message = templatefile("${path.module}/message.tftpl", {
    environment = var.environment
  })
}

output "message" {
  value = local.rendered_message
}
message.tftpl
Environment: ${environment}

長いテキストは外部テンプレートへ分離。file()は文字列をそのまま読み込み、templatefile()は指定した変数を展開

① 式の結果だけを対話確認。起動後に次の式を1行ずつ入力し、exitで終了

PowerShell
terraform console
Terraform console
upper("dev")
contains(["dev", "stg"], "dev")
{ for name in ["orders", "notifications"] : name => upper(name) }
exit

検証用リソースの削除

queue-labで作成したキューを今後のState・モジュール練習に使う場合は削除を後回し。構成とStateを残したまま、Terraformから削除

① 実行場所と管理対象を確認。予定外のリソースが含まれていれば中止

PowerShell
Get-Location
terraform state list

② 削除計画を保存。対象の検証用キュー以外が含まれないことを確認

PowerShell
terraform plan -destroy -out=destroy.tfplan
⚠️ 注意

次のコマンドは保存済みの削除計画を確認入力なしで実行。キュー内のメッセージも失われるため、不要になった検証用キューだけを対象に実施

③ 確認した削除計画を実行

PowerShell
terraform apply destroy.tfplan

④ 管理リソースがStateから除かれたことを確認

PowerShell
terraform state list

構成ファイルを残した状態の通常Planは再作成を提案。削除後にNo changesとなることを完了条件にはしない

Gitで管理するファイル

構成ファイルと.terraform.lock.hclはバージョン管理。ローカル作業用の.gitignoreに次を追加し、秘密値を含むtfvarsは登録対象から除外

.gitignore
.terraform/
*.tfstate
*.tfstate.*
*.tfplan
crash.log
crash.*.log
*.tfvars
*.tfvars.json
.terraformrc
terraform.rc

共有用の入力例は秘密値を除いたterraform.tfvars.exampleで管理。既に追跡済みのファイルには.gitignoreが遡って適用されないため、コミット前に差分を確認
