Gitリモート操作

clone・リポジトリ作成・pushの実行記録と、fetch・pull・追跡ブランチの使い分け

ローカル・リモート・追跡ブランチ

名前場所・役割
main自分のPCにあるローカルブランチ
origin接続先URLに付ける名前。認証情報やアカウント名ではない
origin/mainPC内に保存した、最後に取得・更新したリモートmainの位置
GitHub上のmainサーバー側のブランチ。ほかの人のpushでも更新される

git statusのahead／behindはPC内のorigin/mainとの比較。サーバーの最新状態を確認するにはfetchが必要。working tree cleanは未コミットの変更がない状態で、push済みかどうかとは別

Gitの初期設定はGit 概要、HTTPS・SSHの設定はGitHub認証を参照。以下の実行結果は作業時点の記録

追跡ブランチの設定

追跡先は「このローカルブランチが通常どのリモートブランチとやり取りするか」の設定。ファイルの送受信やマージは行わない

1. mainの追跡先をorigin/mainに設定

Git Bash
$ git branch --set-upstream-to=origin/main main
branch 'main' set up to track 'origin/main'.

2. 追跡先との関係を確認

Git Bash
$ git status
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean
コマンド（使い分け）意味
git branch -u origin/main main--set-upstream-toの短縮形。既存のorigin/mainを追跡先に設定
git push -u origin main初回pushと追跡設定をまとめて実行する場合の操作例
git branch -vv各ローカルブランチの追跡先・差分状態を表示

通常の同名ブランチ運用では、設定後はgit pullやgit pushの引数を省略可能。push先の決定にはpush.defaultなどの設定も関係

fetch・merge・pullの違い

操作origin/main現在のブランチ・作業ファイル
git fetch originリモートの履歴を取得して更新そのまま。mainへは取り込まない
git merge origin/main新たな取得は行わない取得済みのorigin/mainを現在のブランチへ統合
git pull --no-rebase先にfetchで更新取得後にmergeで統合
git pull --rebase先にfetchで更新取得後にローカルの独自コミットを付け直す
git pull --ff-only先にfetchで更新分岐していなければ前進。分岐していれば統合せず停止

引数なしのgit pullの統合方法は設定・Gitのバージョンに依存するため、方式を明示すると意図が伝わる

次は追跡先設定済みのmainで、取得と内容確認を分ける操作例。実行結果は状態により変化

1. 未コミットの変更を確認。変更があればコミットまたはstashしてから続行

Git Bash（操作例）
git status

2. 取り込み先のmainへ切り替え

Git Bash（操作例）
git switch main

3. リモートの最新履歴を取得

Git Bash（操作例）
git fetch origin

4. ローカルとリモート追跡ブランチの履歴を確認

Git Bash（操作例）
git log --all --graph --oneline

5. mainとorigin/mainのファイル内容を比較

Git Bash（操作例）
git diff main origin/main

6. 取得済みのorigin/mainをmainへ取り込む

Git Bash（操作例）
git merge origin/main

競合時は編集・保存 → git add → git commitで完了。実際のfetch／merge／pushの出力はpush拒否への対処に掲載

取得と統合をまとめる場合は上記のfetch・mergeの代わりにgit pull --no-rebaseを使用。分岐を統合せずに更新だけしたい場合はgit pull --ff-onlyを使用

強制pushの注意点

git push -fは通常の履歴保護を無視してリモートブランチを更新する操作。ほかの人のコミットをブランチの履歴から外す可能性があるため、push拒否の一般的な解決策としては使用しない

通常の拒否はfetchで差分を確認し、mergeなどで統合してから再push。共有後のamendやrebaseは、チームの合意なしに実施しない

履歴を書き換える必要がある場合は、対象・他者の作業・保護ルールを確認し、期待するリモート位置を条件にする--force-with-leaseを検討。ただし無条件に安全になるわけではなく、バックグラウンドのfetchなどで期待値が変わる点にも注意

bareリポジトリとGitHubリポジトリ

操作作成場所作成されるもの
git init自分のPC作業ファイルを編集できる通常のリポジトリ
git init --bare project.git実行したPC・サーバー作業ツリーを持たない、共有先として使うリポジトリ
gh repo createGitHubGitHub上のリポジトリ。認証・権限が必要

git init --bareだけではGitHub上にリポジトリは作成されない。office／homeで共有先に使ったremote.gitはbareリポジトリに該当

公開したブランチのレビューを依頼する流れはGitHubのPull Requestとレビューを参照
