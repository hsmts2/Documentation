AWS Managed Microsoft AD 構築・管理

2つのAvailability Zoneへ配置するAWS Managed Microsoft ADの構成と作成手順をまとめる
ディレクトリ作成後のユーザー、グループ、パスワードおよび可用性確認まで整理する

AWS Managed Microsoft ADの2台ドメインコントローラー構成・役割

目次

概要

本資料で説明すること

本資料では、AWS Managed Microsoft ADad.example.comに配置された2台のドメインコントローラーについて、通常時の役割、PDC Emulatorとの違い、クライアントによる接続先の選択および障害時の動作を説明する

今回の構成では、2台をap-northeast-1aとap-northeast-1cへ1台ずつ配置し、DNS IPアドレスとして192.168.225.68と192.168.225.126を使用する

結論

結論：2台とも稼働し、一方は待機専用ではない

2台とも通常時から稼働する書き込み可能なドメインコントローラーです。ユーザー認証、コンピューター認証、DNS、Kerberos、LDAP、グループポリシーなどのActive Directory機能を提供し、ディレクトリ情報を相互にレプリケーションする

AWSが2台を作成する理由

AWS Managed Microsoft ADでは、ディレクトリ作成時に2台のドメインコントローラーが異なるアベイラビリティーゾーンのサブネットへ1台ずつ配置されます。目的は、1台または1つのアベイラビリティーゾーンへ障害やメンテナンスの影響が生じても、もう1台を利用できる構成にすること

AWS Directory Serviceコンソールでは、この初期2台を Required と表示します。Requiredは「主系」という意味ではなく、可用性を確保するために削除できない必須の2台という意味です。可用性や処理性能をさらに高めるために追加したDCは Additional と表示される

出典：AWS公式：AWS Managed Microsoft ADで作成される内容

RequiredとAdditionalの違い

AWSコンソール上の区分 意味 削除・縮退
Required DC ディレクトリ作成時にAWSが作成する初期2台。異なるAZへ分散される 2台未満にはできない
Additional DC 可用性、耐障害性または認証処理性能を高めるために追加するDC 合計2台を下限として削減可能

AWS公式ページの一部には、削除できない初期2台を「primary and secondary domain controllers」と表現した箇所があります。ただし、これはADの処理方式が主系／待機系であることを示すものではありません。同じAWS公式資料ではすべてのDCが書き込み可能であると説明されているため、本資料では誤解の少ない Required DC-1／Required DC-2 という表現へ統一する

どちらが「メイン」なのか

通常の認証・検索処理には固定のメインDCはない

Microsoft Active Directory Domain Servicesはマルチマスター方式です。書き込み可能な各DCは、ユーザーやコンピューターなどのディレクトリ変更を受け付け、変更内容を他のDCへレプリケーションします。このため、AWS Managed Microsoft ADの2台を一般的なアクティブ／スタンバイ構成として説明しない

AWSの公式ホワイトペーパーでも、AWS Managed Microsoft ADのすべてのDCは書き込み可能であり、DCとFSMOロールの割り当てはAWSが管理すると説明されている

出典：AWS公式ホワイトペーパー：FSMOロールと書き込み可能なドメインコントローラー

PDC Emulatorは「全体のメインDC」ではない

Active Directoryでは、競合を避ける必要がある一部の処理だけを1台が担当します。この役割をFSMO（Flexible Single Master Operations、操作マスター）と呼び、PDC EmulatorもFSMOの1つ

PDC Emulatorの主な役割 説明
パスワード変更の優先処理 最近変更されたパスワード情報を優先的に受け取り、別DCでパスワード不一致となった場合の照会先になる
アカウントロックアウト ロックアウト関連処理の中心的な役割を持つ
時刻同期 フォレストルートドメインのPDC Emulatorがドメイン階層の時刻基準になる
GPO編集 既定ではGPOの変更先としてPDC Emulatorが使用される

PDC Emulatorを保持するDCが1台存在しても、そのDCだけが認証、DNS、LDAP、Kerberosなどの通常処理を担当するわけではありません。もう1台も停止待機ではなく、通常時からサービスを提供するDC

AWS Managed Microsoft ADでは、DCのOS管理、FSMOロールの割り当て、障害時の復旧をAWSが管理します。お客様がPDC Emulatorを「主系」に指定したり、通常運用でFSMOロールを手動移行したりする構成ではない

出典：Microsoft公式：Windows Serverにおける操作マスター役割

クライアントはどちらのDCを利用するのか

WindowsのクライアントやActive Directory対応アプリケーションは、通常、次の流れでDCを選択する

  1. DCがDNSへ登録したLDAP、Kerberos、グローバルカタログ、サイトなどのSRVレコードを照会
  2. 候補DCへLDAP UDP pingを送信し、利用可能性を確認
  3. サイトとサブネットの情報がある場合は、同じサイトまたは最適なサイトのDCを優先
  4. 応答した適切なDCを利用し、選択結果を一定時間キャッシュ
  5. 選択中のDCが応答しなくなった場合は、別の利用可能なDCを再探索

したがって、毎回2台へ単純にラウンドロビンする動作でも、常に「DNSアドレスの1番目」だけを使用する動作でもありません。アプリケーションからDCのホスト名またはIPアドレスを固定せず、Windows DC Locatorを利用することが重要

出典：Microsoft公式：Active Directoryドメインコントローラーの検索

2台間でレプリケーションされるもの

代表的には、次の情報が2台のDC間でレプリケーションされる

  • ユーザー、グループ、コンピューターなどのActive Directoryオブジェクト
  • パスワードおよびグループメンバーシップなどの属性
  • Active Directory統合DNSゾーンの情報
  • グループポリシーのディレクトリ情報とSYSVOL上のファイル

片方のDCへ障害またはメンテナンスが発生した場合

項目 動作
クライアントの接続 選択中のDCが応答しなければ、DC Locatorにより別の利用可能なDCを再探索する
認証・名前解決 ネットワークからもう1台へ到達できれば、通常処理を継続できる構成となる
AWSのパッチ適用 AWSはDCを順番にパッチし、同時に必要な稼働DC数を失わないよう管理する
DC障害 AWSが同じAZ内で同じIPアドレスを使用して障害DCを自動的に置き換える
FSMO依存処理 PDC Emulatorなど特定ロールへ依存する一部処理では、一時的な遅延または制限が生じる可能性がある

「1台故障しても必ず無瞬断・無影響」とは説明しません。アプリケーション側のDNSキャッシュ、DC選択のキャッシュ、接続タイムアウト、ネットワーク到達性、FSMO依存処理によっては、一時的な遅延や再試行が発生する

出典：AWS公式：AWS Managed Microsoft ADの主要概念

お客様説明時の回答例

Q1. どちらがメインのドメインコントローラーですか

どちらか一方を通常処理のメインとして固定する構成ではありません。2台とも書き込み可能な稼働DCです。特定のDCがPDC EmulatorなどのFSMOロールを保持しますが、これは一部処理の役割分担であり、認証全体の主系という意味ではない

Q2. もう1台は待機系ですか

待機専用ではありません。通常時から認証、DNS、LDAP、Kerberos、グローバルカタログなどを提供し、もう1台とディレクトリ情報をレプリケーションしている

Q3. コンソールの2つのDNS IPはプライマリとセカンダリですか

2つのIPは、別々のAZに配置された2台のDC兼DNSサーバーのアドレスです。DNSクライアント側で表示順はありますが、Active DirectoryのDC選択はDNS SRVレコードとDC Locatorによって行われるため、1番目のIPが認証処理全体の主系という意味ではない

Q4. 片方が停止したら自動的に切り替わりますか

Windowsクライアントは、利用中のDCが応答しない場合に別の利用可能なDCを再探索します。AWSは障害DCを同じAZ・同じIPで自動置換します。ただし、キャッシュや接続タイムアウトにより一時的な遅延が生じる可能性があるため、無瞬断とは説明しない

Q5. 2台より増やせますか

増やせます。認証要求が多い場合や、可用性をさらに高めたい場合はAdditional DCを追加できます。追加したDCも、ディレクトリが使用する既存のAZとサブネットへ分散される

運用確認に使用できるコマンド

管理用EC2またはドメイン参加済み端末で、必要に応じて次を実行します。いずれも確認用の読み取り操作

powershell
## 現在のログオンで使用したDC
$env:LOGONSERVER

## ドメイン内で検出できるDC
nltest /dclist:ad.example.com

## DC LocatorによるDCの再検出

コマンド結果は確認時点の状態です。特定DCを通常接続先として固定する目的には使用しない

AWS Managed Microsoft AD構築手順と前提条件の確認

AWS Managed Microsoft ADで作成される内容

AWS Managed Microsoft ADを作成すると、AWSが高可用性に必要な基盤と、ディレクトリ管理に使用するActive Directoryオブジェクトを自動で構成する

AWSが構成する基盤

作成内容 役割・運用上の扱い
2台のドメインコントローラー 異なる2つのアベイラビリティーゾーンへ配置されます。主系／待機系ではなく、どちらも通常時から稼働する書き込み可能なドメインコントローラー
ENI 各ドメインコントローラーをVPCへ接続する
セキュリティグループ Active Directoryの通信に必要なルールが設定されます。初期状態では、作成先VPCのプライマリIPv4 CIDRからの通信が許可される
2つのDNS IPアドレス ドメイン参加、名前解決、認証およびグループポリシーの参照に使用します。クライアント側のDNS設定は、ディレクトリ作成後に別途行う
バックアップと暗号化 バックアップは1日1回自動実行され、ドメインコントローラーのAmazon EBSボリュームは暗号化される

Active Directory内に作成される管理領域

作成内容 役割・運用上の扱い
Adminユーザー ディレクトリ管理者として、NetBIOS名と同名のOU配下にあるUsersへ作成されます。本環境ではad\Users
AWS Delegated Groups OU ユーザーへ管理権限を委任するためのグループが格納されます。GPO管理や詳細なパスワードポリシー管理など、作業内容に対応する委任グループを使用する
AWS Reserved OU AWSが使用するサービス管理アカウントが格納されます。お客様が管理対象として使用する領域ではない
ad OU ディレクトリ作成時に指定したNetBIOS名に基づく管理用OUです。配下にComputersとUsersが作成され、お客様が管理するコンピューターとユーザーを配置する

AWSが作成して適用するGPO

GPO 主な適用対象・役割
Default Domain Policy ドメインへ適用され、パスワードとKerberosのポリシーを設定する
ServerAdmins ドメインコントローラー以外のコンピューターへ、委任されたサーバー管理者グループをローカル管理者として設定する
AWS Reserved Policy:User AWS Reserved OU内のユーザーへAWS推奨のセキュリティ設定を適用する
AWS Managed Active Directory Policy すべてのドメインコントローラーへAWS推奨のセキュリティ設定を適用する
TimePolicyNT5DS / TimePolicyPDC PDC Emulatorとそれ以外のドメインコントローラーに、それぞれ必要な時刻同期設定を適用する
Default Domain Controllers Policy 作成されますが、AWS Managed Microsoft ADでは代わりにAWS Managed Active Directory Policyが使用される

AWSが作成したGPOは、削除、編集または既存リンクの解除を行えません。お客様固有の設定は専用GPOとして作成し、お客様が管理するOUへリンクする

出典：AWS公式：AWS Managed Microsoft ADで作成される内容

概要

本手順書で実施すること

既存VPCad-vpc-002の異なるアベイラビリティーゾーンに配置されたプライベートサブネット（192.168.225.64/27・192.168.225.96/27）を使用し、ディレクトリDNS名ad.example.com、NetBIOS名ad、Standard EditionのAWS Managed Microsoft ADを1ディレクトリ作成する

作成後は、ディレクトリが「アクティブ」になったことと、AWSから割り当てられた2つのDNS IPアドレス、VPCおよびサブネットを確認する

完了条件

次の項目をすべて確認できた時点で、本作業を完了とする

  • ✔ ディレクトリのステータスが「アクティブ」である
  • ✔ DNS IPアドレスが2つ表示されている
  • ✔ 作成先VPCと2つのサブネットが構築条件と一致している

2台の役割、PDC Emulatorとの違い、クライアントによる接続先ドメインコントローラーの選択および障害時の動作は、AWS Managed Microsoft ADの2台ドメインコントローラー構成・役割を参照してください

前提条件

AWS Managed Microsoft ADのサービス要件

  • 同一のネットワークタイプで、異なるアベイラビリティーゾーンに配置された2つ以上のサブネットがある
  • VPCのハードウェアテナンシーが「デフォルト」である
  • VPCで198.18.0.0/15のアドレス空間を使用していない
  • 作業者のIAM IDにds:CreateMicrosoftADと、VPC・サブネットの参照、セキュリティグループおよびENIの作成に必要なEC2権限が付与されている

本環境の構築条件

  • ✔ 操作リージョンがアジアパシフィック（東京）ap-northeast-1である
  • ✔ VPCad-vpc-002のステータスが「利用可能」である
  • ✔ VPCのDNS解決とDNSホスト名が有効である
  • ✔ 次の2つのプライベートサブネットが利用可能である
用途 サブネット名 CIDR アベイラビリティーゾーン
Directory Service用（1台目） ad-pri-sub-002-002a 192.168.225.64/27 ap-northeast-1a
Directory Service用（2台目） ad-pri-sub-002-002c 192.168.225.96/27 ap-northeast-1c
  • ✔ Adminユーザーに設定するパスワードを準備している

警告：Adminパスワードを作業記録や画面キャプチャへ残さない

Adminパスワードは、手順書、チケット、作業ログおよび画面キャプチャへ記録しません。AWSコンソールで入力したパスワードは再表示できない

IAM権限

IAM権限とActive Directory内のグループ権限は別物である。AWSマネジメントコンソールを操作できても、Active Directoryの管理権限が自動的に付与されることはない。逆も同様である

日常運用へAWSDirectoryServiceDataFullAccessを一律に付与せず、対象Directory ARNへ必要なアクションだけを許可する

役割 主なアクション例
機能の状態確認 ds:DescribeDirectories、ds:DescribeDirectoryDataAccess
機能の有効化 上記に加えてds:EnableDirectoryDataAccess
機能の無効化 必要時のみds:DisableDirectoryDataAccess
ユーザー参照・作成 ds:AccessDSData、ds-data:ListUsers、ds-data:DescribeUser、ds-data:CreateUser
グループ参照・メンバー操作 ds:AccessDSData、ds-data:ListGroups、ds-data:DescribeGroup、ds-data:ListGroupMembers、ds-data:AddGroupMember、ds-data:RemoveGroupMember
ユーザー削除 ds:AccessDSData、参照系アクション、ds-data:DeleteUser

削除権限は、参照・作成・メンバー操作の担当権限から分離することを推奨する

AWS Managed Microsoft ADの管理上の注意

AdminとAdministrator

項目 Admin Administrator
管理主体 お客様 AWS
用途 お客様用OUとAWSから委任された範囲の管理 AWSによるディレクトリ運用
Domain Admins / Enterprise Admins メンバーではない AWSが排他的に管理する組み込み高特権アカウント
お客様による利用 初期設定・緊急時。日常運用は個人識別できる管理ユーザーを推奨 利用・変更しない

Adminのパスワードは後から取得できない。リセットを行う場合は、対象アカウントが無効化されていたときに再び有効となる仕様があるため、リセット後にアカウント状態を確認する

AWSが管理するオブジェクト

  • AWS Reserved OU内のAWS_で始まるサービス管理アカウントは変更しない
  • AWSが管理する組み込みアカウントのAdministratorとKerberosで使用するkrbtgtは変更しない
  • AWS Delegated GroupsはOU名であり、その配下に用途別のAWS Delegated ...グループがある
  • AWS Delegated Administratorsは非常に強い委任管理権限を持つ。一般ユーザーへ付与しない
  • AWS Delegated FSx AdministratorsはFSx管理用の高権限グループである。FSx管理担当者以外へ付与しない
  • 既存のグループの入れ子関係は、ユーザー追加・削除作業と分けて管理する。図10に表示される既存のAWS Delegated Administratorsグループは、本作業で変更しない
  • 既定オブジェクトとして確認できない環境固有グループは、所有者と用途が確定するまで変更しない

パスワードポリシー

AWS Managed Microsoft ADのDefault Domain Policyには次の値が設定され、PSOが割り当てられていないユーザーへ適用される。AWSが作成したDefault Domain Policyは編集、削除または既存リンクの解除を行わない

項目 AWS既定値
パスワード履歴 24個
最長有効期間 42日（Adminを含む）
最短有効期間 1日
最小長 7文字
複雑さ 有効
可逆暗号化による保存 無効

本番環境で異なるポリシーが必要な場合は、Active Directory管理センター（ADAC）のSystem\Password Settings Containerに用意されているCustomerPSO-01～CustomerPSO-05を編集し、ユーザーまたはセキュリティグループへ割り当てる

PSO 変更できない優先順位値
CustomerPSO-01 10
CustomerPSO-02 20
CustomerPSO-03 30
CustomerPSO-04 40
CustomerPSO-05 50

優先順位値が小さいPSOほど優先されます。個人へ直接割り当てたPSOはグループ経由のPSOより優先されるため、通常は承認済みのセキュリティグループ単位で割り当てる

PSOを設定して適用する
  1. 操作ユーザーがAWS Delegated Fine Grained Password Policy Administratorsのメンバーであることを確認
  2. ドメイン参加済みの管理用EC2でADACを起動
  3. ツリービューへ切り替え、System\Password Settings Containerを開く
  4. 使用するCustomerPSO-01～CustomerPSO-05を開き、承認されたパスワード履歴、長さ、有効期間、複雑さおよびロックアウト値を設定します。優先順位値は変更できない
  5. 「直接の適用先」へ承認されたユーザーまたはセキュリティグループを追加
  6. レプリケーション後、対象ユーザーの実効ポリシーをPowerShellで確認
powershell
Get-ADUserResultantPasswordPolicy -Identity '<ユーザー名>'
  • ✔ 想定したCustomerPSO-0xが返される
  • ✔ PSOを割り当てないユーザーではDefault Domain Policyが適用される
  • ✔ 実効ポリシーの確認にnet userを使用していない

管理者によるパスワードのリセットでは、パスワード履歴と最短有効期間が適用されません。また、最小長や複雑さなどの新しい品質要件は、通常、次回のパスワード変更時に評価される
