AWS Managed Microsoft ADは、異なるアベイラビリティーゾーンへ2台の書き込み可能なドメインコントローラーを配置する

2台とも通常時から認証、DNS、Kerberos、LDAP、グループポリシーを提供するため、主系／待機系の構成として扱わない

ドメインコントローラーの構成

ディレクトリ作成時の2台は、可用性を確保するために削除できない Required DC として異なるアベイラビリティーゾーンへ配置される

可用性、耐障害性または認証処理性能をさらに高める場合は Additional DC を追加できる

AWSコンソール上の区分 仕様 削除・縮退
Required DC ディレクトリ作成時にAWSが作成する初期2台 2台未満にはできない
Additional DC 必要に応じて追加する書き込み可能なDC 合計2台を下限として削減可能

AWS公式資料で初期2台を「primary and secondary domain controllers」と表現する場合がありますが、Active Directoryの処理方式が主系／待機系であることを示すものではない

本資料では、誤解を避けるため Required DC-1／Required DC-2 と表記する

処理方式とPDC Emulator

AWS Managed Microsoft ADはマルチマスター方式で動作し、すべてのDCが書き込み可能です。ユーザーやコンピューターなどの変更は、DC間で相互にレプリケーションされる

FSMOロールは競合を避ける必要がある一部処理を1台へ割り当てる仕組みです。PDC Emulatorを保持するDCが認証全体の主系になるわけではない

PDC Emulatorの主な役割 仕様
パスワード変更 最近変更されたパスワード情報を優先的にレプリケーションし、別DCで不一致となった場合の照会先になる
アカウントロックアウト ロックアウト関連処理の中心的な役割を持つ
時刻同期 フォレストルートドメインの時刻基準になる
GPO編集 既定のGPO変更先として使用される

DCのOS管理、FSMOロールの割り当ておよび障害時の復旧はAWSが管理するため、お客様がPDC Emulatorを主系として指定したり、通常運用でFSMOロールを移行したりしない

クライアントによるDCの選択

WindowsクライアントやActive Directory対応アプリケーションは、次の流れで接続先DCを選択する

  1. DNSに登録されたLDAP、Kerberos、グローバルカタログおよびサイトのSRVレコードを照会
  2. 候補DCの応答とサイト／サブネット情報を基に、利用可能なDCを選択
  3. 選択結果を一定時間キャッシュし、応答しない場合は別のDCを再探索

毎回2台へ単純にラウンドロビンする動作でも、DNSアドレスの1番目だけを常に使用する動作でもない

アプリケーションから特定DCのホスト名やIPアドレスを固定せず、Windows DC Locatorを利用する

WindowsおよびWindows Serverでドメインコントローラーを検索するクライアントがDNS、LDAP pingおよびサイト情報を使用して適切なドメインコントローラーを検出する流れを説明します。Microsoft LearnMicrosoft Learn

レプリケーションと障害時の動作

DC間では、Active Directoryオブジェクト、パスワードやグループメンバーシップ、Active Directory統合DNS、GPOおよびSYSVOL上のファイルをレプリケーションする

項目 仕様
クライアント接続 選択中のDCが応答しない場合、DC Locatorが別の利用可能なDCを再探索する
認証・名前解決 ネットワークからもう1台へ到達できる場合、通常処理を継続できる構成となる
AWSのメンテナンス 必要な稼働DC数を同時に失わないよう、DCのパッチ適用をAWSが管理する
DC障害 AWSが障害DCを同じアベイラビリティーゾーン内で同じIPアドレスを使用して自動的に置き換える
FSMO依存処理 特定ロールへ依存する一部処理では、一時的な遅延または制限が生じる可能性がある

アプリケーション側のDNSキャッシュ、DC選択のキャッシュ、接続タイムアウト、ネットワーク到達性によっては、一時的な遅延や再試行が発生するため、1台の障害時も必ず無瞬断・無影響とは限らない

AWS Managed Microsoft ADのベストプラクティス

お客様説明時の回答例

Q1. どちらがメインのドメインコントローラーですか

どちらか一方を通常処理のメインとして固定する構成ではありません。2台とも書き込み可能な稼働DCです。特定のDCがPDC EmulatorなどのFSMOロールを保持しますが、これは一部処理の役割分担です。認証全体の主系という意味ではありません。

Q2. もう1台は待機系ですか

待機専用ではありません。通常時から認証、DNS、LDAP、Kerberos、グローバルカタログなどを提供し、もう1台とディレクトリ情報をレプリケーションしています。

Q3. コンソールの2つのDNS IPはプライマリとセカンダリですか

2つのIPは、別々のAZに配置された2台のDC兼DNSサーバーのアドレスです。DNSクライアント側で表示順はありますが、Active DirectoryのDC選択はDNS SRVレコードとDC Locatorによって行われるため、1番目のIPが認証処理全体の主系という意味ではありません。

Q4. 片方が停止したら自動的に切り替わりますか

Windowsクライアントは、利用中のDCが応答しない場合に別の利用可能なDCを再探索します。AWSは障害DCを同じAZ・同じIPで自動置換します。ただし、キャッシュや接続タイムアウトにより一時的な遅延が生じる可能性があるため、無瞬断とは説明しません。

Q5. 2台より増やせますか

増やせます。認証要求が多い場合や、可用性をさらに高めたい場合はAdditional DCを追加できます。追加したDCも、ディレクトリが使用する既存のAZとサブネットへ分散されます。

運用確認に使用できるコマンド

管理用EC2またはドメイン参加済み端末で、必要に応じて次を実行します。いずれも確認用の読み取り操作です。

PowerShell
## 現在のログオンで使用したDC
$env:LOGONSERVER

## ドメイン内で検出できるDC
nltest /dclist:ad.example.com

## DC LocatorによるDCの再検出
nltest /dsgetdc:ad.example.com /force

## DC、IP、サイト、Global Catalogの確認
Get-ADDomainController -Filter * |
    Select-Object HostName, IPv4Address, Site, IsGlobalCatalog

## 現在のFSMOロール保持先
Get-ADDomain |
    Select-Object PDCEmulator, RIDMaster, InfrastructureMaster

コマンド結果は確認時点の状態です。特定DCを通常接続先として固定する目的には使用しません。

管理範囲

Active Directory内に作成される管理領域

作成内容 役割・運用上の扱い

ℹ️ 情報：IAMとActive DirectoryのAdminの違い

AWSの構築・設定操作に使用するIAMユーザー／IAMロールと、Active Directoryの管理に使用するAdminは、別のID・権限として管理します。Adminを作成しても、AWSリソースへのアクセス権は自動で付与されません。

構築作業

1. Directory Serviceのセットアップを開始する

  1. AWSマネジメントコンソールへサインインします。
  2. 画面右上で、リージョンが「アジアパシフィック（東京）」になっていることを確認します。
  3. サービス検索から「Directory Service」を開きます。
  4. 「ディレクトリのセットアップ」で「AWS Managed Microsoft AD」を選択します。
  5. 「ディレクトリのセットアップ」を選択します。

2. ディレクトリタイプを選択する

  1. 「ディレクトリタイプ」で「AWS Managed Microsoft AD」を選択します。
  2. 「AWS Managed Microsoft ADの使用を開始する」で「AWS managed ADドメインを新規作成」を選択します。
  3. 「次へ」を選択します。

本環境ではAWS Managed Microsoft ADを新規作成するため、「既存のADドメインをハイブリッドディレクトリで拡張・新規」は選択しません。

3. ディレクトリ情報を入力する

DNS名はActive Directoryで使用する完全修飾ドメイン名です。NetBIOS名はドメインの短縮名として使用します。

⚠️ 注意：ディレクトリのDNS名を既存のDNS名前空間と重複させない

同じ名前のAmazon Route 53プライベートホストゾーンなどが存在すると、クライアントの名前解決に影響する可能性があります。入力前に既存のDNS名前空間と重複していないことを確認します。

「ディレクトリ情報を入力」画面では、次の設定値を使用します。

項目 設定値
ディレクトリのタイプ Microsoft AD
エディション Standard Edition
ディレクトリのDNS名 ad.example.com
ディレクトリのNetBIOS名 ad
ディレクトリの説明 未入力
  1. エディションで「Standard Edition」を選択します。
  2. ディレクトリのDNS名にad.example.comを入力します。
  3. ディレクトリのNetBIOS名にadを入力します。
  4. ディレクトリの説明は未入力とします。
  5. 続けて、次の「Adminパスワードを入力する」でパスワードを設定します。

ℹ️ 情報：クライアントのDNS設定は後続手順で実施する

ディレクトリを作成しただけでは、VPC内のクライアントが自動的にDirectory ServiceのDNS IPアドレスを使用する状態にはなりません。管理用EC2などの名前解決に必要なDHCPオプションセットまたはクライアントDNS設定は、後続手順で実施します。

4. Adminパスワードを入力する

  1. 「Adminパスワード」に、準備したパスワードを入力します。
  2. 「パスワードを確認」に、同じパスワードを再入力します。
  3. 次のパスワード要件を満たしていることを確認します。
    • 文字数：8文字以上64文字以下
    • 小文字、大文字、数字、英数字以外の文字の4分類のうち、3分類以上を含む
    • adminという単語を含まない

仕様

構成・動作

AWS Directory Service Dataは、AWS Managed Microsoft ADのユーザー、グループおよびグループメンバーシップを管理する機能です。「ユーザーとグループの管理」を有効化すると、AWSマネジメントコンソールから対応する操作を実施できます。

操作 動作・運用上の扱い
管理機能の有効化 対象ディレクトリで行う初期設定です。有効になっている場合は、作業のたびに有効化し直す必要はありません。
ユーザーの作成 ログイン名、初期パスワード、氏名などを設定してユーザーアカウントを作成します。作成時に既存グループへ追加できます。
グループへの追加 ユーザーは追加先グループに割り当てられた役割・権限を継承します。
グループからの削除 指定したグループのメンバーシップを削除します。ユーザーアカウント自体は残ります。
ユーザーアカウントの削除 ユーザーアカウント自体を削除します。グループメンバーシップの削除とは操作対象が異なります。

ユーザーへ直接割り当てたPSOは、グループ経由のPSOより優先されます。同じ適用区分で複数のPSOが該当する場合は、優先順位値が小さいPSOが優先されます。運用では、管理対象に応じたセキュリティグループ単位での割り当てを基本とします。

ℹ️ 情報：グループから削除してもユーザーアカウントは残る

この操作で削除する対象は、指定グループのメンバーシップです。ユーザーアカウント自体や、他のグループへの所属は残ります。

  1. 対象ディレクトリの「グループ」タブで、AWS Delegated Administratorsを開きます。
  2. 「メンバー」タブで、ログイン名がsampleadmin、メンバータイプが「ユーザー」の行を確認します。
  3. sampleadminだけを選択し、削除元グループ名とユーザーログイン名を再確認します。

⚠️ 注意：削除を選択する前にグループとユーザーを再確認する

本手順の掲載画面では、「削除」を選択した後に確認ダイアログは表示されず、メンバーシップの削除が実行されます。対象グループがAWS Delegated Administrators、対象ユーザーがsampleadminと一致していることを確認してから操作します。

  1. 対象に誤りがなければ、「削除」を選択します。
  2. 削除成功メッセージを確認し、メンバー一覧からsampleadminが消え、その他のユーザーや子グループが残っていることを確認します。
  1. 「ユーザー」タブでsampleadminを検索し、ユーザーアカウント自体が残っていることを確認します。

誤って削除した場合は作業依頼を確認し、削除元のグループへ対象ユーザーを再追加します。前の手順の操作方法を参照し、グループ名とユーザー名は実際に誤削除した対象へ置き換えます。グループから継承した権限の変更は、関連サービスでの再サインイン後に確認が必要になる場合があります。

4. ユーザーアカウントを削除する

項目 設定値
削除するユーザー samplework
表示名 sample work

削除前に、ログイン名、表示名、氏名、アカウントの状態および最終利用状況を作業依頼と照合します。WorkSpaces、FSx、共有フォルダー、バッチやサービスアカウントなどで使用されていないことを確認し、削除対象ユーザーのSIDと全グループメンバーシップを記録して保管します。

⚠️ 注意：ユーザーアカウントの削除はアクセス権にも影響する

この操作は、ユーザーアカウント自体を削除します。削除前の無効化期間やデータ引継ぎなど、必要な対応が完了していることを確認します。同じログイン名で新規作成してもSIDが変わるため、以前のアクセス権は自動では復旧しません。

セキュリティ識別子（SID）

  1. 対象ディレクトリの「ユーザー」タブを開きます。
  2. sampleworkを検索し、削除対象ユーザーだけを選択します。
  1. 「アクション」から「ユーザーアカウントを削除」を選択します。
  1. 確認ダイアログのユーザーログイン名sampleworkと表示名sample workを照合します。
  2. 対象ユーザーの情報と、アクセスに必要な情報が削除される旨を確認します。
  3. 対象に誤りがなければ、「ユーザーアカウントを削除」を選択します。
  1. 削除成功メッセージを確認します。
  2. 「ユーザー」タブでsampleworkを検索し、一覧に表示されず、対象外のユーザーが残っていることを確認します。

一覧への反映が遅れている場合は、画面を更新して待機します。状態を確認するまで、削除操作を繰り返しません。

❌ エラー：誤ったユーザーを削除した場合

追加の変更を停止し、対象ユーザーと影響範囲を確認します。復旧手順が整備されている場合は、ドメイン参加済みの管理用端末からActive Directory Recycle Binによる復元を検討します。ディレクトリのスナップショット復元はディレクトリ全体へ影響するため、単一ユーザーの通常復旧として実施しません。

5. パスワードポリシーを設定する（必要時）

この操作は、ドメイン既定のパスワードポリシーとは異なる設定が必要な場合に実施します。掲載画像のユーザー作成・グループ操作に必須の作業ではありません。

  1. ドメイン参加済みの管理用EC2へ、必要なAD管理権限を持つユーザーでサインインします。
  2. AD管理ツールが未導入の場合は、管理者権限のPowerShellで次のコマンドを実行します。
PowerShell
Install-WindowsFeature RSAT-ADDS

Active Directory管理ツールのインストール

DNS管理も行う場合は、サーバーマネージャーでDNS Server Toolsを追加します。

  1. 操作ユーザーがAWS Delegated Fine Grained Password Policy Administratorsのメンバーになっていることを確認します。
  2. ADACを起動してツリービューへ切り替え、System\Password Settings Containerを開きます。
  3. 使用するCustomerPSO-01～CustomerPSO-05を開きます。
  4. 承認されたパスワード履歴、長さ、有効期間、複雑さおよびロックアウト値を設定します。優先順位値は変更できません。
  5. 「直接の適用先」へ対象ユーザーまたはセキュリティグループを追加し、変更を保存します。
  6. レプリケーション後、「作業後確認」の手順で対象ユーザーの実効ポリシーを確認します。

パスワードポリシーの割り当てと確認／パスワードポリシー管理権限の委任

作業後確認

ユーザーとグループの状態を確認する

作業依頼で指定された操作の結果を確認します。本手順の掲載例を順に実施した場合は、次の最終状態を確認します。

  1. ディレクトリの詳細で、「ユーザーとグループの管理」が「有効」になっていることを確認します。
  2. 「ユーザー」タブでsampleadminが「有効」と表示されることを確認します。
  3. AWS Delegated FSx Administratorsのメンバーに、Adminとsampleadminが表示されることを確認します。
  4. AWS Delegated Administratorsのメンバーにsampleadminが表示されず、既存の対象外メンバーが残っていることを確認します。
  5. 「ユーザー」タブでsampleworkを検索し、一覧に表示されないことを確認します。

パスワードポリシーの適用結果を確認する（変更時のみ）

  1. 管理用EC2のPowerShellで、対象ユーザーの実効PSOを確認します。<ユーザー名>は確認対象のログイン名へ置き換えます。
PowerShell
Get-ADUserResultantPasswordPolicy -Identity '<ユーザー名>'
  1. 想定したCustomerPSO-0xと設定値が返されることを確認します。
  2. PSOを割り当てていないユーザーについてドメイン既定値を確認する場合は、次のコマンドを使用します。
PowerShell
Get-ADDefaultDomainPasswordPolicy -Identity 'ad.example.com'

Get-ADUserResultantPasswordPolicyは、Default Domain Policy自体の内容を表示するコマンドではありません。実効ポリシーの確認にnet userは使用しません。

パスワードポリシーの割り当てと確認／Get-ADDefaultDomainPasswordPolicy
