AWS Managed Microsoft AD・WorkSpaces OU／GPO構成概要

目次

概要

AWS Managed Microsoft ADを作成した直後のOU／GPOと、本作業で追加したAmazon WorkSpaces用OU／GPOを整理します。AWSが管理する領域は変更せず、お客様管理OUであるad配下にWorkSpaces OUを作成し、AD Connectorの権限委任、ターゲットOUおよびDCV用GPOの適用先を同じOUへ揃える

本手順書で確認すること

  • AWS Managed Microsoft ADが自動作成する管理領域とGPO
  • お客様が管理できるad、ComputersおよびUsers OUの役割
  • 今回追加したWorkSpaces OU、委任先グループおよびGPOの関係
  • 新規WorkSpaceへ反映されるOU／GPOと、既存WorkSpaceへの影響

完了条件

  • ✔ AWS管理領域とお客様管理領域を区別できる
  • ✔ WorkSpacesのコンピューター格納先がad\Computers\WorkSpacesである
  • ✔ ターゲットOUとConnectorsグループへの委任先が同じOUである
  • ✔ Amazon WorkSpaces DCV PolicyがWorkSpaces OUへ直接リンクされている

WorkSpacesコンピューター格納先 ad\Computers\WorkSpaces

GPMCで確認するManaged AD初期構成とWorkSpaces追加項目

AWS Managed Microsoft ADを作成すると、ドメインルートにAWS Delegated Groups、AWS ReservedおよびNetBIOS名と同名のOU（本環境ではad）が作成されます。ad配下には、お客様が管理するComputers OUとUsers OUが作成され、初期Adminユーザーはad\Usersに配置される

ドメイン直下には、Builtin、組み込みのComputersコンテナー、Domain ControllersなどWindows Active Directory標準のコンテナーも表示されます。ドメイン直下のComputersコンテナーと、お客様管理領域のad\Computers OUは別の場所

同時に、Default Domain Policy、ServerAdmins、AWS Reserved Policy:User、AWS Managed Active Directory Policyおよび時刻同期用GPOなどが作成・リンクされます。AWSが作成・管理するOUやGPOは、お客様が変更、削除またはリンク解除する対象にしない

出典：AWS公式：AWS Managed Microsoft ADで作成される内容

次の図では、GPMCの実画面を基に、①ルートドメイン、②お客様管理OUのad、③ad配下のComputersとUsers、④AWSが作成するGPOの役割と管理範囲を示します。画面内のWorkSpaces OUとAmazon WorkSpaces DCV Policyは今回追加した項目であり、ディレクトリ作成直後の既定項目ではありません。したがって、この図は「初期構成だけ」を表すものではなく、初期項目と今回の追加項目を同じ管理ツリー上で区別するための図

今回追加したWorkSpaces用構成

ad\Computers配下へWorkSpaces OUを作成し、AD Connectorが使用するConnectorsグループへ、同OU内のコンピューターオブジェクトを作成、削除、読み取りおよび書き込みする権限を委任します。サービスアカウントとグループはad\Usersに配置したまま、権限だけをWorkSpaces OUへ委任する

Amazon WorkSpacesのターゲットOUを同じOUへ設定し、Amazon WorkSpaces DCV Policyを直接リンクします。既定GPOの継承は維持され、その上にWorkSpaces固有設定が適用される。Windows WorkSpacesで使用できる管理テンプレートと設定項目は出典：AWS公式：WorkSpaces PersonalでWindows WorkSpacesを管理する

ターゲットOUを変更しても、作成済みWorkSpaceのコンピューターオブジェクトは自動移動されません。変更後に新規作成または再構築したWorkSpaceへ反映される

Amazon WorkSpaces作成・バンドル設定手順

概要

本手順書で実施すること

VPC003～VPC006に作成したAD ConnectorをWorkSpaces Personalへ登録し、各VPCのWorkSpaces用プライベートサブネットを2つ指定します。その後、PowerPro with Windows 10 (Server 2022 based)、DCV（旧WSP）、ルート80GB、ユーザー50GBのWindows WorkSpaceをユーザー単位で作成し、AVAILABLE、Active Directory上のOU所属およびクライアント接続を確認する

本書の操作を対象AD Connectorごとに繰り返します。カスタムイメージとカスタムバンドルを使用する場合は、Amazon WorkSpacesカスタムイメージ・バンドル作成・共有手順を先に完了する

完了条件

  • ✔ 対象AD ConnectorがWorkSpaces Personalへ登録されている
  • ✔ 対象VPCの異なるアベイラビリティーゾーンにある2サブネットを選択している
  • ✔ Directory ID、ユーザー、バンドル、DCV、実行モード、80GB／50GBおよび暗号化設定が承認済み値と一致している
  • ✔ WorkSpaceがAVAILABLEとなり、対象OUへコンピューターオブジェクトが作成されている
  • ✔ WorkSpacesクライアントからドメインユーザーで接続できる

WorkSpacesとバンドル

  • パブリックバンドル：AWSが提供するOS、コンピューティング、ストレージおよびプロトコルの組み合わせ
  • カスタムイメージ：参照WorkSpaceのOS、アプリケーションおよび設定を取り込んだイメージ
  • カスタムバンドル：カスタムイメージへコンピューティングタイプとストレージ設定を組み合わせた起動テンプレート

今回の画面では、PowerPro with Windows 10 (Server 2022 based)を選択しています。表示名に「Windows 10」が含まれますが、括弧内のServer 2022 basedを含む正式名称で記録する

前提条件

  • ✔ 対象リージョンがアジアパシフィック（東京）である
  • ✔ VPCピアリング、両方向のルート、ネットワークACLおよびDC用SGの許可が設定済みである
  • ✔ 対象VPCのAD Connectorが「アクティブ」で、ユーザー検索が成功する
  • ✔ AD Connectorの2つのサブネットから、両方のDNSサーバー／ドメインコントローラーへ到達できる
  • ✔ ADConnectorServiceが有効・未ロックで、AD Connectorへ登録したパスワードと一致する
  • ✔ ConnectorsへWorkSpaces OU内のコンピューター作成・削除・読み取り・書き込みを委任している
  • ✔ WorkSpacesのターゲットOUがad\Computers\WorkSpacesである
  • ✔ 利用ユーザーがActive Directoryにあり、同じディレクトリでPersonal WorkSpaceを重複作成しない
  • ✔ Service Quotasと各サブネットの空きIPアドレスに余裕がある
  • ✔ 実行モード、暗号化、KMSキー、タグ、セルフサービス権限およびインターネット接続方式が承認済みである

注意：Directory IDは現行コンソールで照合する

Directory IDは、ドメイン名、VPC、ディレクトリタイプおよび状態と合わせて現行AWSコンソールで確認する。別VPCのAD Connectorや過去資料のIDを流用しない

AD Connectorの登録

AWS Directory ServiceでAD Connectorを作成しただけではWorkSpacesで使用できません。対象AD ConnectorをWorkSpaces Personalへ登録し、WorkSpacesを起動する2サブネットを指定する

登録前の確認

  1. Amazon WorkSpacesコンソールを開き、「ディレクトリ」を選択
  2. WorkSpacesタイプが「個人」であることを確認
  3. 対象AD Connectorが登録済み一覧にないことを確認
  4. 「ディレクトリの作成」を選択

図1では、①登録済みディレクトリの一覧、②「ディレクトリの作成」を確認する

ディレクトリを登録する

  1. WorkSpacesタイプで「個人」を選択
  2. WorkSpaceデバイス管理で「AWS Directory Service」を選択
  3. Directory ID、タイプ、ドメイン、VPCおよび状態を照合して対象AD Connectorを選択
  4. 対象VPCのWorkSpaces用サブネットを異なるアベイラビリティーゾーンから2つ選択
  5. セルフサービスアクセス許可を承認済み設計に合わせます。有効にすると、利用者が再構築、コンピューティングタイプ、ボリュームおよび実行モードなどを変更でき、料金へ影響する場合がある
  6. 「登録」を選択し、REGISTERINGから登録済みへ変わるまで待機
  7. 登録後のDirectory ID、AD Connector、VPC、ドメインおよび2サブネットを確認

図2では、赤枠の状態が「登録済み」であることを確認する

AWSが作成した<Directory ID>_workspacesMembers形式のセキュリティグループを確認し、既存ルールを根拠なく削除または置換しない

ターゲットOUの確認

  1. WorkSpacesコンソールの「ディレクトリ」で対象AD Connectorを選択
  2. 「ターゲットドメインと組織単位」を開く
  3. Amazon WorkSpaces用OU作成・権限委任・ターゲットOU設定手順で設定したDNと一致することを確認
  4. Connectorsへの委任先OUとも一致することを確認

WorkSpaces専用OUやお客様作成GPOは、WorkSpace作成時に自動作成されません。GPOはGPMCで対象OUへリンクする

WorkSpaceの作成

出典：AWS公式：WorkSpaces PersonalのWorkSpaceを作成する

作成を開始する

  1. WorkSpacesコンソールで「WorkSpaces」を選択
  2. 「WorkSpacesを起動」から「個人」を選択
  3. 「WorkSpacesの作成」を選択

図3では、①「個人」、②「WorkSpacesの作成」を選択する

バンドル、ディレクトリおよびユーザーを指定する

  1. 「手動で設定」を選択
  2. 「WorkSpacesバンドルを使用」を選択
  3. 正式名称、Bundle ID、OS、プロトコルおよびコンピューティングタイプを確認して、承認済みバンドルを選択
  4. 実行モードを選択し、AutoStopの場合は停止までの時間を指定
  5. Directory ID、ドメインおよびVPCを照合して登録済みAD Connectorを選択
  6. 申請されたドメインユーザーを選択
  7. ルート80GB、ユーザー50GBを指定
  8. ルート／ユーザーボリュームの暗号化とKMSキーを承認済み設計に合わせる
  9. 必須タグ、ローカル管理者権限、追加SG、インターネット接続およびデバイスアクセス制御を確認

図4では、①手動設定、②WorkSpacesバンドル、③バンドル、④実行モード、⑤停止時間、⑥ディレクトリ、⑦ユーザー、⑧80GB／50GB、⑨暗号化設定を確認する

選択したバンドルの詳細で、バンドルID、言語、OS、プロトコルおよびハードウェアを確認する

図5のパブリックバンドル詳細にはルート175GB／ユーザー100GBが表示されます。今回のWorkSpace作成ではカスタマイズ欄で80GB／50GBを選択します。バンドル詳細の既定表示と、作成時に確定したストレージを混同しない

注意：ストレージと暗号化は作成前に確定する

WorkSpace作成後、ボリュームは拡張できますが縮小できません。暗号化なしで作成したWorkSpaceへ後から暗号化を追加すること、暗号化済みWorkSpaceから暗号化を解除することもできません。誤った場合は利用者影響とデータ退避を確認して再作成する

作成を実行する

  1. バンドル、Directory ID、ユーザー、実行モード、ストレージ、暗号化、KMSキーおよびタグを最終確認
  2. 「WorkSpacesの作成」を選択
  3. 一覧で状態が「構築中」またはPENDINGになったことを確認
  1. 状態が「使用可能」またはAVAILABLEになるまで待機
  2. WorkSpace ID、ユーザー、コンピューター名、バンドル、80GB／50GB、実行モード、DCV、IPアドレスおよび暗号化状態を確認

作成後の確認

Active Directory

  1. ADUCでad\Computers\WorkSpacesを開き、新しいコンピューターオブジェクトを確認
  2. コンピューター名がWorkSpacesコンソールの値と一致することを確認
  3. gpresult /scope computer /rを実行し、Amazon WorkSpaces DCV Policyが適用されていることを確認

クライアント接続

  1. WorkSpacesクライアントをインストール
  2. 対象ディレクトリの登録コードを入力
  3. Active Directoryのユーザー名とパスワードでサインイン
  4. デスクトップ、業務ネットワーク、DNS、時刻同期および必要アプリケーションを確認
  5. AutoStopを使用する場合は、切断、停止および再接続を確認

よくある問い合わせと切り分け

次の5件は、AD ConnectorでWorkSpacesを使用する際に問い合わせが多い内容

出典：AWS公式：WorkSpaces Personalに関する問題のトラブルシューティング

招待メールまたはパスワードリセットメールが届かない

AD Connector、信頼されたドメイン、またはActive Directoryに既に存在するユーザーを使用する場合、ウェルカムメールやパスワードリセットメールは自動送信されません。管理者が登録コード、クライアントの入手先および接続方法を安全な経路で案内し、パスワードリセットはActive Directory管理者が実施する

「パスワードを忘れた場合」が表示されない

AD Connectorまたは信頼されたドメインのユーザーは、WorkSpacesクライアントからパスワードをセルフリセットできません。Active Directory側で本人確認とパスワードリセットを行い、「次回ログオン時にパスワード変更が必要」を有効にした場合のWorkSpaces接続可否も運用手順に従って確認する

DNS unavailable

AD Connectorから指定DNSサーバーのTCP 53とUDP 53へ通信できない場合に発生します。AD Connectorの両サブネットから両DNS IPへのルート、セキュリティグループ、ネットワークACLおよびDNSサーバー側ファイアウォールを確認する

Connectivity issues detected

LDAP unavailable (TCP port 389)またはKerberos/authentication unavailable (TCP port 88)が表示された場合は、AD ConnectorからドメインコントローラーへのTCP／UDP 88（Kerberos）とTCP／UDP 389（LDAP）を確認する。片方のドメインコントローラーだけでなく、両方へ到達できることを確認する

SRV record

AD Connectorは、指定DNSサーバーから_ldap._tcp.<DNSドメイン名>と_kerberos._tcp.<DNSドメイン名>のSRVレコードを取得する必要があります。次のコマンドで両レコードを確認し、対象ドメインコントローラーが返ることを確認する

powershell
Resolve-DnsName -Type SRV '_ldap._tcp.ad.example.com'
Resolve-DnsName -Type SRV '_kerberos._tcp.ad.example.com'

最後の3件はAD Connectorの作成・接続診断でも発生します。WorkSpace作成を繰り返す前に、AD Connector側のネットワークとDNSを解消する

作成に失敗した場合

  1. AD ConnectorとWorkSpacesへのディレクトリ登録が正常か確認
  2. 両サブネットから両DNSサーバー／ドメインコントローラーへ到達できることを確認
  3. サブネットの空きIP、2つのAZ、往復ルート、SGおよびネットワークACLを確認
  4. ADConnectorServiceの有効化、ロック、パスワード期限およびAD Connectorに保存した認証情報を確認
  5. ConnectorsのOU委任とWorkSpacesのターゲットOUが一致することを確認
  6. 対象ユーザー、重複WorkSpace、Service QuotasおよびKMSキー権限を確認
  7. WorkSpacesのエラーメッセージ、CloudTrailおよびAWS Health Dashboardを確認

AWS公式は、接続したディレクトリでWorkSpaceの起動が繰り返し失敗する場合、AD Connector指定時の両DNSサーバー／ドメインコントローラーへ各ディレクトリサブネットから到達できることを確認するよう案内しています。必要に応じて各サブネットへ検証用EC2を起動し、両DNS IPを使ったドメイン参加で切り分ける

誤作成時の対応

  1. 対象WorkSpaceのID、ユーザー、Directory IDおよび誤設定内容を照合
  2. 利用者へ登録コードを案内せず、必要なデータがないことを確認
  3. 対象WorkSpaceだけを終了
  4. Active Directory側のコンピューターオブジェクトを確認
  5. 正しい値でWorkSpaceを再作成

ディレクトリ登録を解除する場合は、そのディレクトリを使用するWorkSpacesと関連サービスをすべて確認する。稼働中のWorkSpacesがある状態で、ディレクトリ登録、AD Connector、サービスアカウント、OU委任または必須SGルールを先に削除しない

Amazon WorkSpaces用OU作成・権限委任・ターゲットOU設定手順

  • ✔ WorkSpacesのターゲットOUが委任先OUと一致している
  • ✔ 設定後に新規作成したWorkSpaceが対象OUへ自動配置されている

OU構成

text
ad.example.com
└─ ad
   ├─ Computers
   │  └─ WorkSpaces
   └─ Users
      ├─ ADConnectorService
      ├─ Connectors
      └─ WorkSpaces利用ユーザー

ADConnectorServiceとConnectorsの配置先はad\Usersです。権限を委任する場所は、WorkSpacesのコンピューターオブジェクトを作成するad\Computers\WorkSpacesです。アカウントの配置先と権限の委任先を混同しない

ドメイン直下の組み込みComputersコンテナーと、お客様管理領域のad\Computers OUは別の場所です。ADUCで完全なパスを確認してから操作する

注意：同じ権限委任を二重に登録しない

AD Connector用サービスアカウント作成・権限委任・運用手順でad\Computers\WorkSpacesへの委任を完了済みの場合は、詳細ACLを確認して本書の委任操作を省略します。同じConnectors、対象オブジェクト、権限および適用先のACEを重複して追加しない

  • ✔ ADUCとActive Directory PowerShellモジュールを使用できる
  • ✔ OU作成と権限委任ができるドメイン管理資格情報を使用している

WorkSpacesクライアントで管理用WorkSpaceへ接続し、Windowsデスクトップが表示されることを確認する

サーバーマネージャーの「ローカルサーバー」で、①コンピューター名とドメイン名を確認する

WorkSpaces Personalでは、登録済みディレクトリごとにコンピューターアカウントのターゲットOUを1つ指定する

  1. 保存成功の通知と、保存後のOU共通名・OU識別名を確認

新規WorkSpaceによるOU所属確認

  1. Amazon WorkSpaces作成・バンドル設定手順に従い、未使用の検証用ドメインユーザーでWorkSpaceを1台新規作成
  2. 作成前にDirectory IDとターゲットOUを再確認
  3. WorkSpaceがAVAILABLEになるまで待機
  4. ADUCでad\Computers\WorkSpacesを開き、新しいコンピューターオブジェクトを確認
  5. PowerShellでもDNを確認
powershell

Get-ADComputer -SearchBase $workSpacesOu -Filter * -Properties DistinguishedName,whenCreated |
    Select-Object Name,DistinguishedName,whenCreated

対象1台だけを確認する場合は次を実行する

powershell

    Format-List Name,DistinguishedName,whenCreated

DistinguishedNameが次の形式であることを確認する

text
CN=<コンピューター名>,OU=WorkSpaces,OU=Computers,OU=ad,DC=ad,DC=example,DC=com

コンピューターオブジェクトを後から手動移動して成功扱いにしません。新規作成時点から指定OUへ配置されたことを確認する

切り戻し

ターゲットOUを誤って設定した場合は、新規WorkSpaceの作成を停止し、WorkSpacesディレクトリのターゲットOUを変更前のDNへ戻します。誤ったOUにあるコンピューターオブジェクトは、対応するWorkSpaceを特定してから処置する

既存WorkSpaceの再構築は単なる再起動ではありません。ルートボリュームがバンドルの最新イメージから再作成され、ユーザーボリュームも最新スナップショットから再作成されます。OU反映だけを目的に安易に実行せず、バックアップ、スナップショット時刻、KMSキー、利用者影響および承認を確認した別作業として実施する

Amazon WorkSpaces用GPO作成・適用・運用手順

目次

概要

本手順書で実施すること

DCV（旧WSP）の管理テンプレートwsp.admx／wsp.admlをドメインの中央ストアへ配置し、お客様作成GPOをad\Computers\WorkSpaces OUへ直接リンクします。Amazon WorkSpaces DCV Policyでは、Configure clipboard redirectionを「有効／Copy and Paste」に設定する

併せて、検証用GPOWorkSpaces-Computer-Policyを使用し、GPO本体の作成、OUへのリンク、適用順序の変更、リンク解除とGPO本体削除の違いを確認する。最後に代表WorkSpaceでgpupdateとgpresultを実行する

完了条件

  • ✔ 中央ストアへ対象版のwsp.admxとwsp.admlを配置している
  • ✔ Amazon WorkSpaces DCV Policyがad\Computers\WorkSpacesへ直接リンクされている
  • ✔ リンクが有効、強制なし、Authenticated Users、WMIフィルターなしである
  • ✔ 親OUadに同GPOの直接リンクが残っていない
  • ✔ Configure clipboard redirectionが「有効／Copy and Paste」である
  • ✔ gpresultで対象WorkSpaceへのGPO適用を確認している
  • ✔ 検証用GPOだけを削除し、継続利用するGPOを残している

Windows WorkSpacesの管理テンプレート、適用できる設定および注意事項は出典：AWS公式：WorkSpaces PersonalでWindows WorkSpacesを管理する

Amazon WorkSpaces DCV PolicyはAWS Managed Microsoft ADの作成時に自動作成されるGPOではありません。本手順でお客様が作成し、管理するGPOです。既に存在する場合は新規作成せず、GPO名、設定、所有者、全リンク先および変更申請を照合してから使用する

前提条件

  • ✔ Amazon WorkSpaces用OU作成・権限委任・ターゲットOU設定手順を完了している
  • ✔ ad\Computers\WorkSpaces OUと対象WorkSpaceが存在する
  • ✔ ドメイン参加済み管理端末でGPMCを使用できる
  • ✔ パイロットWorkSpaceのC:\Program Files\Amazon\WSPから、対象版のwsp.admxとwsp.admlを取得している
  • ✔ 変更前のリンク、設定、セキュリティフィルター、WMIフィルターおよび適用順序を確認している
  • ✔ Amazon WorkSpaces DCV Policyが既存か未作成かを確認し、既存の場合はお客様管理GPOであることを確認している
  • ✔ 有効化する設定値がセキュリティ・運用・利用部門で承認されている

DCV用GPO本体を準備する

  1. GPMCで対象ドメインの「グループポリシーオブジェクト」を開き、Amazon WorkSpaces DCV Policyの有無を確認
  2. 既に存在する場合は、GPOの「スコープ」と「設定」を開き、全リンク先、セキュリティフィルター、WMIフィルターおよび既存設定を確認する。別用途の同名GPOやAWS管理GPOとして扱われている場合は操作を中止
  3. 存在しない場合は「グループポリシーオブジェクト」を右クリックし、「新規」を選択
  4. 名前へAmazon WorkSpaces DCV Policyを入力し、「ソース スターターGPO」は「なし」のまま作成
  5. 作成直後はリンク先がなく、設定が未構成であることを確認する。後続の「DCV用GPOのリンク範囲変更」でWorkSpaces OUだけへリンクし、「DCV設定の反映」で設定

注意：既存の同名GPOを上書きしない

同名GPOが存在する場合は、そのGPOを本手順で新規作成しません。既存のリンク先や設定が本書と異なる場合は、影響範囲を確認して変更内容を再承認する

  2. 「ソース スターターGPO」は「なし」のまま「OK」を選択

GPOの適用順序変更

同じOUに複数GPOをリンクした場合は、競合する設定がないことを確認してから順序を変更する

  1. WorkSpaces OUのリンク一覧で、Amazon WorkSpaces DCV Policyが順序1、WorkSpaces-Computer-Policyが順序2であることを確認
  1. WorkSpaces-Computer-Policyを選択し、「リンクを上に移動」を選択

図21では、①検証用GPO、②「リンクを上に移動」を確認する

  1. WorkSpaces-Computer-Policyが順序1、Amazon WorkSpaces DCV Policyが順序2になったことを確認

同じコンテナーにリンクされたGPOは、リンク順序1が最も高い優先度です。ただし、実効値はサイト、ドメイン、OU、継承、強制、セキュリティフィルターおよびWMIフィルターの影響を受けるため、代表端末のgpresultで確認する

検証用GPOの削除

本節で削除するのはWorkSpaces-Computer-Policyだけです。AWSが作成・管理するGPOと、継続利用するAmazon WorkSpaces DCV Policyは削除しない

  1. WorkSpaces-Computer-Policyの全リンク先とセキュリティフィルターを確認
  2. 必要な保持期間に従ってGPOをバックアップ
  3. GPO本体を右クリックして「削除」を選択

図23では、①削除対象、②「削除」を確認する

  1. 確認メッセージに、GPO本体とドメイン内のリンクが削除される旨が表示されていることを確認し、「はい」を選択
  1. 「グループポリシーオブジェクト」一覧から検証用GPOが消えたことを確認
  1. WorkSpaces OUのリンク一覧にAmazon WorkSpaces DCV Policyだけが残っていることを確認

特定OUへの適用だけを止める場合は、GPO本体を削除せずリンクを削除します。GPO本体を誤って削除した場合は追加変更を停止し、バックアップから復元して必要なOUへ再リンクする

GPO適用結果の確認

代表WorkSpaceで管理者PowerShellまたはコマンドプロンプトを開く

powershell
gpupdate /force
gpresult /scope computer /r

gpupdateでコンピューターとユーザーポリシーの更新成功を確認する。図27では、コンピューターのOUがad\Computers\WorkSpacesで、適用GPOにAmazon WorkSpaces DCV Policyがあり、削除したWorkSpaces-Computer-Policyがないことを確認する

適用されない場合は、gpresultの拒否理由とイベントビューアーのMicrosoft\Windows\GroupPolicy\Operationalを確認する。Active DirectoryとSYSVOLのレプリケーション待ち、セキュリティフィルター、WMIフィルター、空のGPOおよびアクセス拒否を切り分ける

多数のWorkSpacesは、通常のグループポリシー更新で順次反映されます。gpupdate /forceは代表端末での即時確認や障害調査に使用し、全台へ手動で繰り返し実行しない

ユーザーGPOとパスワードポリシー

コンピューター設定はWorkSpaceのコンピューターオブジェクトが所属するad\Computers\WorkSpacesへリンクします。ユーザー設定は利用者のユーザーオブジェクトが所属するOUへリンクします。WorkSpaces利用者だけに限定する場合は、専用ユーザーOU、セキュリティフィルター、または設計済みのループバック処理を使用する

WorkSpacesコンピューターOUへリンクするGPOは、ドメインユーザーのパスワード有効期限を変更するためのGPOではありません。ドメインの既定パスワードポリシーと、対象ユーザーへ割り当てたきめ細かなパスワードポリシーを別に管理する

切り戻し

設定値だけを戻す場合は、対象設定を「未構成」へ戻し、GPMCの「設定」、gpupdateおよびgpresultで反映を確認する。適用だけを止める場合は、WorkSpaces OUのリンクを無効化または削除し、GPO本体を保持する
