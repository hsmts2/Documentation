Amazon WorkSpaces 構築・OU・GPO

[Amazon WorkSpaces] WorkSpaces Personal構築・接続手順書

仕様

構成・動作

項目 内容
AWS管理領域 ドメインコントローラーとAWS管理のOU・GPOはAWSが管理します。
お客様管理領域 ad配下のComputersとUsersを使用します。
WorkSpaces用OU ad\Computers\WorkSpacesを作成し、コンピューターアカウントを配置します。
サービスアカウント ad\UsersのADConnectorServiceをConnectorsへ追加し、同グループへWorkSpaces OUの権限を委任します。
ターゲットOU WorkSpacesの登録済みディレクトリで、同じWorkSpaces OUを指定します。
GPO お客様作成のAmazon WorkSpaces DCV PolicyをWorkSpaces OUへ直接リンクします。

ドメイン直下のComputersコンテナーと、ad\Computers OUは別の管理領域です。ユーザーはad\Usersに配置し、WorkSpaces専用OUにはコンピューターアカウントを配置します。

本図は構築後の構成を示す説明図です。専用OU・委任・GPOは⑦と⑧で設定します。AWSが作成する領域の詳細はAWS Managed Microsoft ADで作成される内容を参照してください。

管理範囲

  • パブリックバンドル：AWSが提供するOS、コンピューティング、ストレージおよびプロトコルの組み合わせ
  • カスタムイメージ：参照WorkSpaceのOS、アプリケーションおよび設定を取り込んだイメージ
  • カスタムバンドル：カスタムイメージへコンピューティングタイプとストレージ設定を組み合わせた起動テンプレート

今回の画面では、PowerPro with Windows 10 (Server 2022 based)を選択しています。表示名に「Windows 10」が含まれますが、括弧内のServer 2022 basedを含む正式名称で記録します。

制約事項

ℹ️ 情報：ターゲットOUの反映対象

変更後に新規作成または再構築するWorkSpaceへ反映されます。既存のコンピューターアカウントは自動移動されません。詳細はWorkSpaces PersonalのOU選択を参照してください。

作業の実施順序

  1. 本書の構築作業でAD ConnectorをWorkSpacesへ登録します。
  2. ④または⑦で準備した専用OUと権限委任を確認し、⑦でターゲットOU設定を完了します。未作成の場合は、ドメイン参加済みの管理用EC2からOUを作成します。
  3. 本書へ戻り、WorkSpaceを作成して接続とOU所属を確認します。
  4. ⑧でGPOを設定し、代表WorkSpaceで適用を確認します。
  5. カスタムバンドルを使用する場合は⑨で参照WorkSpaceからイメージ・バンドルを作成し、そのバンドルを指定して追加のWorkSpaceを作成します。

構築作業

1. AD Connectorを登録する

AWS Directory ServiceでAD Connectorを作成しただけではWorkSpacesで使用できません。対象AD ConnectorをWorkSpaces Personalへ登録し、WorkSpacesを起動する2サブネットを指定します。

登録前の確認
  1. Amazon WorkSpacesコンソールを開き、「ディレクトリ」を選択します。
  2. WorkSpacesタイプが「個人」となっていることを確認します。
  3. 対象AD Connectorが登録済み一覧にないことを確認します。
  4. 「ディレクトリの作成」を選択します。
ディレクトリを登録する
  1. WorkSpacesタイプで「個人」を選択します。
  2. WorkSpaceデバイス管理で「AWS Directory Service」を選択します。
  3. Directory ID、タイプ、ドメイン、VPCおよび状態を照合して対象AD Connectorを選択します。
  4. 対象VPCのWorkSpaces用サブネットを異なるアベイラビリティーゾーンから2つ選択します。
  5. セルフサービスアクセス許可を承認済み設計に合わせます。有効にすると、利用者が再構築、コンピューティングタイプ、ボリュームおよび実行モードなどを変更でき、料金へ影響する場合があります。
  6. 「登録」を選択し、REGISTERINGから登録済みへ変わるまで待ちます。
  7. 登録後のDirectory ID、AD Connector、VPC、ドメインおよび2サブネットを確認します。

AWSが作成した<Directory ID>_workspacesMembers形式のセキュリティグループを確認し、既存ルールを削除または置換する場合は影響範囲を確認します。

登録操作の詳細は既存ディレクトリの登録を参照してください。

2. ターゲットOUを確認する

OUが未作成の場合は⑦を実施してから、次の確認を行います。

  1. WorkSpacesコンソールの「ディレクトリ」で対象AD Connectorを選択します。
  2. 「ターゲットドメインと組織単位」を開きます。
  3. Amazon WorkSpaces用OU作成・権限委任・ターゲットOU設定手順で設定したDNと一致することを確認します。
  4. Connectorsへの委任先OUとも一致することを確認します。

WorkSpaces専用OUやお客様作成GPOは、WorkSpace作成時に自動作成されません。GPOはGPMCで対象OUへリンクします。

3. WorkSpaceを作成する

詳細なコンソール操作はWorkSpaces PersonalのWorkSpaceを作成するも参照してください。

作成を開始する
  1. WorkSpacesコンソールで「WorkSpaces」を選択します。
  2. 「WorkSpacesを起動」から「個人」を選択します。
  3. 「WorkSpacesの作成」を選択します。
バンドル、ディレクトリおよびユーザーを指定する
  1. 「手動で設定」を選択します。
  2. 「WorkSpacesバンドルを使用」を選択します。
  3. 正式名称、Bundle ID、OS、プロトコルおよびコンピューティングタイプを確認して、承認済みバンドルを選択します。
  4. 実行モードを選択し、AutoStopの場合は停止までの時間を指定します。
  5. Directory ID、ドメインおよびVPCを照合して登録済みAD Connectorを選択します。
  6. 申請されたドメインユーザーを選択します。
  7. ルート80GB、ユーザー50GBを指定します。
  8. ルート／ユーザーボリュームの暗号化とKMSキーを承認済み設計に合わせます。
  9. 必須タグ、ローカル管理者権限、追加SG、インターネット接続およびデバイスアクセス制御を確認します。

選択したバンドルの詳細で、バンドルID、言語、OS、プロトコルおよびハードウェアを確認します。

図5のパブリックバンドル詳細にはルート175GB／ユーザー100GBが表示されます。今回のWorkSpace作成ではカスタマイズ欄で80GB／50GBを選択します。バンドル詳細の既定表示と、作成時に確定したストレージを混同しません。

⚠️ 注意：ストレージと暗号化は作成前に確定する

WorkSpace作成後、ボリュームは拡張できますが縮小できません。暗号化なしで作成したWorkSpaceへ後から暗号化を追加すること、暗号化済みWorkSpaceから暗号化を解除することもできません。誤った場合は利用者影響とデータ退避を確認して再作成します。

作成を実行する
  1. バンドル、Directory ID、ユーザー、実行モード、ストレージ、暗号化、KMSキーおよびタグを最終確認します。
  2. 「WorkSpacesの作成」を選択します。
  3. 一覧で状態が「構築中」またはPENDINGになったことを確認します。
  1. 状態が「使用可能」またはAVAILABLEになるまで待ちます。
  2. WorkSpace ID、ユーザー、コンピューター名、バンドル、80GB／50GB、実行モード、DCV、IPアドレスおよび暗号化状態を確認します。

4. OU所属とクライアント接続を確認する

Active Directory
  1. ADUCでad\Computers\WorkSpacesを開き、新しいコンピューターオブジェクトを確認します。
  2. コンピューター名がWorkSpacesコンソールの値と一致することを確認します。
  3. ⑧を実施済みの場合は、gpresult /scope computer /rでAmazon WorkSpaces DCV Policyの適用を確認します。初回構築で⑧が未実施の場合は、接続確認後に⑧へ進みます。
クライアント接続
  1. WorkSpacesクライアントをインストールします。
  2. 対象ディレクトリの登録コードを入力します。
  3. Active Directoryのユーザー名とパスワードでサインインします。
  4. デスクトップ、業務ネットワーク、DNS、時刻同期および必要アプリケーションを確認します。
  5. AutoStopを使用する場合は、切断、停止および再接続を確認します。

取得時の登録コードは画面例です。実作業では接続先ディレクトリの登録コードを使用します。パスワードは画面キャプチャや作業記録へ残しません。

接続完了画面は⑦の管理端末確認の図1を参照してください。

運用作業

1. よくある問い合わせと切り分け

次の5件は、AD ConnectorでWorkSpacesを使用する際に問い合わせが多い内容です。詳細な条件と最新情報はWorkSpaces Personalに関する問題のトラブルシューティングを参照してください。

招待メールまたはパスワードリセットメールが届かない

AD Connector、信頼されたドメイン、またはActive Directoryに既に存在するユーザーを使用する場合、ウェルカムメールやパスワードリセットメールは自動送信されません。管理者が登録コード、クライアントの入手先および接続方法を安全な経路で案内し、パスワードリセットはActive Directory管理者が実施します。

「パスワードを忘れた場合」が表示されない

AD Connectorまたは信頼されたドメインのユーザーは、WorkSpacesクライアントからパスワードをセルフリセットできません。Active Directory側で本人確認とパスワードリセットを行い、「次回ログオン時にパスワード変更が必要」を有効にした場合のWorkSpaces接続可否も運用手順に従って確認します。

DNS unavailable

AD Connectorから指定DNSサーバーのTCP 53とUDP 53へ通信できない場合に発生します。AD Connectorの両サブネットから両DNS IPへのルート、セキュリティグループ、ネットワークACLおよびDNSサーバー側ファイアウォールを確認します。

Connectivity issues detected

LDAP unavailable (TCP port 389)またはKerberos/authentication unavailable (TCP port 88)が表示された場合は、AD ConnectorからドメインコントローラーへのTCP／UDP 88（Kerberos）とTCP／UDP 389（LDAP）を確認します。片方のドメインコントローラーだけでなく、両方へ到達できることを確認します。

SRV record

AD Connectorは、指定DNSサーバーから_ldap._tcp.<DNSドメイン名>と_kerberos._tcp.<DNSドメイン名>のSRVレコードを取得する必要があります。次のコマンドで両レコードを確認し、対象ドメインコントローラーが返ることを確認します。

PowerShell
Resolve-DnsName -Type SRV '_ldap._tcp.ad.example.com'
Resolve-DnsName -Type SRV '_kerberos._tcp.ad.example.com'

最後の3件はAD Connectorの作成・接続診断でも発生します。WorkSpace作成を繰り返す前に、AD Connector側のネットワークとDNSを解消します。

2. 作成に失敗した場合

  1. AD ConnectorとWorkSpacesへのディレクトリ登録が正常か確認します。
  2. 両サブネットから両DNSサーバー／ドメインコントローラーへ到達できることを確認します。
  3. サブネットの空きIP、2つのAZ、往復ルート、SGおよびネットワークACLを確認します。
  4. ADConnectorServiceの有効化、ロック、パスワード期限およびAD Connectorに保存した認証情報を確認します。
  5. ConnectorsのOU委任とWorkSpacesのターゲットOUが一致することを確認します。
  6. 対象ユーザー、重複WorkSpace、Service QuotasおよびKMSキー権限を確認します。
  7. WorkSpacesのエラーメッセージ、CloudTrailおよびAWS Health Dashboardを確認します。

接続したディレクトリでWorkSpaceの起動が繰り返し失敗する場合は、AD Connector指定時の両DNSサーバー／ドメインコントローラーへ各ディレクトリサブネットから到達できることを確認します。必要に応じて各サブネットへ検証用EC2を起動し、両DNS IPを使ったドメイン参加で切り分けます。

3. 誤作成時の対応

  1. 対象WorkSpaceのID、ユーザー、Directory IDおよび誤設定内容を照合します。
  2. 利用者へ登録コードを案内せず、必要なデータがないことを確認します。
  3. 対象WorkSpaceだけを終了します。
  4. Active Directory側のコンピューターオブジェクトを確認します。
  5. 正しい値でWorkSpaceを再作成します。

ディレクトリ登録を解除する場合は、そのディレクトリを使用するWorkSpacesと関連サービスをすべて確認します。稼働中のWorkSpacesがある状態で、ディレクトリ登録、AD Connector、サービスアカウント、OU委任または必須SGルールを先に削除しません。

[Amazon WorkSpaces] ターゲットOU作成・権限委任手順書

仕様

構成・動作

text
ad.example.com
└─ ad
   ├─ Computers
   │  └─ WorkSpaces
   └─ Users
      ├─ ADConnectorService
      ├─ Connectors
      └─ WorkSpaces利用ユーザー

ADConnectorServiceとConnectorsの配置先はad\Usersです。権限を委任する場所は、WorkSpacesのコンピューターオブジェクトを作成するad\Computers\WorkSpacesです。アカウントの配置先と権限の委任先を混同しません。

ドメイン直下の組み込みComputersコンテナーと、お客様管理領域のad\Computers OUは別の場所です。ADUCで完全なパスを確認してから操作します。

⚠️ 注意：同じ権限委任を二重に登録しない

AD Connector用サービスアカウント作成・権限委任・運用手順でad\Computers\WorkSpacesへの委任を完了済みの場合は、詳細ACLを確認して本書の委任操作を省略します。同じConnectors、対象オブジェクト、権限および適用先のACEを重複して追加しません。

管理範囲

お客様管理OU配下を対象とし、ConnectorsへWorkSpacesコンピューターの管理に必要な権限を委任します。AWS管理領域の設定は変更しません。

制約事項

ターゲットOUは登録済みディレクトリごとに1つ指定します。変更後の新規作成・再構築に適用され、既存オブジェクトは自動移動されません。

構築作業

ℹ️ 情報：工程ごとに前提を確認する

OU作成と権限委任は、AD Connector作成前に管理用EC2から実施できます。④で同じOUとConnectorsへの委任を完了している場合は、設定内容を照合します。ターゲットOUの保存は、⑥でディレクトリを登録した後、新規WorkSpaceを作成する前に実施します。

1. 管理端末と既存WorkSpaceを確認する

管理用EC2または既存の管理用WorkSpaceへ接続します。初回構築でWorkSpaceがない場合は、ドメイン参加済みの管理用EC2を使用します。図1と図2は管理用WorkSpaceでの確認例です。

サーバーマネージャーの「ローカルサーバー」で、コンピューター名とドメイン名を確認します。

PowerShellで確認する場合は次を実行し、PartOfDomainがTrue、Domainが対象ドメインとなっていることを確認します。

PowerShell
Get-CimInstance Win32_ComputerSystem |
    Select-Object Name, Domain, PartOfDomain

作成済みWorkSpaceがある場合は、ターゲットOUの変更前に現在の所属OUを確認します。初回構築でWorkSpaceがない場合は、この確認を省略します。

PowerShell
Get-ADComputer -Identity '<WorkSpaceのコンピューター名>' -Properties DistinguishedName |
    Format-List Name, DistinguishedName

⚠️ 注意：ターゲットOU変更は既存WorkSpaceを移動しない

ターゲットOUの変更は、変更後に新規作成または再構築したWorkSpaceへ反映されます。既存WorkSpaceのコンピューターオブジェクトは自動移動されません。

2. WorkSpaces OUを作成する

同じDNのOUが存在する場合は、OUの配置先と誤削除防止を確認し、新規作成を省略します。

OUを新規作成する
  1. 対象ドメインの管理資格情報でADUCを開きます。
  2. ad.example.com、ad、Computersの順に展開します。
  3. ad\Computersを右クリックし、「新規作成」から「組織単位」を選択します。
  1. 名前へWorkSpacesを入力します。
  2. 「コンテナーを誤って削除されないように保護する」を有効のままにします。
  3. 「OK」を選択します。
  1. 左ツリーと右ペインの両方で、ad\Computers配下にWorkSpaces OUが表示されることを確認します。
OUのDNを確認する
PowerShell
$workSpacesOuDn = 'OU=WorkSpaces,OU=Computers,OU=ad,DC=ad,DC=example,DC=com'

Get-ADOrganizationalUnit -Identity $workSpacesOuDn -Properties ProtectedFromAccidentalDeletion |
    Select-Object Name, DistinguishedName, ProtectedFromAccidentalDeletion

NameがWorkSpaces、DistinguishedNameが承認済みDN、ProtectedFromAccidentalDeletionがTrueとなっていることを確認します。

3. Connectorsへの権限委任を確認・設定する

委任内容
項目 選択内容
委任先OU ad\Computers\WorkSpaces
委任対象 Connectors
タスク 委任するカスタムタスク
オブジェクト種類 コンピューターオブジェクト
作成・削除 選択したオブジェクトの作成、選択したオブジェクトの削除
アクセス許可 読み取り、書き込み

WorkSpaces専用OUにはユーザーを配置しないため、ユーザーオブジェクトの作成・削除・書き込み権限は追加しません。ユーザー検索に必要な既存の読み取り権限は維持し、WorkSpacesコンソールから対象ユーザーを検索できることを別途確認します。

委任ウィザードを実行する
  1. ADUCでad\Computers\WorkSpacesを右クリックし、「制御の委任」を選択します。
  1. ウィザードで「次へ」を選択し、「追加」からConnectorsを指定します。
  2. 「名前の確認」で対象ドメインのConnectorsへ解決されたことを確認し、「OK」、「次へ」の順に選択します。
  1. 「委任するカスタムタスクを作成する」を選択して「次へ」を選択します。
  1. 「フォルダー内の次のオブジェクトのみ」を選択します。
  2. 「コンピューター オブジェクト」と、選択したオブジェクトの作成・削除を選択して「次へ」を選択します。
  1. 表示カテゴリで「全般」を選び、「読み取り」と「書き込み」を選択します。
  2. 「次へ」を選択し、完了画面で委任内容を確認して「完了」を選択します。

⚠️ 注意：作成・削除と読み取り・書き込みを組み合わせる

図9の作成・削除と、図10の読み取り・書き込みを組み合わせて委任します。上部の「プロパティ固有」は表示カテゴリです。選択しただけでは権限は付与されません。

詳細ACLを確認する
  1. ADUCの「表示」から「拡張機能」を有効にします。
  2. WorkSpaces OUの「プロパティ」、「セキュリティ」、「詳細設定」の順に開きます。
  3. Connectorsのアクセス許可エントリを確認します。
  4. OU自体にコンピューターオブジェクトの作成・削除、子コンピューターオブジェクトに読み取り・書き込みがあることを確認します。
  5. 適用先がWorkSpaces OUまたは子コンピューターオブジェクトへ限定され、フルコントロールや親OU全体への権限がないことを確認します。

ADConnectorServiceを直接ACLへ追加せず、Connectorsグループ経由で委任します。

PowerShellでACLを参照する場合の実行例です。出力のConnectorsに関するエントリと適用先を、上記の詳細設定画面と照合します。

PowerShell
dsacls "OU=WorkSpaces,OU=Computers,OU=ad,DC=ad,DC=example,DC=com"

4. WorkSpacesのターゲットOUを設定する

WorkSpaces Personalでは、登録済みディレクトリごとにコンピューターアカウントのターゲットOUを1つ指定します。設定方法はWorkSpacesディレクトリの管理も参照してください。

  1. AWSマネジメントコンソールでAmazon WorkSpacesを開き、対象リージョンを確認します。
  2. 「ディレクトリ」から対象AD Connectorを選択します。
  3. Directory ID、ドメイン、VPCおよびサブネットを作業申請と照合します。
  4. 「ターゲットドメインと組織単位」で「編集」を選択します。
  5. WorkSpacesを検索し、承認済みDNと一致するOUを選択します。
  6. 候補に表示されない場合は、承認済みDNをカスタムOUとして入力します。
  7. 「保存」を選択します。
  1. 保存成功の通知と、保存後のOU共通名・OU識別名を確認します。

5. 新規WorkSpaceのOU所属を確認する

  1. Amazon WorkSpaces作成・バンドル設定手順に従い、未使用の検証用ドメインユーザーでWorkSpaceを1台新規作成します。
  2. 作成前にDirectory IDとターゲットOUを再確認します。
  3. WorkSpaceがAVAILABLEになるまで待ちます。
  4. ADUCでad\Computers\WorkSpacesを開き、新しいコンピューターオブジェクトを確認します。
  5. PowerShellでもDNを確認します。
PowerShell
$workSpacesOu = 'OU=WorkSpaces,OU=Computers,OU=ad,DC=ad,DC=example,DC=com'

Get-ADComputer -SearchBase $workSpacesOu -Filter * -Properties DistinguishedName,whenCreated |
    Select-Object Name,DistinguishedName,whenCreated

対象1台だけを確認する場合は次を実行します。

PowerShell
Get-ADComputer -Identity '<WorkSpaceのコンピューター名>' -Properties DistinguishedName,whenCreated |
    Format-List Name,DistinguishedName,whenCreated

DistinguishedNameが次の形式となっていることを確認します。

text
CN=<コンピューター名>,OU=WorkSpaces,OU=Computers,OU=ad,DC=ad,DC=example,DC=com

コンピューターオブジェクトを後から手動移動して成功扱いにしません。新規作成時点から指定OUへ配置されたことを確認します。

運用作業

1. 設定を切り戻す

ターゲットOUを誤って設定した場合は、新規WorkSpaceの作成を停止し、WorkSpacesディレクトリのターゲットOUを変更前のDNへ戻します。誤ったOUにあるコンピューターオブジェクトは、対応するWorkSpaceを特定してから処置します。

既存WorkSpaceの再構築は単なる再起動ではありません。ルートボリュームがバンドルの最新イメージから再作成され、ユーザーボリュームも最新スナップショットから再作成されます。OU反映だけを目的に安易に実行せず、バックアップ、スナップショット時刻、KMSキー、利用者影響および承認を確認した別作業として実施します。

[Amazon WorkSpaces] GPO作成・適用・運用手順書

仕様

構成・動作

  • WorkSpaces固有設定をDefault Domain Policyへ追加しない
  • お客様管理OUad配下に、お客様作成GPOをリンクする
  • GPO本体の既存設定とリンク範囲を確認した後に対象OUへ直接リンクする
  • 適用だけを止める場合は、GPO本体を残してリンクを無効化または削除する
  • GPO本体を削除する場合は、お客様作成GPOだけを対象にし、バックアップと全リンク先を確認する
  • AWSが作成・管理するGPOを変更、削除またはリンク解除しない
GPO 用途 最終状態
Amazon WorkSpaces DCV Policy お客様が作成・管理するDCV固有設定 WorkSpaces OUへ直接リンクして継続利用
WorkSpaces-Computer-Policy GPO管理操作の確認 リンク・順序変更・削除を確認後に削除
WorkSpaces-User-Policy 利用者向け設定 ユーザーOUまたはループバック設計後に別途作成

Windows WorkSpacesの管理テンプレート、適用できる設定および注意事項はWorkSpaces PersonalでWindows WorkSpacesを管理するを参照してください。

Amazon WorkSpaces DCV PolicyはAWS Managed Microsoft ADの作成時に自動作成されるGPOではありません。本手順でお客様が作成し、管理するGPOです。既に存在する場合は新規作成せず、GPO名、設定、所有者、全リンク先および変更申請を照合してから使用します。

管理範囲

コンピューター設定はWorkSpaceのコンピューターオブジェクトが所属するad\Computers\WorkSpacesへリンクします。ユーザー設定は利用者のユーザーオブジェクトが所属するOUへリンクします。WorkSpaces利用者だけに限定する場合は、専用ユーザーOU、セキュリティフィルター、または設計済みのループバック処理を使用します。

WorkSpacesコンピューターOUへリンクするGPOは、ドメインユーザーのパスワード有効期限を変更するためのGPOではありません。ドメインの既定パスワードポリシーと、対象ユーザーへ割り当てたきめ細かなパスワードポリシーを別に管理します。

制約事項

同じOUのリンク順序は1が最優先です。継承・強制・フィルターも適用結果に影響するため、代表WorkSpaceで確認します。検証用GPOの作成・順序変更・削除は任意の運用確認です。

構築作業

1. DCV管理テンプレートを中央ストアへ配置する

中央ストアは次のパスです。

text
\\ad.example.com\SYSVOL\ad.example.com\Policies\PolicyDefinitions

既にPolicyDefinitionsがある場合は、フォルダー全体を作り直したり、ローカルのフォルダー一式で上書きしたりしません。対象ファイルだけを版管理して追加します。

パイロットWorkSpaceからwsp.admxを次へコピーします。

text
コピー元：C:\Program Files\Amazon\WSP\wsp.admx
コピー先：\\ad.example.com\SYSVOL\ad.example.com\Policies\PolicyDefinitions\wsp.admx

PolicyDefinitionsが未作成の場合は、中央ストアで使用するWindows用テンプレート一式を準備してから作成します。既存ストアがある場合は対象のDCVファイルだけを追加・更新します。

PolicyDefinitions配下に言語フォルダーen-USがあることを確認します。存在しない場合は同名のフォルダーを作成します。

wsp.admlを次へコピーします。

text
コピー元：C:\Program Files\Amazon\WSP\wsp.adml
コピー先：\\ad.example.com\SYSVOL\ad.example.com\Policies\PolicyDefinitions\en-US\wsp.adml

⚠️ 注意：中央ストア全体を置換しない

中央ストアは同一ドメインのGPMC利用者が共有します。既存ファイルを削除せず、追加するファイルの取得元、更新日時およびバージョンを確認します。

中央ストアの準備はグループポリシー管理用テンプレートの中央ストアを参照してください。

2. DCV用GPO本体を準備する

  1. GPMCで対象ドメインの「グループポリシーオブジェクト」を開き、Amazon WorkSpaces DCV Policyの有無を確認します。
  2. 既に存在する場合は、GPOの「スコープ」と「設定」を開き、全リンク先、セキュリティフィルター、WMIフィルターおよび既存設定を確認します。別用途の同名GPOやAWS管理GPOとして扱われている場合は操作を中止します。
  3. 存在しない場合は「グループポリシーオブジェクト」を右クリックし、「新規」を選択します。
  4. 名前へAmazon WorkSpaces DCV Policyを入力し、「ソース スターターGPO」は「なし」のまま作成します。

本図は名前を入力する画面です。直前の手順では「グループポリシーオブジェクト」から「新規」を選択し、GPO本体を作成します。

  1. 作成直後はリンク先がなく、設定が未構成となっていることを確認します。後続の「DCV用GPOをWorkSpaces OUへリンクする」でリンク先を設定し、「DCV設定を反映する」で設定します。

⚠️ 注意：既存の同名GPOを上書きしない

同名GPOが存在する場合は、そのGPOを本手順で新規作成しません。既存のリンク先や設定が本書と異なる場合は、影響範囲を確認して変更内容を再承認します。

3. DCV管理テンプレートの表示を確認する

Amazon WorkSpaces DCV Policyを編集し、次を展開します。

text
コンピューターの構成
└─ ポリシー
   └─ 管理用テンプレート
      └─ Amazon
         └─ WSP

AWS資料ではDCV、GPMCのテンプレート名ではWSPと表示される場合があります。Amazon > WSPの設定一覧を確認します。

図6の全項目が「未構成」の場合、この画面で確認できるのはテンプレートの読み込みまでです。設定値の反映は後続の図15～17で確認します。

4. DCV用GPOをWorkSpaces OUへリンクする

最初にWorkSpaces OUへ対象GPOを直接リンクし、リンクが有効となっていることを確認します。親OUad側に同じGPOのリンクが存在する場合だけ、他の子OUへの影響を確認したうえで親OU側のリンクを削除します。

WorkSpaces OUへ直接リンクする
  1. GPMCでad\Computers\WorkSpacesを右クリックします。
  2. 「既存のGPOのリンク」を選択します。
  1. Amazon WorkSpaces DCV Policyを選択して「OK」を選択します。
  1. WorkSpaces OUのリンク一覧で、「リンクの有効化」が「はい」、「強制」が「いいえ」、WMIフィルターが「なし」となっていることを確認します。
  2. セキュリティフィルターはAuthenticated Usersとします。
親OUのリンクだけを削除する
  1. WorkSpaces OU側の直接リンクが有効となっていることを確認します。
  2. 親OUadに同じGPOの直接リンクがあるかを確認します。リンクがない場合は削除操作を行わず、「GPO本体のスコープを確認する」へ進みます。
  3. 親OUにリンクがある場合は、ad配下の子OUとコンピューターを確認し、WorkSpaces OU以外でこのGPOを継承している対象がないこと、または継承を止めても影響がないことを確認します。ほかの子OUや端末がこのGPOを必要としている場合は、親OUのリンクを削除せず、対象別のリンク設計を再検討します。
  4. 影響がないことを確認できた場合だけ、親OUad直下に表示されるAmazon WorkSpaces DCV Policyのリンクを右クリックし、「削除」を選択します。
  1. 確認メッセージに「この操作ではGPO自体は削除されません」と表示されていることを確認して「OK」を選択します。
  1. GPO本体が残り、WorkSpaces OUに同GPOの直接リンクが1件あることを確認します。

「リンクの有効化」がチェック済みの場合は押し直しません。押すとリンクが無効になります。リンクの削除とGPO本体の削除は別の操作です。

GPO本体のスコープを確認する
  1. 「グループポリシーオブジェクト」配下のAmazon WorkSpaces DCV Policyを選択します。
  2. 「スコープ」を開き、リンク先が次の1件だけとなっていることを確認します。
text
ad.example.com/ad/Computers/WorkSpaces
  1. 強制なし、リンク有効、Authenticated Users、WMIフィルターなしを確認します。

詳細レポートでも、GPO本体、リンク先とセキュリティフィルターを照合できます。

図14はドメインルートへ直接リンクされたGPOとリンク順序の確認例です。WorkSpaces専用GPOのリンク先は、WorkSpaces OUで確認します。

Default Domain PolicyへAmazon\WSP設定を追加していないことも確認します。

5. DCV設定を反映する

Amazon WorkSpaces DCV Policyを編集し、Computer Configuration\Policies\Administrative Templates\Amazon\WSPのConfigure clipboard redirectionを開きます。

  1. 「有効」を選択します。
  2. オプションをCopy and Pasteにします。
  3. 「適用」、「OK」の順に選択します。

設定一覧で、Configure clipboard redirectionだけが「有効」となっていることを確認します。

GPO本体の「設定」で、Configure clipboard redirectionが「有効」、Clipboard redirection optionがCopy and Pasteとなっていることを確認します。

Copy and Pasteでは双方向のコピー＆ペーストを許可します。GPMCの設定値、gpresultの適用GPO名と、接続後のコピー＆ペースト動作を確認します。

6. GPO適用結果を確認する

代表WorkSpaceで管理者PowerShellまたはコマンドプロンプトを開きます。

PowerShell
gpupdate /force
gpresult /scope computer /r

gpupdateでコンピューターとユーザーポリシーの更新成功を確認します。図18では、コンピューターのOUがad\Computers\WorkSpacesで、適用GPOにAmazon WorkSpaces DCV Policyがあり、検証用のWorkSpaces-Computer-Policyがないことを確認します。

適用されない場合は、gpresultの拒否理由とイベントビューアーのMicrosoft\Windows\GroupPolicy\Operationalを確認します。Active DirectoryとSYSVOLのレプリケーション待ち、セキュリティフィルター、WMIフィルター、空のGPOおよびアクセス拒否を切り分けます。

多数のWorkSpacesは、通常のグループポリシー更新で順次反映されます。gpupdate /forceは代表端末での即時確認や障害調査に使用し、全台へ手動で繰り返し実行しません。

DCV設定の動作確認はポリシー更新後にセッションを終了して再接続してから行います。必要に応じて作業時間内にWorkSpaceを再起動します。

運用作業

1. 検証用GPOで管理操作を確認する（任意）

ℹ️ 情報：検証用GPOを使用する場合

以下はGPO管理操作を確認する場合だけ実施します。空のWorkSpaces-Computer-Policyを作成し、リンク・順序変更・削除まで完了します。通常のDCV用GPO構築だけの場合は省略できます。

検証用GPO本体の作成

WorkSpaces-Computer-Policyは、GPO本体の作成、リンク、リンク順序変更、リンク解除および削除という管理操作を確認するための一時GPOです。設定値は追加しないため、ポリシーの機能適用を検証するGPOではありません。承認済みの作業時間内だけ使用し、本書の削除手順まで同じ作業で完了します。

  1. gpmc.mscを起動します。
  2. 対象ドメインの「グループポリシーオブジェクト」を右クリックし、「新規」を選択します。
  1. GPO名へWorkSpaces-Computer-Policyを入力します。
  2. 「ソース スターターGPO」は「なし」のまま「OK」を選択します。
  1. GPO本体が作成され、「スコープ」のリンク一覧が空となっていることを確認します。

本体作成時は「グループポリシーオブジェクト」から「新規」を使用します。GPOの作成とOUへのリンクを分け、後続手順でリンク先を明示的に選択します。

検証用GPOのリンク
  1. WorkSpaces OUを右クリックし、「既存のGPOのリンク」を選択します。
  1. WorkSpaces-Computer-Policyを選択して「OK」を選択します。
GPOの適用順序変更

同じOUに複数GPOをリンクした場合は、競合する設定がないことを確認してから順序を変更します。

  1. WorkSpaces OUのリンク一覧で、Amazon WorkSpaces DCV Policyが順序1、WorkSpaces-Computer-Policyが順序2となっていることを確認します。
  1. WorkSpaces-Computer-Policyを選択し、「リンクを上に移動」を選択します。
  1. WorkSpaces-Computer-Policyが順序1、Amazon WorkSpaces DCV Policyが順序2になったことを確認します。

同じコンテナーにリンクされたGPOは、リンク順序1が最も高い優先度です。ただし、実効値はサイト、ドメイン、OU、継承、強制、セキュリティフィルターおよびWMIフィルターの影響を受けるため、代表端末のgpresultで確認します。

検証用GPOの削除

本節で削除するのはWorkSpaces-Computer-Policyだけです。AWSが作成・管理するGPOと、継続利用するAmazon WorkSpaces DCV Policyは削除しません。

  1. WorkSpaces-Computer-Policyの全リンク先とセキュリティフィルターを確認します。
  2. 必要な保持期間に従ってGPOをバックアップします。
  3. GPO本体を右クリックして「削除」を選択します。
  1. 確認メッセージに、GPO本体とドメイン内のリンクが削除される旨が表示されていることを確認し、「はい」を選択します。
  1. 「グループポリシーオブジェクト」一覧から検証用GPOが消えたことを確認します。
  1. WorkSpaces OUのリンク一覧にAmazon WorkSpaces DCV Policyだけが残っていることを確認します。

特定OUへの適用だけを止める場合は、GPO本体を削除せずリンクを削除します。GPO本体を誤って削除した場合は追加変更を停止し、バックアップから復元して必要なOUへ再リンクします。

2. 既定GPOのスコープと継承を参照する

GPMCでDefault Domain Policyを選択し、「スコープ」を開きます。リンク先、リンクの有効化、強制、セキュリティフィルターおよびWMIフィルターを参照します。AWSが管理するGPOの設定やリンクは変更しません。

取得時の画面では、ドメインとAWS Reservedへのリンク、Authenticated Usersのセキュリティフィルター、WMIフィルター「なし」が表示されています。これはスコープの確認例です。個々の端末への適用結果は、前節のgpresultで確認します。

GPMCでDomain Controllersを選択すると、AWS管理GPOと時刻同期GPOを参照できます。設定やリンクは変更しません。

adの「グループポリシーの継承」では、Default Domain PolicyとServerAdminsの継承を確認できます。WorkSpacesの実効設定はWorkSpaces OUと対象端末で確認します。

3. 設定を切り戻す

新規に追加した設定値だけを戻す場合は、対象設定を「未構成」へ戻し、GPMCの「設定」、gpupdateおよびgpresultで反映を確認します。変更前に設定値が存在した場合は、その値へ戻します。適用だけを止める場合は、WorkSpaces OUのリンクを無効化または削除し、GPO本体を保持します。
