AD Connector用サービスアカウントの作成・権限委任・運用手順

文書の位置づけ

本書では、Amazon WorkSpacesで使用するAD Connectorについて、接続先のAWS Managed Microsoft ADに専用サービスアカウントを作成し、必要最小限の権限を付与して運用する手順を記載する

対象となる操作は次のとおりである

  1. 委任用セキュリティグループConnectorsを作成
  2. AD Connector専用サービスアカウントを作成
  3. サービスアカウントをConnectorsへ追加
  4. WorkSpacesのコンピューターオブジェクト格納先OUを決定または作成
  5. 対象OUへ、WorkSpacesのドメイン参加に必要な権限を委任
  6. アカウント状態、グループ所属および委任先を確認
  7. AD Connector作成後の動作確認、パスワード変更および廃止を行う

AD Connector自体の作成、WorkSpacesへのディレクトリ登録およびWorkSpaceの作成は、別手順書の対象とする

重要

Connectorsグループとサービスアカウントの格納先はp-pm\Usersで問題ない。権限の委任先は、WorkSpacesのコンピューターオブジェクトが実際に作成されるOU、またはその権限を継承させる承認済みの親OUとする。OU名だけで既存の委任を誤りと断定せず、WorkSpacesのターゲットOUと継承設計を確認して判断する

前提条件

  • 対象ドメインに参加したWindows管理端末を使用すること
  • Active Directoryユーザーとコンピューター（ADUC）がインストールされていること
  • AWS Managed Microsoft ADのお客様管理OUで、グループ、ユーザー、OUおよび委任設定を管理できるドメイン資格情報を使用すること
  • 作業対象のDNSドメイン、NetBIOS名、OUおよびアカウント名が承認済みの設計と一致していること
  • WorkSpacesで使用するコンピューター格納先OUを、AD Connector作成前に決定していること
  • パスワードの保管先、更新担当者、更新周期、次回更新日および障害時の連絡先が決定していること
  • パスワードを本書、作業チケット、チャット、コマンド履歴および画面キャプチャへ記録しないこと

ローカルのAdministratorで管理端末へサインインしただけでは、Active Directoryを変更できない。ADUCと確認用PowerShellは、対象ドメインの管理資格情報で起動する

アカウントと権限の設計

サービスアカウント

  • AD Connectorごとに、通常のADドメインユーザーを1アカウント用意する
  • 人が通常作業へ使用するユーザーと共用しない
  • Domain Admins、Enterprise Admins、AWS Delegated Administratorsなどの高権限グループへ追加しない
  • Domain Usersと、承認済みのConnectorsだけに所属させる
  • 「ユーザーは次回ログオン時にパスワード変更が必要」は無効にする
  • アカウントを有効、未ロックの状態に保つ
  • KerberosおよびLDAPによるネットワーク認証を妨げる設定を行わない

AD ConnectorはAWSコンソールへユーザー名とパスワードを登録する方式であるため、本書ではグループ管理サービスアカウント（gMSA）ではなく、専用の通常ユーザーを使用する

コンピューター格納先OU

WorkSpaces専用OUは自動作成されない。専用OUを指定しない場合は既定のコンピューター格納先が使用されるが、GPOの適用範囲と委任権限を分離しやすくするため、次のような専用OUを作成することを推奨する

text
p-pm
└─ Computers
   └─ WorkSpaces

本番で使用するOUは設計承認後に確定し、WorkSpacesへディレクトリを登録した後の「ターゲットドメインと組織単位」に同じOUを指定する。委任先OUとWorkSpaces側の指定OUを一致させる

操作手順

  1. 承認済みのOU設計を確認
  2. 専用OUを作成する場合は、p-pm\Computersを右クリックし、「新規作成」から「組織単位（OU）」を選択

powershell
Get-ADOrganizationalUnit -Filter * |

  • 既存のp-pm\Usersへの委任は、WorkSpacesコンピューター作成先OUまたは承認済みの親OUと一致するかを確認して採否を判断すること
  • 後続のWorkSpaces設定で、このOUと同じDNを指定すること

WorkSpaces用コンピューターOUへ権限を委任する

本環境ではp-pm\Computers\WorkSpacesをコンピューター専用OUとして使用します。このため、同OUへ委任する正本はAmazon WorkSpaces用OU作成・権限委任・ターゲットOU設定手順の6章とし、Connectorsへコンピューターオブジェクトの作成、削除、読み取りおよび書き込みだけを委任する

AWS公式の汎用例ではコンピューターオブジェクトとユーザーオブジェクトの両方を選択する場合がありますが、ユーザーを格納しない本環境のWorkSpaces専用OUへ、ユーザーオブジェクトの作成・削除・書き込み権限は追加しません。ユーザー検索に必要な読み取りはp-pm\Users側で維持し、AD Connectorが「アクティブ」でWorkSpacesコンソールから対象ユーザーを検索できることで確認する

権限の範囲を広げないため、委任開始時に選択するOUが最重要である。WorkSpacesコンピューター作成先OU、または権限を継承させる承認済みの親OUから開始する。AWS Managed Microsoft ADでは、ドメインルート、AWS ReservedおよびDomain Controllersから開始しない

操作手順

  1. ADUCで、承認済みのWorkSpacesコンピューター格納先OUを選択
  2. 対象OUを右クリックし、「制御の委任」を選択

本書の採用方針

本環境では「コンピューター オブジェクト」だけを選択し、権限がドメイン全体へ広がらないよう、委任先を承認済みのWorkSpacesコンピューターOUへ限定します。ユーザーオブジェクトの作成・削除・書き込みは委任しない

組織のセキュリティ基準によりコンピューターオブジェクトだけへ限定する場合は、AWS Managed Microsoft ADのドメイン参加権限の手順との差異、WorkSpacesの作成・再構築・削除試験、および承認結果を記録してから変更する

期待結果と不足証跡

  • Connectorsの委任先が、承認済みのWorkSpacesコンピューター作成先OUまたは承認済みの親OUと一致していること
  • ドメインルートおよびAWS管理OUへ新しい委任を付与していないこと
  • 図8～図13は操作説明画像として掲載済みである。構築証跡を完成させるため、追加取得候補C、DおよびEを取得すること

作成後の確認

ADオブジェクトの確認

対象ドメインの管理資格情報でPowerShellを起動して実行します。本番では、ADConnectorServiceを承認済みの環境別サービスアカウント名へ読み替える

powershell
Get-ADUser -Identity 'ADConnectorService' `
    -Properties Enabled,LockedOut,PasswordExpired,PasswordNeverExpires,PasswordLastSet |
    Select-Object SamAccountName,
                  Enabled,
                  LockedOut,
                  PasswordExpired,
                  PasswordNeverExpires,
                  PasswordLastSet

Get-ADPrincipalGroupMembership 'ADConnectorService' |
    Select-Object Name, GroupScope, GroupCategory

次を確認する

  • EnabledがTrueであること
  • LockedOutとPasswordExpiredがFalseであること
  • Connectorsへ所属していること
  • 申請されていない高権限グループへ所属していないこと

OUの委任内容は、承認済みのDNへ読み替えて確認する

powershell
dsacls '<WorkSpacesコンピューターOUのDN>'

出力にはSIDや環境情報が含まれる。現行の提出方針では追加マスキングを行わないが、提出対象が削除予定の検証環境であることを確認し、認証情報が含まれないことを確認する

AD ConnectorおよびWorkSpacesの確認

AD Connector作成後に次を確認する

  1. Directory ServiceでAD Connectorのステータスが「アクティブ」であることを確認
  2. WorkSpacesから対象ディレクトリのADユーザーを検索できることを確認
  3. 検証用WorkSpaceを1台作成できることを確認
  4. コンピューターオブジェクトが承認済みのWorkSpaces OUへ作成されることを確認
  5. 検証ユーザーがWorkSpaceへサインインできることを確認
  6. 再構築および削除の検証で、OU権限エラーが発生しないことを確認

ネットワーク接続テストだけでは、OUへのコンピューターオブジェクト作成権限まで確認できない。最終確認には検証用WorkSpaceの作成が必要である

パスワード運用

AWS Managed Microsoft ADの既定ドメインポリシーでは、パスワードの最大有効期間は42日である。Fine-Grained Password Policy（FGPP）または承認済みの例外設定がない場合、サービスアカウントにも適用される

期限切れ、ロック、無効化、または「次回ログオン時にパスワード変更」が有効になると、AD Connectorのユーザー検索およびWorkSpacesのドメイン参加が失敗する可能性がある

定期変更

  1. 変更日時、担当者、対象AD Connector、影響確認項目および切り戻し担当者を確定
  2. AD側でサービスアカウントのパスワードを変更
  3. 直後にDirectory Serviceの対象AD Connectorを開き、サービスアカウント認証情報を同じ新パスワードへ更新
  4. AD Connectorのステータスが「アクティブ」であることを確認
  5. WorkSpacesからADユーザーを検索できることを確認
  6. 必要に応じて検証用WorkSpaceの作成またはドメイン接続を確認
  7. 次回更新日と結果を運用台帳へ記録

変更順序は、必ず「AD側」から「AD Connector側」とする。AD Connector側だけを更新しても、Active Directory側のパスワードは変更されない

42日の既定ポリシーを使用する場合は、期限到達前に十分な余裕を持って変更する。少なくとも期限の7日前までに変更を完了できる運用を推奨する

障害時の確認

  • アカウントが有効であること
  • アカウントがロックされていないこと
  • パスワードが期限切れでないこと
  • 次回ログオン時の変更が要求されていないこと
  • Directory Serviceへ登録された認証情報がAD側の現在値と一致していること
  • 対象OUに、承認済みの委任が残っていること

無効化・削除・切り戻し

AD Connectorが使用中のサービスアカウントを先に無効化、削除またはConnectorsから除外してはならない

安全に切り替える場合は、次の順序で実施する

  1. 新しい専用サービスアカウントを作成し、Connectorsへ追加
  2. AD Connectorの認証情報を新アカウントへ更新
  3. AD Connectorの「アクティブ」、ユーザー検索および検証用WorkSpace作成を確認
  4. 問題がある場合は、AD Connectorを旧アカウントへ戻す
  5. 正常確認後に旧アカウントを無効化
  6. 定められた観察期間後に、旧アカウントをConnectorsから除外して削除

委任設定を削除する場合は、対象OUの詳細なセキュリティ設定でConnectorsに対する明示的なアクセス制御エントリだけを削除する。継承された権限や、他のユーザー・グループの権限を変更しない

既存のp-pm\Usersへの委任が適切かは、WorkSpacesのターゲットOUと継承設計を確認して判断する。対象外OUへの不要な明示的委任と確認できた場合に限り、正しいOUへの委任と動作確認が完了してから、Users OU上のConnectorsに対する明示的な権限だけを削除する

VPCピアリング・ドメインコントローラーSG変更・AD Connector作成手順

1. 文書の目的

本書では、Amazon WorkSpacesからAWS Managed Microsoft ADを利用するために、次の作業を実施する手順を記載する

  1. AWS Managed Microsoft AD配置VPCとAD Connector／WorkSpaces配置VPCをVPCピアリングで接続し、双方のルートを設定
  2. AWS Managed Microsoft ADのドメインコントローラー用セキュリティグループ（以下、DC用SG）へ接続元VPCの許可ルールを追加
  3. WorkSpacesを配置するVPCにAD Connectorを作成
  4. AD Connectorが作成したセキュリティグループと接続状態を確認

本書の画像は、2026年9月1日および2日にp-pm.example.comで実施した検証作業の画面である。顧客環境はworkspaces.example.comであり、画面中のDirectory ID、VPC ID、サブネットID、SG ID、DNS IPおよびアカウント表示を、そのまま本番値として使用してはならない

画像の提出方針

全体構築作業順序に従い、管理用EC2起動・接続・AD管理開始手順と、AD Connector用サービスアカウント作成・権限委任・運用手順を先に完了する。WorkSpacesへのディレクトリ登録およびWorkSpaceの作成は、Amazon WorkSpaces作成・バンドル設定手順を使用する

2. AWSの仕様と本環境の設計を区別する

AD Connector接続時の最小要件として、接続先ドメインコントローラーに対し、AD Connectorを配置する2サブネットのCIDRからTCP/UDP 53、88、389を許可します。これはAD Connectorがディレクトリへ接続するための最小3ポートであり、WorkSpace本体がドメイン参加・認証・GPO等でドメインコントローラーと通信するための全要件ではない

WorkSpaces VPCとディレクトリコントローラー間では、DNS、Kerberos、NTP、RPC、Netlogon、LDAP、SMB、LDAPS、動的RPCおよびグローバルカタログ等の追加ポートが必要です。ポートを限定する設計へ変更する場合は、作業時点の要件一覧、方向、プロトコルおよび送信元／宛先を確認します。また、AD Connectorの2サブネットは異なるアベイラビリティーゾーンに配置する必要がある

本顧客環境では、複数VPCからのActive Directory関連通信とSGルール数を考慮し、各接続元VPCのCIDRから「すべてのトラフィック」を1ルールずつ許可する設計が既存資料で確認されている。これは本環境固有のセキュリティ例外であり、AWS共通の必須設定または最小権限の例ではない。必要ポートへ限定できるかを検討し、限定しない理由とリスクを変更申請に記録して承認を得る。採用時は、送信元CIDR、ルーティング、ネットワークACLおよび組織のセキュリティ基準を再確認する

3. 前提条件

  • 作業リージョンがアジアパシフィック（東京）であること
  • AWS Managed Microsoft ADおよび対象VPCが作成済みであること
  • Managed AD側VPCとAD Connector側VPCのCIDRが重複していないこと
  • 対象VPC、対象サブネットおよび両VPCの変更対象ルートテーブルを特定済みであること
  • DC用SGと、変更対象Directory IDの対応をAWS Directory Serviceコンソールで確認できること
  • AD Connector用の2サブネットが、同一VPCかつ異なるアベイラビリティーゾーンにあり、同じネットワークタイプであること
  • 対象VPCのハードウェアテナンシーがdefaultであること
  • 接続先が単一ラベルドメインではなく、完全修飾ドメイン名であること
  • Active Directoryのドメイン機能レベルがWindows Server 2003以上であること
  • 対象ユーザーのKerberos事前認証が有効であること
  • 接続先DNSサーバー／ドメインコントローラーのIPアドレスを2つ確認済みであること
  • _ldap._tcp.<DNSドメイン名>および_kerberos._tcp.<DNSドメイン名>のSRVレコードが接続先DNSで解決できること
  • Connectorsグループ、専用サービスアカウントおよびWorkSpacesコンピューター格納先OUへの委任が準備済みであること
  • サービスアカウントが有効、未ロック、パスワード期限内で、「次回ログオン時にパスワード変更」が無効であること
  • WorkSpaces利用時は、サービスアカウントにコンピューターのドメイン参加、コンピューターオブジェクトの作成、および対象OUへの読み取り・書き込み権限があること
  • 作業申請、実施時間、切り戻し担当者および影響確認方法が決定していること

5.5 SG変更前に経路と名前解決を確認する

次を確認してからDC用SGを変更します。名前解決と疎通確認は、選択する各AD Connectorサブネットと同じルートおよびネットワークACL条件を持つ接続元から、2台の接続先DNS／DC IPの双方へ実施します。Managed AD側VPC内の管理EC2だけでの成功は、VPCピアリング経由の到達性を証明しません。2台は主系／待機系ではなく、どちらも利用可能なDCとして動作するため、双方への到達性が必要です。詳細はAWS Managed Microsoft ADの2台ドメインコントローラー構成・役割を参照する

  • VPCピアリング接続の状態がアクティブである
  • AD Connector側VPCからManaged AD側VPCへの往路が保存済みである
  • Managed AD側VPCからAD Connector側VPCへの戻り経路が保存済みである
  • 双方のネットワークACLが必要通信を拒否していない
  • VPCのDNSサポートおよびDNSホスト名が設計どおりである
  • 接続先DNSでADのSRVレコードを取得できる

AD Connector作成画面ではManaged ADのDNS IPを直接指定するため、VPCピアリングの「DNS解決を有効化」は本接続の必須条件ではありません。別用途でピアリング先のプライベートDNS名を解決する設計がある場合だけ、その要件に従って有効化する

確認例：

powershell
$dnsServers = @('192.168.225.68', '192.168.225.110')
foreach ($dnsServer in $dnsServers) {
    Resolve-DnsName -Type SRV '_ldap._tcp.workspaces.example.com' -Server $dnsServer
    Resolve-DnsName -Type SRV '_kerberos._tcp.workspaces.example.com' -Server $dnsServer
    Test-NetConnection -ComputerName $dnsServer -Port 53
    Test-NetConnection -ComputerName $dnsServer -Port 88
    Test-NetConnection -ComputerName $dnsServer -Port 389
}

TCPの確認だけではUDP疎通を証明できないため、ネットワークACL、SGおよびフローログも合わせて確認する

10. 障害時の確認順序

  1. 接続先DNS IPを、AD Connector自身のIPと取り違えていないか
  2. VPCピアリングがアクティブか
  3. 両VPCのルートテーブルに往復経路があるか
  4. DC用SGに正しい接続元CIDRがあるか
  5. ネットワークACLでDNS、Kerberos、LDAPおよび戻り通信が拒否されていないか
  6. _ldap._tcpと_kerberos._tcpのSRVレコードを2台のDNSから取得できるか
  7. サービスアカウントが有効、未ロック、期限内か
  8. 「次回ログオン時にパスワード変更」が無効か
  9. Connectorsグループ所属と対象OUへの委任が残っているか
  10. WorkSpaces利用時の読み取り・書き込み権限があるか

11. パスワード変更時の注意

サービスアカウントのパスワードが期限切れ、ロック、無効、またはAD Connector登録値と不一致になると、ユーザー検索やドメイン参加が失敗する可能性がある

パスワードを変更する場合は、次の順序を守る

  1. 変更前に、サービスアカウントとAD Connectorの対応表を確認
  2. 1アカウントを複数AD Connectorで共有している場合は、影響する全コネクタを同一作業で更新する計画と切り戻し手順を用意
  3. Active Directory側で専用サービスアカウントのパスワードを変更
  4. 直後にDirectory Serviceの対象AD Connectorすべてで「サービスアカウントの認証情報」を更新
  5. 各AD Connectorが「アクティブ」であることを確認
  6. 既存のWorkSpaceがある場合は、WorkSpacesからのユーザー検索と既存WorkSpaceのドメイン接続を確認します。既存WorkSpaceがない場合は、ユーザー検索をディレクトリ登録後に確認し、新規の検証用WorkSpaceは課金を伴うため承認後にAmazon WorkSpaces作成・バンドル設定手順で作成
  7. 次回更新日と担当者を運用台帳へ記録

11.1 WorkSpaces未使用時の登録状態と課金

AD ConnectorをWorkSpacesへ登録した後、30日間連続してWorkSpacesが関連付かない場合は、WorkSpacesから自動的に登録解除されることがある。その後はDirectory Serviceの料金条件に従うため、検証用WorkSpaceを削除した際は、ディレクトリ登録状態と課金影響も運用確認の対象とする

12. 切り戻し・削除

12.1 SG変更の切り戻し

AD Connector作成前に中止する場合は、今回追加した送信元CIDRのルールだけを削除します。既存のAWS管理ルールや他VPC用ルールを変更しないでください。削除前後のルール件数と対象CIDRを記録する

AD ConnectorまたはWorkSpacesが利用中の場合は、先にSGルールを削除しないでください。利用状況、依存リソースおよび通信影響を確認してから変更する

12.2 AD Connectorの削除

  1. 対象AD Connectorを使用するWorkSpacesがないことを確認
  2. WorkSpacesからディレクトリ登録を解除
  3. Directory Serviceの「アプリケーション管理」で、WorkSpacesを含むすべての関連サービスが解除済みであり、他の依存関係がないことを確認
  4. AD Connectorを削除
  5. 削除後にAWS管理のENIとSGの削除／残存状態を確認します。稼働中にENIやSGを手動削除せず、残存する場合は依存関係を調査
  6. 不要になったDC用SGの追加ルールを、変更申請に従い削除します。VPC CIDR単位の許可を削除する前に、同じCIDR内のドメイン参加済みEC2やその他のリソースがManaged ADを利用していないことを確認
  7. サービスアカウントが他のAD ConnectorやAWS連携で共有されていないことを確認
  8. サービスアカウントは直ちに削除せず、観察期間後に無効化・削除
