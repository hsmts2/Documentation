AD Connector 構築・権限委任

AD Connector専用サービスアカウントと最小権限の委任を準備する
VPCピアリング、往復ルート、DC用Security GroupおよびAD Connector作成を依存順にまとめる

AD Connector用サービスアカウントの作成・権限委任・運用手順

目次

概要

本手順書で実施すること

AWS Managed Microsoft ADのad\Usersに、委任用セキュリティグループConnectorsとAD Connector専用ユーザーADConnectorServiceを作成します。サービスアカウントをConnectorsへ追加したうえで、Amazon WorkSpacesのコンピューターオブジェクト作成先ad\Computers\WorkSpacesに、コンピューターオブジェクトの作成、削除、読み取りおよび書き込み権限を委任する

本手順では、サービスアカウントの状態確認、パスワード変更時の更新順序および使用終了時の切り替えも取り扱います。AD Connector本体の作成とAmazon WorkSpacesの作成は、別手順書で実施する

完了条件

次の項目をすべて確認できた時点で、本作業を完了とする

  • ✔ Connectorsがグローバル／セキュリティグループとして作成されている
  • ✔ ADConnectorServiceが有効かつ未ロックで、初回ログオン時のパスワード変更が無効である
  • ✔ ADConnectorServiceがConnectorsへ所属し、申請されていない高権限グループへ所属していない
  • ✔ Connectorsの委任先がad\Computers\WorkSpacesである
  • ✔ WorkSpacesのコンピューターオブジェクトを指定OUへ作成・削除できる

注意：アカウントの配置先と権限委任先を分ける

ConnectorsとADConnectorServiceの配置先はad\Usersです。今回の権限委任先は、WorkSpacesのコンピューターオブジェクトが作成されるad\Computers\WorkSpacesです。配置先のad\Usersへ機械的に委任しないでください

前提条件

  • ✔ 対象ドメインに参加したWindows管理端末を使用している
  • ✔ Active Directoryユーザーとコンピューター（ADUC）がインストールされている
  • ✔ AWS Managed Microsoft ADのお客様管理OUで、グループ、ユーザー、OUおよび委任設定を管理できるドメイン資格情報を使用している
  • ✔ DNSドメイン、NetBIOS名、OUおよびアカウント名が承認済みの設計と一致している
  • ✔ WorkSpacesのコンピューターオブジェクト作成先OUが決定している
  • ✔ パスワードの保管先、更新担当者、更新周期および障害時の連絡先が決定している
  • ✔ パスワードを手順書、作業チケット、チャット、コマンド履歴および画面キャプチャへ記録しない運用になっている

ローカルのAdministratorで管理端末へサインインしただけでは、Active Directoryを変更できません。ADUCと確認用PowerShellは、対象ドメインの管理資格情報で起動する

本番環境のOU、グループおよびサービスアカウント名は、現時点の設計値を記載しています。本番作業前に構成資料と照合し、変更承認がある場合だけ更新する

アカウントと権限の設計

サービスアカウント

  • AD Connectorごとに、通常のADドメインユーザーを1アカウント用意する
  • 人が通常作業へ使用するユーザーと共用しない
  • Domain Admins、Enterprise Admins、AWS Delegated Administratorsなどの高権限グループへ追加しない
  • Domain Usersと、承認済みのConnectorsだけに所属させる
  • 「ユーザーは次回ログオン時にパスワード変更が必要」は無効にする
  • アカウントを有効、未ロックの状態に保つ
  • KerberosおよびLDAPによるネットワーク認証を妨げる設定を行わない

AD ConnectorはAWSコンソールへユーザー名とパスワードを登録する方式であるため、本書ではグループ管理サービスアカウント（gMSA）ではなく、専用の通常ユーザーを使用する

AD Connectorで使用するサービスアカウントには、ユーザーとグループの読み取りが必要です。Amazon WorkSpacesで使用する場合は、コンピューターのドメイン参加とコンピューターオブジェクトの作成権限も必要

出典：AWS公式：AD Connectorの前提条件とサービスアカウントへの権限委任

コンピューター格納先OU

WorkSpaces専用OUは自動作成されません。専用OUを指定しない場合は既定のコンピューター格納先が使用されますが、GPOの適用範囲と委任権限を分離しやすくするため、次のような専用OUを使用する

text
ad
└─ Computers
   └─ WorkSpaces

本番では表のad\Computers\WorkSpacesを使用し、WorkSpacesへディレクトリを登録した後の「ターゲットドメインと組織単位」に同じOUを指定します。作業前に構成資料と照合し、委任先OUとWorkSpaces側の指定OUを一致させる

操作手順

  1. ad\Usersで、作成したサービスアカウントのプロパティを開く

  2. 「所属するグループ」タブを選択

  3. 既定のDomain Users以外に、意図しない高権限グループが表示されていないことを確認

  4. 「追加」を選択

  5. オブジェクト名へConnectorsを入力

  6. 「名前の確認」を選択し、対象ドメインのConnectorsへ解決されることを確認

  7. 「OK」を選択

  8. 「所属するグループ」にDomain UsersとConnectorsが表示されることを確認

  9. 「適用」、「OK」の順に選択

実施後の確認

  • ✔ サービスアカウントがConnectorsのメンバーである
  • ✔ Domain Admins、Enterprise Admins、AWS Delegated Administratorsなど、申請されていない高権限グループへ所属していない

WorkSpaces用コンピューターOUを決定または作成する

この節と次の権限委任は、WorkSpaces側のOU手順を未実施の場合だけ行います。Amazon WorkSpaces用OU作成・権限委任・ターゲットOU設定手順で同じOUとConnectorsへの委任を完了済みの場合は、OUと詳細ACLが本節の要件を満たすことだけを確認し、ウィザードを再実行しない

操作手順

  1. 承認済みのOU設計を確認
  2. 専用OUを作成する場合は、ad\Computersを右クリックし、「新規作成」から「組織単位（OU）」を選択
  3. 今回および本番の設定値としてWorkSpacesを入力します。本番作業前に表の設計値と一致することを確認
  4. 誤削除防止設定を有効にして作成
  5. OUのプロパティまたはPowerShellで識別名（DN）を確認し、運用台帳へ記録
powershell
Get-ADOrganizationalUnit -Filter * |
    Select-Object Name, DistinguishedName

実施後の確認

  • ✔ WorkSpacesのコンピューターオブジェクト格納先が一意に決まっている
  • ✔ ドメインルートまたはAWS管理OUを委任先にしていない
  • ✔ WorkSpaces側のターゲットOUと同じ識別名（DN）を使用する

WorkSpaces用コンピューターOUへ権限を委任する

本環境ではad\Computers\WorkSpacesをコンピューター専用OUとして使用します。OU作成とWorkSpaces側のターゲットOU設定は、Amazon WorkSpaces用OU作成・権限委任・ターゲットOU設定手順を参照してください。本手順では、Connectorsへコンピューターオブジェクトの作成、削除、読み取りおよび書き込みだけを委任する

既存ACLに同じConnectorsのアクセス許可エントリがある場合は、対象オブジェクト、権限および適用先を詳細ACLで照合します。要件を満たしていれば委任ウィザードを再実行せず、重複ACEを作成しない

AWS公式の汎用例ではコンピューターオブジェクトとユーザーオブジェクトの両方を選択する場合がありますが、ユーザーを格納しない本環境のWorkSpaces専用OUへ、ユーザーオブジェクトの作成・削除・書き込み権限は追加しません。ユーザー検索に必要な読み取りはad\Users側で維持し、AD Connectorが「アクティブ」でWorkSpacesコンソールから対象ユーザーを検索できることで確認する

権限の範囲を広げないため、委任開始時にad\Computers\WorkSpacesを選択したことを確認する。AWS Managed Microsoft ADでは、ドメインルート、AWS ReservedおよびDomain Controllersから開始しない

操作手順

  1. ADUCで、承認済みのWorkSpacesコンピューター格納先OUを選択

  2. 対象OUを右クリックし、「制御の委任」を選択

  3. 「オブジェクト制御の委任ウィザードの開始」が表示されたことを確認し、「次へ」を選択します。この開始画面自体には対象OUは表示されない

作成後の確認

ADオブジェクトの確認

対象ドメインの管理資格情報でPowerShellを起動して実行します。本番でも表のADConnectorServiceを使用します。構成変更が承認されている場合だけ、コマンドのアカウント名を変更後の値へ読み替える

powershell
Get-ADUser -Identity 'ADConnectorService' `
    -Properties Enabled,LockedOut,PasswordExpired,PasswordNeverExpires,PasswordLastSet |
    Select-Object SamAccountName,
                  Enabled,
                  LockedOut,
                  PasswordExpired,
                  PasswordNeverExpires,
                  PasswordLastSet

Get-ADPrincipalGroupMembership 'ADConnectorService' |
    Select-Object Name, GroupScope, GroupCategory

次を確認する

  • ✔ EnabledがTrueである
  • ✔ LockedOutとPasswordExpiredがFalseである
  • ✔ Connectorsへ所属している
  • ✔ 申請されていない高権限グループへ所属していない

OUの委任内容は、承認済みのDNへ読み替えて確認する

powershell
dsacls '<WorkSpacesコンピューターOUのDN>'

AD ConnectorおよびWorkSpacesの確認

AD Connector作成後に次を確認する

  1. Directory ServiceでAD Connectorのステータスが「アクティブ」であることを確認
  2. WorkSpacesから対象ディレクトリのADユーザーを検索できることを確認
  3. 検証用WorkSpaceを1台作成できることを確認
  4. コンピューターオブジェクトが承認済みのWorkSpaces OUへ作成されることを確認
  5. 検証ユーザーがWorkSpaceへサインインできることを確認
  6. 再構築および削除の検証で、OU権限エラーが発生しないことを確認

ネットワーク接続テストだけでは、OUへのコンピューターオブジェクト作成権限まで確認できません。最終確認には新しい検証用WorkSpaceの作成が必要

パスワード運用

AWS Managed Microsoft ADの既定ドメインポリシーでは、パスワードの最大有効期間は42日です。Fine-Grained Password Policy（FGPP）または承認済みのアカウント例外がない場合、サービスアカウントにも適用される

期限切れ、ロック、無効化、または「次回ログオン時にパスワード変更」が有効になると、AD Connectorのユーザー検索およびWorkSpacesのドメイン参加が失敗する可能性がある

PasswordNeverExpires=Trueはアカウント単位の例外であり、PSOの適用を示すものではありません。実効パスワードポリシーは次のコマンドで確認する

powershell
Get-ADUserResultantPasswordPolicy -Identity 'ADConnectorService'

定期変更

  1. 変更日時、担当者、対象AD Connector、影響確認項目および切り戻し担当者を確定
  2. AD側でサービスアカウントのパスワードを変更
  3. 直後にDirectory Serviceの対象AD Connectorを開き、サービスアカウント認証情報を同じ新パスワードへ更新
  4. AD Connectorのステータスが「アクティブ」であることを確認
  5. WorkSpacesからADユーザーを検索できることを確認
  6. 必要に応じて検証用WorkSpaceの作成またはドメイン接続を確認
  7. 次回更新日と結果を運用台帳へ記録

警告：パスワード変更はAD側から実施する

変更順序は、必ず「AD側」から「AD Connector側」とします。AD側で変更した直後に、AD Connectorへ保存されている認証情報を同じ新パスワードへ更新してください。AD Connector側だけを更新しても、Active Directory側のパスワードは変更されない

42日の既定ポリシーを使用する場合は、組織で承認された更新周期に従い、有効期限より前に変更を完了する

障害時の確認

  • アカウントが有効であること
  • アカウントがロックされていないこと
  • パスワードが期限切れでないこと
  • 次回ログオン時の変更が要求されていないこと
  • Directory Serviceへ登録された認証情報がAD側の現在値と一致していること
  • 対象OUに、承認済みの委任が残っていること

無効化・削除・切り戻し

AD Connectorが使用中のサービスアカウントを先に無効化、削除またはConnectorsから除外しない

安全に切り替える場合は、次の順序で実施する

  1. 新しい専用サービスアカウントを作成し、Connectorsへ追加
  2. AD Connectorの認証情報を新アカウントへ更新
  3. AD Connectorの「アクティブ」、ユーザー検索および検証用WorkSpace作成を確認
  4. 問題がある場合は、AD Connectorを旧アカウントへ戻す
  5. 正常確認後に旧アカウントを無効化
  6. 定められた観察期間後に、旧アカウントをConnectorsから除外して削除

委任設定を削除する場合は、対象OUの詳細なセキュリティ設定でConnectorsに対する明示的なアクセス制御エントリだけを削除します。継承された権限や、他のユーザー・グループの権限を変更しない

既存のad\Usersへの委任が適切かは、WorkSpacesのターゲットOUと継承設計を確認して判断します。対象外OUへの不要な明示的委任と確認できた場合に限り、正しいOUへの委任と動作確認が完了してから、Users OU上のConnectorsに対する明示的な権限だけを削除する

AD Connectorで作成される内容

AD Connectorを作成すると、Directory Serviceは選択した2つのサブネットに対応する2つのアベイラビリティーゾーンへAD Connectorインスタンスを配置し、各インスタンスへENIを作成します。これらのENIはVPCとAD Connector間の接続に必要なため、手動で削除しません。障害が発生したAD Connectorインスタンスは、同じアベイラビリティーゾーンで同じIPアドレスを使用して自動的に置き換えられる

AD Connectorは既存Active Directoryへの認証要求を中継し、ディレクトリデータをAWS側へレプリケートしない

出典：AWS公式：AD Connectorで作成されるもの

通信要件と本環境の設計

AD Connector接続時の最小要件として、接続先ドメインコントローラーに対し、AD Connectorを配置する2サブネットのCIDRからTCP/UDP 53、88、389を許可します。これはAD Connectorがディレクトリへ接続するための最小3ポートであり、WorkSpace本体がドメイン参加・認証・GPO等でドメインコントローラーと通信するための全要件ではない

WorkSpaces VPCとディレクトリコントローラー間では、DNS、Kerberos、NTP、RPC、Netlogon、LDAP、SMB、LDAPS、動的RPCおよびグローバルカタログ等の追加ポートが必要です。ポートを限定する設計へ変更する場合は、作業時点の要件一覧、方向、プロトコルおよび送信元／宛先を確認する。また、AD Connectorの2サブネットは異なるアベイラビリティーゾーンに配置する必要がある

本番環境では、複数VPCからのActive Directory関連通信とSGルール数を考慮し、各接続元VPCのCIDRから「すべてのトラフィック」を1ルールずつ許可する設計が既存資料で確認されています。これは本環境固有のセキュリティ例外であり、AWS共通の必須設定または最小権限の例ではありません。必要ポートへ限定できるかを検討し、限定しない理由とリスクを変更申請に記録して承認を得ます。採用時は、送信元CIDR、ルーティング、ネットワークACLおよび組織のセキュリティ基準を再確認する

出典：AWS公式：AD Connectorの前提条件

  • ✔ AWS Managed Microsoft ADおよび対象VPCが作成済みである

本番環境での確認コマンドを次に示します。192.168.225.110は構築前に現行のDirectory Serviceコンソールで再確認し、実際のDNS IPが異なる場合はコマンドを置き換える

powershell
$dnsServers = @('192.168.225.68', '192.168.225.110')
foreach ($dnsServer in $dnsServers) {
    Resolve-DnsName -Type SRV '_ldap._tcp.ad.datumidea.jp' -Server $dnsServer
    Resolve-DnsName -Type SRV '_kerberos._tcp.ad.datumidea.jp' -Server $dnsServer
    Test-NetConnection -ComputerName $dnsServer -Port 53
    Test-NetConnection -ComputerName $dnsServer -Port 88
    Test-NetConnection -ComputerName $dnsServer -Port 389
}

TCPの確認だけではUDP疎通を証明できないため、ネットワークACL、SGおよびフローログも合わせて確認する

障害時の確認順序

  1. 接続先DNS IPを、AD Connector自身のIPと取り違えていないか
  2. VPCピアリングがアクティブか
  3. 両VPCのルートテーブルに往復経路があるか
  4. DC用SGに正しい接続元CIDRがあるか
  5. ネットワークACLでDNS、Kerberos、LDAPおよび戻り通信が拒否されていないか
  6. _ldap._tcpと_kerberos._tcpのSRVレコードを2台のDNSから取得できるか
  7. サービスアカウントが有効、未ロック、期限内か
  8. 「次回ログオン時にパスワード変更」が無効か
  9. Connectorsグループ所属と対象OUへの委任が残っているか
  10. WorkSpaces利用時の読み取り・書き込み権限があるか

パスワード変更時の注意

サービスアカウントのパスワードが期限切れ、ロック、無効、またはAD Connector登録値と不一致になると、ユーザー検索やドメイン参加が失敗する可能性がある

PasswordNeverExpires=Trueはアカウント単位の例外であり、PSOが適用されている根拠ではありません。実効パスワードポリシーはGet-ADUserResultantPasswordPolicyで確認する

パスワードを変更する場合は、次の順序で実施する

  1. 変更前に、サービスアカウントとAD Connectorの対応表を確認
  2. 1アカウントを複数AD Connectorで共有している場合は、影響する全コネクタを同一作業で更新する計画と切り戻し手順を用意
  3. Active Directory側で専用サービスアカウントのパスワードを変更
  4. 直後にDirectory Serviceの対象AD Connectorすべてで「サービスアカウントの認証情報」を更新
  5. 各AD Connectorが「アクティブ」であることを確認
  6. 既存のWorkSpaceがある場合は、WorkSpacesからのユーザー検索と既存WorkSpaceのドメイン接続を確認する。既存WorkSpaceがない場合は、ユーザー検索をディレクトリ登録後に確認し、新規の検証用WorkSpaceは課金を伴うため承認後にAmazon WorkSpaces作成・バンドル設定手順で作成
  7. 次回更新日と担当者を運用台帳へ記録

警告：AD側の変更直後にAD Connectorの保存資格情報も更新する

パスワードは最初にActive Directory側で変更し、直後に対象AD Connectorへ保存されている認証情報を同じ新パスワードへ更新します。AD Connector側だけを更新しても、Active Directory側のパスワードは変更されない

WorkSpaces未使用時の登録状態と課金

AD ConnectorをWorkSpacesへ登録した後、30日間連続してWorkSpacesが関連付かない場合は、WorkSpacesから自動的に登録解除され、Directory Serviceの料金条件に従って課金されます。検証用WorkSpaceを削除した際は、ディレクトリ登録状態と課金影響を確認する

出典：AWS公式：WorkSpaces Personalへのディレクトリ登録と登録解除

切り戻し・削除

SG変更の切り戻し

AD Connector作成前に中止する場合は、今回追加した送信元CIDRのルールだけを削除します。既存のAWS管理ルールや他VPC用ルールを変更しないでください。削除前後のルール件数と対象CIDRを記録する

AD ConnectorまたはWorkSpacesが利用中の場合は、先にSGルールを削除しないでください。利用状況、依存リソースおよび通信影響を確認してから変更する

AD Connectorの削除

  1. 対象AD Connectorを使用するWorkSpacesがないことを確認
  2. WorkSpacesからディレクトリ登録を解除
  3. Directory Serviceの「アプリケーション管理」で、WorkSpacesを含むすべての関連サービスが解除済みであり、他の依存関係がないことを確認
  4. AD Connectorを削除
  5. 削除後にAWS管理のENIとSGの削除／残存状態を確認する。稼働中にENIやSGを手動削除せず、残存する場合は依存関係を調査
  6. 不要になったDC用SGの追加ルールを、変更申請に従い削除します。VPC CIDR単位の許可を削除する前に、同じCIDR内のドメイン参加済みEC2やその他のリソースがManaged ADを利用していないことを確認
  7. サービスアカウントが他のAD ConnectorやAWS連携で共有されていないことを確認
  8. サービスアカウントは直ちに削除せず、観察期間後に無効化・削除
